# Bloch L2-EVM — design
**Status: DESIGN ONLY. Not built, not audited, not safe. Testnet / zero-value.** An EVM-compatible Layer-2 for the ownerless Bloch-SIS-PoW base, designed so real Uniswap/ERC-20 contracts deploy UNCHANGED (PosternDex = literally Uniswap on the L2). It is an **owned Postern product** (it has a sequencer/operator) that ANCHORS to the ownerless base as ordinary transactions — the base gains no operator and needs no consensus change. Companion: [`POSTERNDEX-AMM-DESIGN.md`](POSTERNDEX-AMM-DESIGN.md), [`POSTERNDEX-BRIDGE-DESIGN.md`](POSTERNDEX-BRIDGE-DESIGN.md).
> **The reorg gate (read first).** An L2 inherits its L1's finality. Bloch today is k=4 forgeable, 51%-attackable, unaudited — a Bloch reorg can unwind L2 state anchored to reorged blocks. Real value is gated on Bloch mainnet security (k=8 ramp, WAN hashrate, checkpoint finality) + a third-party audit + legal review. Everything below is testnet/zero-value until then.
_Generated from a 16-agent design fleet (1 PMO → 5 Fable-5 designers → 10 Sonnet reviewers). Each component carries its reviewers' verdicts._

## 1. EVM Execution Layer for the Bloch L2 (revm, Ethereum account/state model, bridged-BLCH gas, eth_* JSON-RPC) — the execution half of a zk-validity rollup that anchors to the ownerless Bloch-SIS-PoW base as ordinary transactions. DESIGN ONLY: unbuilt, unaudited, testnet/zero-value first.

**Architecture.** One Rust crate, `bloch-l2-evm`, with two build targets sharing byte-identical execution logic: (1) NATIVE — embedded in the L2 sequencer/full node (built as a Reth-SDK node: reth-node-builder with a single-sequencer consensus stub, custom ChainSpec, reth's jsonrpsee RPC stack, revm as the executor — the exact pattern op-reth uses); (2) GUEST — compiled for riscv32im/no_std inside the SP1 program (component 3), following Succinct's RSP (Reth Succinct Processor) pattern: the host supplies an ExecutionWitness (partial Merkle-Patricia tries + bytecodes + 256 ancestor headers), the guest verifies all witness proofs against the committed pre-state root, re-executes the block(s) with the SAME pinned revm, and commits (prev_state_root, new_state_root, batch commitment, withdrawal root, Bloch anchor ref) as public values. The EVM itself is UNMODIFIED revm pinned to a named hardfork (SpecId::CANCUN at genesis; Prague via a coordinated, height-gated upgrade that changes the SP1 program vkey). State is the standard Ethereum account model — account = (nonce, balance, codeHash, storageRoot), keccak-256 hexary MPT for both the account trie and per-account storage tries — so the state root anchored to Bloch is a plain Ethereum state root and `eth_getProof` works unchanged. The native gas token is an L2 REPRESENTATION OF BRIDGED BLCH: zero issuance on the L2 (block reward = 0), balances enter only via deposit system-transactions (OP-Stack-style type-0x7E envelope processed at block start, minting to the recipient exactly what was escrowed on L1) and leave via withdrawals proven against the anchored state root. Never a new coin, never sold — consistent with BLCH's not-a-security posture. Unit mapping: BLCH is u64 base units with 8 decimals on L1; the L2 scales by 10^10 so 1 BLCH = 10^18 wei-equivalent and MetaMask/ethers display naturally; the bridge enforces the scaling is exact and total L2 supply ≤ L1 escrow. Fees: EIP-1559 active as Cancun specifies; the basefee is NOT destroyed but routed to a disclosed BaseFeeVault predeploy (protocol-level fee accounting outside EVM opcode semantics — the OP Stack precedent — chosen so no bridged BLCH is ever burned and the L1 escrow always balances, and so Postern never operates a BLCH burn); priority fee → SequencerFeeVault; COINBASE returns the fee-vault address. Anchoring: every batch the sequencer writes one ordinary zero-value Bloch TxOutput whose script_pubkey is an "L2V0" envelope (same zero-consensus-change trick as TKV0) carrying batch index, prev/new state roots, DA commitment, and the SP1 vkey hash; Bloch nodes neither parse nor verify it — the base gains no operator and needs no consensus change. The full FRI proof (SP1 core proof, raw STARK — never the Groth16/Plonk wrapper, per the repo's post-quantum coherence rule) is far too large for a 1MB Bloch block; it lives in the DA/proof-distribution layer and ANYONE running the open-source L2 verifier checks it against the anchored roots. Determinism contract for guest re-execution (normative): integer-only arithmetic (revm/ruint/alloy-primitives are u256 integer math; `#![deny(clippy::float_arithmetic)]` in the shared crate; no f32/f64 anywhere in the execution path); no host randomness or time — block.timestamp is set by the sequencer under a monotonicity rule and bounded drift against the referenced Bloch anchor header's timestamp, and PREVRANDAO := keccak256(parent_l2_block_hash ‖ bloch_anchor_block_hash), documented as WEAK randomness exactly as on every L2; no filesystem/network/syscalls in the guest beyond sp1_zkvm::io; HashMaps only with deterministic iteration or sorted (BTreeMap) in any state-affecting path; Cargo.lock committed, revm version pinned exactly, and the guest ELF hash / SP1 vkey pinned in the ChainSpec — any dependency bump is a documented program upgrade with a new vkey recorded in subsequent L2V0 anchors.

**Concrete choices.** revm (Rust, MIT, the engine inside Reth) pinned to one exact version and SpecId::CANCUN — chosen over geth/evmone (Go/C++ cannot compile into the SP1 RISC-V guest) and over SputnikVM (less maintained, weaker hardfork tracking); revm is the only production EVM that runs both natively and in-zkVM from one codebase, and it powers Reth mainnet nodes, so "unmodified revm at a named hardfork" IS mainline Ethereum semantics. Reth SDK (reth-node-builder + reth-rpc) for the node/RPC/mempool/txpool so the eth_* surface is Reth's, not hand-rolled. RSP (github.com/succinctlabs/rsp) as the direct template for in-SP1 block re-execution — this exact revm-in-SP1 pattern is proven there, and it leverages the SP1 toolchain Bloch already ships in crates/coherence-prover (FRI core proofs only, PQ rule preserved). alloy-primitives/alloy-consensus/alloy-trie for types, tx envelopes, and the keccak MPT. sp1-patches accelerated crates (keccak256, k256/secp256k1, and SHA-256) so ecrecover/keccak-heavy Uniswap traffic proves in tractable cycles. kzg-rs (pure-Rust) for the 0x0a point-evaluation precompile inside the guest, c-kzg natively. Hardfork pin CANCUN rather than Prague at genesis: RSP/tooling maturity and a smaller precompile audit surface; Prague (EIP-7702 etc.) is an explicit, height-gated upgrade path, not a fork of semantics. Chain IDs: distinct, registered in ethereum-lists/chains before any public testnet — proposed 700771 (testnet) / 700770 (a hypothetical future mainnet), placeholders pending registration. Block gas limit 30,000,000 (Ethereum-mainnet parity so any mainnet-deployable contract deploys) with a 2-second L2 block time; proofs batch N blocks per SP1 proof and one L2V0 anchor per batch (Bloch blocks are 30s, so ~1 anchor per 1–4 Bloch blocks). EIP-1559 parameters retuned only in the legal, non-semantic knobs (elasticity 2, denominator raised toward the OP-Stack range so the basefee is stable at 2s blocks) — these are chain-config values Ethereum itself varies per network, not EVM changes. The ONLY deltas from mainline Ethereum, enumerated exhaustively: (1) chainId; (2) gas-token provenance — native balance is bridged BLCH minted solely by deposit transactions, block reward zero, basefee to a vault instead of destroyed, COINBASE = fee vault; (3) precompile/tx availability — the full Cancun precompile set 0x01–0x0a is present and unmodified (ecrecover, sha256, ripemd160, identity, modexp, ecadd, ecmul, ecpairing, blake2f, kzg-point-eval), NO extra precompiles in v1 (a future PQ-signature-verify precompile would sit at a reserved address ≥0x0100 and is explicitly out of scope), and type-3 (EIP-4844 blob) transactions are rejected at the sequencer exactly as on OP-Stack L2s — BLOBHASH/blob-basefee opcodes still return spec-correct values for blobless blocks; plus the OP-style type-0x7E deposit envelope, which exists at the transaction-envelope layer, never inside EVM execution. Anything else differing from Ethereum Cancun is a bug by definition, and the acceptance test is executable: the full ethereum/tests + EEST state-test suites at Cancun must pass bit-for-bit, and Uniswap v2/v3 and OpenZeppelin ERC-20 deploy from unchanged mainnet artifacts with unchanged Foundry scripts — PosternDex is then literally the Uniswap contracts on this L2, satisfying POSTERNDEX-BRIDGE-DESIGN §4's E2 substrate with zero contract edits.

**Interfaces / formats.** ChainSpec (genesis.json, geth-compatible so Foundry/Hardhat consume it directly): { chainId: 700771, hardfork: "cancun" (all pre-Cancun forks active at genesis, terminalTotalDifficulty 0), gasLimit: 30_000_000, blockTimeSecs: 2, baseFee: {elasticity: 2, denominator: 250, initial: 1 gwei}, alloc: predeploys at reserved addresses 0x4200...0000-range (L2StandardBridge, L2ToL1MessagePasser, BaseFeeVault, SequencerFeeVault — Solidity contracts, themselves run by the unmodified EVM), sp1Vkey: bytes32, l2v0Magic: "L2V0" }. L2 block header: the standard Ethereum execution header (parentHash, stateRoot, transactionsRoot, receiptsRoot, logsBloom, number, gasLimit, gasUsed, timestamp, baseFeePerGas, prevRandao in mixHash, withdrawalsRoot=empty) PLUS an out-of-header sidecar {blochAnchorHash: [u8;32], blochAnchorHeight: u64} carried in the batch, so the header itself stays byte-compatible with Ethereum tooling. Deposit tx (type 0x7E): {sourceHash (derived from the L1 escrow txid+vout), from, to, mint: u256 (= L1 sats × 10^10), value, gasLimit, data} — executed first in the block, cannot be dropped by the sequencer once anchored. ExecutionWitness (host→SP1 guest, RSP-shaped): {preStateRoot: B256, blocks: Vec<SealedBlock>, ancestorHeaders: Vec<Header> (≤256, for BLOCKHASH), stateWitness: sparse MPT nodes for every account/storage slot touched, bytecodes: Vec<Bytes> keyed by codeHash} — guest rejects the proof if any witness node fails its keccak path to preStateRoot. Guest public values (committed, what the on-chain anchor binds): {chainId: u64, batchIndex: u64, prevStateRoot: B256, newStateRoot: B256, batchTxListHash: B256 (keccak of the DA blob), withdrawalRoot: B256 (root of the L2ToL1MessagePasser storage), blochAnchorHash: B256, blochAnchorHeight: u64}. L2V0 anchor envelope (one zero-value TxOutput script_pubkey on Bloch, TKV0-style, ≤ 200 bytes, ignored by all unmodified nodes): [magic "L2V0" | version u8=0 | rollupId [u8;32] = keccak(genesis header) | batchIndex u64 LE | prevStateRoot [u8;32] | newStateRoot [u8;32] | daCommitment [u8;32] | vkeyHash [u8;32]]. JSON-RPC surface (Reth's implementations, unmodified): eth_chainId, eth_blockNumber, eth_getBalance, eth_getStorageAt, eth_getTransactionCount, eth_getCode, eth_call, eth_estimateGas, eth_gasPrice, eth_maxPriorityFeePerGas, eth_feeHistory, eth_sendRawTransaction, eth_getTransactionByHash/Receipt, eth_getBlockByNumber/Hash, eth_getLogs, eth_getProof, eth_syncing, net_version, web3_clientVersion, plus eth_subscribe(newHeads|logs) over WebSocket — sufficient for MetaMask (add-network with chainId 700771 + RPC URL), Foundry (forge script --rpc-url), Hardhat, ethers/viem, with zero client patches. Extension namespace bloch_* (never eth_*): bloch_anchorStatus(l2Block) → {anchored: bool, blochTxid, blochHeight, blochConfirmations, proofVerified: bool} so wallets/frontends can display the honest finality state.

**Tradeoffs.** (1) MPT vs verkle/binary trees: MPT chosen — byte-compatible eth_getProof, alloy-trie/reth code exists, and RSP proves MPT witnesses in SP1 today; verkle rejected because Ethereum itself has not shipped it, so adopting it would be a semantic divergence in the one place (state commitment) the anchor depends on. Cost: larger witnesses → more SP1 cycles per block. (2) Cancun-at-genesis vs Prague: Cancun trades newest features (EIP-7702 account abstraction) for proven RSP/test-suite coverage; Prague is an upgrade, not a fork of the design. (3) Basefee-to-vault vs EIP-1559 burn: burning bridged BLCH would be semantically clean vs Ethereum but permanently strands L1 escrow and creates a Postern-operated BLCH supply-reduction mechanism — dangerously close to the burn line drawn in BLOCH-PERMISSIONLESS-TOKENS-L2; the vault matches OP-Stack precedent, keeps escrow solvent, and keeps the fee a disclosed utility revenue, at the cost of one enumerated (and industry-standard) delta. (4) 30M gas limit vs proving cost: full parity means any mainnet contract deploys, but a full 30M-gas block is expensive to prove in SP1 core (FRI) mode — mitigated by 2s blocks rarely being full on a testnet, batch-level proving, and the option to launch at 15M and raise; the PQ rule (no Groth16 wrap) makes proofs large and is non-negotiable here, so DA/bandwidth pays for post-quantum honesty. (5) Reth-SDK node vs minimal custom node: Reth brings a mainnet-grade txpool/RPC for free but is a heavy dependency to track; the alternative (thin sequencer + revm + hand-rolled RPC) is smaller but re-implements exactly the surface most likely to have compatibility bugs — Reth wins because compatibility IS the product. (6) OP-style deposit tx type vs pre-funded EOA drips: the 0x7E envelope adds one non-Ethereum tx type (visible in block explorers) but gives forced, sequencer-uncensorable deposits; pre-funding hides the delta but makes deposits censorable — forced inclusion wins. (7) Single dual-target crate vs separate native/guest crates: one crate risks accidental std leakage into the guest (CI must build riscv32im on every commit) but guarantees the native node and the proof re-execute IDENTICAL code — the whole validity argument rests on that identity, so single-crate wins with CI enforcement.

**Honest risks & limits.** FINALITY IS INHERITED AND TODAY IT IS WEAK: Bloch runs a k=4, low-hashrate, 51%-attackable, unaudited mainnet-beta. An L2 anchor is an ordinary Bloch transaction; if the Bloch block carrying it reorgs away, every L2 state that treated that anchor as settled is endangered — deposits can be minted against escrow txs that a reorg then erases (mint-and-unwind double-spend), and withdrawals finalized against a vanished anchor are unsafe. No finite confirmation depth defends against a majority attacker; CHECKPOINT_DEPTH=1000 in the node only rejects deep reorgs locally. Therefore: REAL VALUE IS GATED on Bloch mainnet security (k=8 ramp, real WAN hashrate, checkpoint finality, third-party audit) exactly as POSTERNDEX-BRIDGE-DESIGN §0 requires — until then this design exists for TESTNET, ZERO-VALUE operation only. TRUST MODEL, stated plainly: the Bloch base does NOT verify SP1 proofs (zero consensus change means zero on-chain verification); "validity rollup" here means anyone CAN verify — state-transition validity is trusted math only for users who run (or trust someone running) the open verifier against the anchored roots; everyone else trusts the sequencer's honesty for state and everyone trusts the sequencer for liveness, ordering, and censorship (single operator, an owned Postern product, per the two-layer rule). Data availability is a further trust: if the sequencer withholds batch data, users cannot reconstruct state or prove withdrawals even though anchors exist. The deposit/withdraw escrow on a covenant-less UTXO chain is CUSTODIAL (multisig/MPC held by the operator/consortium) until a covenant soft-fork exists — the bridged-BLCH gas token is, today, an IOU on that escrow; this is the bridge component's problem but it is the gas token's provenance, so it is this component's disclosure too. PQ tension: EVM compatibility hard-requires secp256k1 ECDSA accounts and keccak-256 — NOT post-quantum — inside an ecosystem whose base chain and prover posture are deliberately PQ-conservative; the L2 is honestly less PQ than its L1 and only the proof system (FRI, no Groth16) keeps the PQ rule. Nothing here is built or audited: revm, Reth, SP1, RSP, the bridge, the sequencer, and this spec itself are unaudited in this composition; bridges and L2s are the most-exploited constructs in the industry. SP1 core (FRI) proofs are large (MBs) and proving full blocks is slow/costly — proof latency delays anchor-backed finality. BLCH remains not-a-security: it is never sold, the L2 never issues new BLCH, no revenue buys or burns it; the L2 is a Postern product using BLCH as gas, and any of this reaching real users requires its own securities/legal review first.

**Open questions.** (1) Cancun vs Prague at genesis — resolve against RSP/ethereum-tests coverage at build time; if Prague, EIP-7702 interactions with the deposit tx type need a spec pass. (2) Final chain-ID values and ethereum-lists/chains registration (700771/700770 are placeholders; collision check required). (3) DA layer for batch data and FRI proofs: self-hosted mirrored object storage (simplest, weakest), Celestia-style external DA (adds a dependency and its own trust/finality), or calldata-in-Bloch-envelopes (1MB blocks and 30s cadence make full tx-data-on-L1 plausibly viable at testnet volumes — quantify throughput before choosing; this choice moves the trust model materially). (4) Batch/anchor cadence and reorg policy: how many Bloch confirmations before the sequencer treats its own anchor as settled, and the exact L2 rollback procedure when an anchored Bloch block reorgs (deterministic re-derivation from the surviving anchor chain must be specified and tested). (5) EIP-1559 denominator/elasticity tuning for 2s blocks (simulate; OP-Stack values as prior). (6) Forced-inclusion path for censored users (L1-initiated transactions via the L2V0 envelope — desirable, but it makes the ownerless base carry L2 inputs; spec the envelope and the derivation rule or explicitly defer). (7) Escrow mechanics pre-covenant (M-of-N disclosure, proof-of-reserves cadence) — owned-bridge component, but the gas token's mint rule depends on it. (8) Whether/when to add a PQ-signature-verify precompile at ≥0x0100 (explicitly additive, never replacing ecrecover) so PQ wallets can exist on the L2. (9) SP1 proving economics: cycles per Uniswap swap at Cancun with sp1-patches, target batch size, GPU cost per proof — needed to validate the 30M gas limit. (10) Exact revm/reth/SP1 version pins and the vkey-upgrade governance story (who signs a program upgrade, how verifiers learn the new vkey — today: the operator, disclosed; is that acceptable even for a testnet?).

## 2. Settlement & Anchoring to the Ownerless Bloch Base ("L2V0" anchor layer) — the subsystem of the Postern EVM L2 that (1) serializes L2 epoch commitments into ordinary zero-value Bloch TxOutput envelopes that every unmodified node already accepts, (2) defines the deterministic rule by which any reader derives the canonical L2 anchor chain from Bloch via the existing JSON-RPC replay/reorg discipline, and (3) specifies the confirmation-depth and reorg-response policy that makes the L2's inheritance of Bloch's (currently weak, k=4) finality explicit and machine-handled rather than implicit and hoped-away.

**Architecture.** SHAPE: a sovereign zk-validity rollup anchored to Bloch, in the precise sense that Bloch provides ORDERING, DATA ANCHORING, and REORG-RESISTANCE for the L2's commitment chain — but NOT proof verification (Bloch is a pure-PoW UTXO chain with no VM; it cannot check an SP1 proof in consensus). Validity is therefore verified client-side by anyone who replays the anchor chain and checks the FRI proofs against the published verifying key — the Sovereign-SDK/Rollkit model, not the Ethereum-rollup model. This must be stated everywhere: 'zk-validity' here means anyone-can-verify, not chain-enforces.

DATAFLOW, per epoch E (an epoch = a fixed run of L2 blocks, e.g. all blocks sealed in a ~60 s window):
1. The sequencer (owned Postern product; one operator among any number of possible competing rollups) executes L2 blocks in revm, seals epoch E, computes: post-state root, the canonical batch encoding (compressed tx list), and the epoch withdrawal root.
2. DA: the compressed batch is chunked and written to Bloch itself as L2V0 DATA envelopes (op 0x03) in one or more ordinary transactions — Bloch-native DA, so the entire L2 is reconstructible from Bloch's RPC alone and DA inherits exactly one chain's finality instead of adding a second trust domain (Celestia would). The batch hash commits to the concatenated chunks.
3. The SP1 prover (the existing crates/coherence-prover pattern: guest ELF + GPU host service on Fly L40S) proves 'executing batch B from pre-root R_{E-1} yields post-root R_E and withdrawal root W_E', core STARK/FRI mode only (repo rule: no Groth16/Plonk wrap — PQ posture). The proof blob (hundreds of KB–MB, too big for an envelope) is published in the DA stream too (op 0x03, kind=proof) or fetched from the operator; either way the COMMIT envelope pins it by hash.
4. The sequencer posts ONE COMMIT envelope (op 0x02) — a zero-value output in an ordinary Bloch transaction, fee-paying like any other tx — carrying {rollup_id, epoch, parent commit txid, state root, batch/DA hash, withdrawal root, proof hash}. Every unmodified node accepts it today, exactly as TKV0 envelopes are accepted: node validation constrains only the script_pubkey of SPENT outputs, never of created ones. Zero base consensus change; the base gains no operator, no bridge contract, no admin key.
5. ANY reader derives the L2 anchor chain with the identical algorithm bloch-tokens already implements: getblockcount → getblockhash(h) → getblockbyheight(h, verbose) from genesis, scanning outputs by index, first-envelope-wins per tx, malformed ⇒ no-op; keep a height→blockhash journal; on hash mismatch rewind to the fork point and replay. Two independent readers of the same selected chain reach byte-identical anchor state.

CANONICAL-ANCHOR RULE (the L2's fork choice, fully deterministic): the canonical commit for epoch E is the FIRST well-formed COMMIT in Bloch canonical order (block height, then tx order, then output index) whose (a) rollup_id matches, (b) epoch = previous canonical epoch + 1, (c) parent_commit_txid equals the txid carrying the canonical commit for E-1, and (d) carrying transaction's input 0 spends an outpoint whose script_pubkey equals the sequencer key hash registered in the rollup's GENESIS envelope (op 0x01) — checkable off-consensus because the node already enforces spender key = SHA3-256(pubkey)[..20] on spends. Everything else is a token-layer-style no-op. Competitors anchor their own L2s under their own rollup_id (= txid of their GENESIS tx, registry-free) with identical rights.

REORG-RESPONSE STATE MACHINE (sequencer-side AnchorManager, and mirrored in every verifier): each anchored commit carries a status Pending → Anchored{depth} → Final-for-policy (depth ≥ K) — or Orphaned when the journal detects a Bloch reorg past its inclusion height. Deterministic responses: (R1) an orphaned COMMIT is re-posted byte-identical on the new canonical branch, in epoch order, before any new epoch is committed — the L2 ledger itself never rewinds (single sequencer; L2 blocks are not derived from L1 ordering), only its anchoring does; (R2) orphaned DATA envelopes are re-posted likewise (the batch hash is unchanged); (R3) any withdrawal whose authorizing commit's inclusion height is above the observed fork point is immediately frozen (state Frozen) until its commit is re-anchored and re-ages to K_w; (R4) if a reorg is deeper than K (majority-attack territory), the bridge enters HALT: no L1 releases, no new deposit mints, epochs continue but are flagged tainted-anchor until a manually reviewed re-anchor — and this halt condition is part of the spec, not an ops improvisation; (R5) deposits (L1→L2) are only minted on the L2 after the deposit tx has K_d confirmations, so a deposit reorged out below K_d was never minted; a deposit reorged out at ≥ K_d is an unbacked mint — detectable, but only remediable by halt + reconciliation, which is exactly why real value is gated.

TRUST MODEL, stated flat: validity of L2 state — trust the math (SP1 FRI) IF you verify proofs, else trust the operator; liveness/ordering/censorship — trust the sequencer (it is a product with an operator); withdrawal EXECUTION on L1 — trust the operator/federation, because pre-covenant Bloch has no way to force a UTXO to honor a proof (the E1 covenant soft-fork is the future trust-minimized path); finality — you inherit Bloch's, which today is a k=4, low-hashrate, 51%-attackable, unaudited beta.

**Concrete choices.** EVM: revm (the Rust EVM used by Reth and Foundry) as the execution engine, with alloy primitive types — chosen because it is the only production-grade EVM that also runs inside the SP1 zkVM today (the rsp / 'Reth Succinct Processor' pattern), giving one execution definition for both the sequencer and the prover guest; Solidity/Uniswap v2-v3 bytecode deploys unchanged (keccak256, secp256k1 ecrecover, ordinary chain-id — PosternDex is literally the Uniswap contracts). geth was considered and rejected: Go cannot be the SP1 guest, so it would force two EVM implementations and an equivalence problem.

Prover: SP1 (Succinct), core STARK/FRI proofs only — chosen over RISC0/Jolt because the repo already ships an SP1 scaffold (crates/coherence-prover: guest/script/service layout, Fly.io L40S GPU deploy, artifact cache) and already encodes the project rule that the Groth16/Plonk curve-SNARK wrappers are forbidden for post-quantum coherence; the L2 inherits that rule, accepting large FRI proof blobs as the price. Guest program = 'STF prover': deserialize (pre_root, batch, MPT witnesses), run revm over the batch, commit (rollup_id, epoch, pre_root, post_root, batch_hash, withdrawal_root) as public values.

State commitment: keccak256 Merkle-Patricia trie roots (standard Ethereum layout) so existing tooling (eth_getProof consumers, block explorers, MetaMask) works unmodified; a Poseidon/binary-trie optimization is a later proving-cost optimization, not v0.

DA: Bloch-native — batch chunks as L2V0 DATA envelopes — chosen over Celestia blobs (adds a second consensus, a second finality clock, and a light-client dependency the ownerless story doesn't need) and over an operator DAC (weakest: withheld data makes proofs unverifiable and exits impossible). Honest cost: Bloch block space and unknown script-size/relay limits bound throughput (open question #1); v0 targets low TPS deliberately.

Envelope standard: 'L2V0' magic, byte-for-byte in the TKV0 idiom (little-endian, strict decode, first-envelope-wins, malformed ⇒ layer no-op, value MUST be 0 per TKV0 caveat E.1 — the node's address indexer misreads long script_pubkeys as addresses, so no BLCH ever rides an envelope). Reference reader to be built as a sibling crate (bloch-l2-anchor) reusing bloch-tokens' BlockSource / Indexer journal+snapshot machinery, which is already reorg-correct and equality-tested against genesis replay.

Sequencer authentication: input-0 key binding to the GENESIS-registered sequencer key hash (verifiable off-consensus from data the node already enforces), with a ROTATE op (0x04) for key rotation — chosen over 'first commit wins, unauthenticated' (griefing: anyone posts garbage commits and forces verifiers to fetch/reject) and over requiring indexers to verify FRI proofs inline for canonicality (proof blobs are large; fetching them must not be a liveness requirement for merely READING the anchor chain).

**Interfaces / formats.** 1. L2V0 ENVELOPE WIRE FORMAT (script_pubkey of a zero-value TxOutput; all ints little-endian; strict decode; exact-length; any violation ⇒ layer no-op, the Bloch tx itself stays valid). Common header: offset 0, 4 bytes, magic ASCII 'L2V0' (4C 32 56 30); offset 4, u8 version = 0x00; offset 5, u8 op.
- op 0x01 GENESIS (registers a rollup; rollup_id := txid of this tx): u64 evm_chain_id; [32] genesis_state_root; [32] sp1_vkey_hash (hash of the SP1 verifying key for the STF program — vkey published in the repo/DA); [20] sequencer_key_hash (SHA3-256(pubkey)[..20], the node's own address form); u8 da_scheme (0x00 = Bloch-native chunks); u8 name_len (0..=32) + name UTF-8. Exact length 18+95+name_len... (normative table pinned by golden-vector tests exactly as bloch-tokens/tests/vectors.rs pins TKV0).
- op 0x02 COMMIT: [32] rollup_id; u64 epoch (strictly = parent epoch + 1); [32] parent_commit_txid (txid carrying canonical commit for epoch-1; all-zero only for epoch 0); [32] l2_state_root (post-state MPT root); u64 first_l2_block; u64 last_l2_block; [32] batch_da_hash (SHA3-256 of concatenated DATA chunk payloads); [32] withdrawal_root (Merkle root of this epoch's withdrawal events); [32] proof_hash (SHA3-256 of the raw SP1 core-FRI proof blob). Fixed length 214 bytes.
- op 0x03 DATA: [32] rollup_id; u64 epoch; u8 kind (0x00 batch, 0x01 proof); u16 chunk_index; u16 chunk_count; var payload (bounded by node script/tx limits — open question). **Tradeoffs.** (1) Sovereign (client-verified) vs L1-enforced rollup: chose sovereign because Bloch has no VM and the alternative — the E1 covenant soft-fork — is a real consensus change the ownerless base's node operators would have to adopt; cost: the base cannot reject an invalid state root, so 'validity' protects only those who verify, and withdrawal enforcement stays with the operator until covenants exist. (2) Bloch-native DA vs Celestia vs DAC: native DA keeps one finality clock and full reconstructibility from one RPC, at the cost of throughput bounded by a small, low-fee-pressure base chain; Celestia would buy throughput at the cost of a second consensus dependency and a weaker 'anchored to Bloch alone' story; DAC rejected as dishonest-by-construction for a system whose selling point is verifiability. (3) SP1 core-FRI vs Groth16-wrapped: FRI keeps the repo's PQ rule and avoids a trusted curve, at the cost of MB-scale proof blobs (hence proof-by-hash in the COMMIT and proofs in the DA stream) and no cheap on-chain verification anywhere. (4) Single sequencer vs decentralized/proof-based canonicality: single registered key is honest about being an owned product, gives deterministic canonicality without requiring readers to fetch proofs, and permits competitors their own rollup_ids; cost: censorship and liveness depend on one operator (mitigation: key rotation op now, forced-inclusion-via-L1-envelopes is a designed-but-deferred extension). (6) keccak MPT state vs zk-friendly trie: tooling compatibility now, proving cost later. (7) Epoch cadence: frequent commits shrink the un-anchored window but spend base block space and prover money; v0 picks ~60 s epochs with proof lag allowed (commit may precede its proof's DATA publication by a bounded number of epochs, each such epoch marked 'unproven' by verifiers until the blob lands).

Stated per POSTERNDEX §3 discipline: this is a product with an operator. (4) UNBACKED-MINT SCENARIO: a deposit confirmed ≥ K_d then reorged out by a majority attacker leaves minted-against-nothing L2 balances; the specified response (HALT + reconciliation) limits blast radius but cannot make anyone whole. ## 3. Proving System — zk-Validity Rollup on SP1 (recommended). The component that makes the L2's state transitions *provably correct*: an SP1 (Plonky3 hash-STARK/FRI) guest program re-executes each sequenced batch with revm (component 1) over the prior state root plus the DA-committed transactions, and emits a post-quantum FRI proof of the transition. The proof commitment rides the anchor envelope on Bloch (component 2) as an ordinary transaction; full proof bytes live with the batch data on the DA layer. Anyone can verify any batch with an open-source verifier against the anchored commitment — 'trust math, not the operator' for state correctness. This is an OWNED Postern product anchoring to the ownerless base; the base gains no operator, no consensus change, and does NOT verify proofs. DESIGN ONLY — nothing built, audited, or value-bearing.

**Architecture.** **Recommendation: zk-VALIDITY rollup, not optimistic/fraud-proof.** Rationale (decisive on this base): fraud proofs require a challenge game adjudicated ON the settlement layer plus watchtowers with the standing to win it. Bloch is a pure-PoW UTXO BlockDAG with no smart contracts — it cannot host a bisection game or slash a sequencer bond without a covenant soft-fork (the E1 path POSTERNDEX-BRIDGE-DESIGN.md defers). An optimistic L2 on Bloch would degrade to 'trust the operator plus a committee', the exact thing the project refuses. Validity proofs invert the burden: the operator must prove correctness before anyone accepts a batch, and verification needs nothing from the base — any off-chain verifier checks the FRI proof against the anchored commitment. This also reuses what Bloch already ships: the SP1 prover scaffold in `crates/coherence-prover` (program/script/service layout), its Fly.io GPU prover service (`/prove`, `/verify`, bearer-auth, `deploy/sp1-prover/` L40S config), and the established post-quantum rule (raw FRI only; Groth16/Plonk curve wrappers forbidden per COHERENCE-C1.md §3).

**Pipeline (per batch):**
1. **Sequencer** (component 3) orders L2 txs into batch `i`, publishes the canonical tx list + any Bloch-deposit events to the DA layer (component 2's data path), computing `batch_tx_commitment = SHAKE-256(canonical tx list)`.
2. **Witness generator** (host-side, `l2-prover/host`): executes batch `i` natively with revm against the sequencer's state DB, recording every touched trie node, account, storage slot, contract bytecode, and ancestor block hash into a self-contained `ExecutionWitness` (the RSP / 'Reth Succinct Processor' pattern — stateless re-execution). Native execution also cross-checks the expected `new_state_root` before burning GPU time.
3. **SP1 guest** (`l2-stf-program`, the analog of `coherence-prover/program`): (a) verifies the `ExecutionWitness` opens against `prev_state_root` (keccak-256 MPT proofs); (b) applies Bloch deposit mints (from component 4's bridge, referenced by `l1_origin` + `deposit_root`); (c) executes every tx through revm with the pinned L2 chain config; (d) accumulates the L2→L1 `withdrawal_root`; (e) computes `new_state_root`; (f) `sp1_zkvm::io::commit` of `BatchPublicValues`. Any divergence makes the proof unsatisfiable — an invalid batch simply cannot be proven.
4. **GPU prover service** (extends `coherence-prover/service`): async `/prove-batch` job API on the existing L40S scale-to-zero deployment; produces the FRI proof (see Choices for core vs compressed mode).
5. **Anchor publisher**: writes an `L2V0` envelope (TKV0-style zero-value `script_pubkey`, component 2's format) into an ordinary Bloch transaction carrying `batch_index`, `new_state_root`, `batch_tx_commitment`, `proof_hash = SHAKE-256(proof bytes)`, and a DA pointer. Full proof bytes (too large for Bloch tx-size norms — FRI proofs are hundreds of KB to MBs, vs TKV0's ≤231-byte envelopes) are published on the DA layer next to the batch and on open mirrors.
6. **Independent verifiers** (`l2-verifier`, open-source, anyone runs one — the TKV0 indexer model): follow Bloch via the node JSON-RPC (`getblockcount`/`getblockhash`/`getblockbyheight`), extract `L2V0` anchors, fetch batch+proof from DA, check `SHAKE-256(proof) == proof_hash`, verify the FRI proof against the pinned guest verifying key, and check the batch chain (`prev_state_root`/`prev_batch_hash` linkage from the last verified anchor). A verifier that sees a bad or missing proof flags the operator publicly; it cannot roll the base back.

**Finality ladder (user-facing, must be shown in-product):** (a) *soft-confirmed* — sequencer receipt, trust the operator; (b) *proven* — FRI proof published and independently verifiable, trust math for validity; (c) *anchored* — commitment in a Bloch block at depth K (TKV0's K=24 guidance, scaled with value); on today's k=4 chain NO depth is finality. Real-value operation is gated on Bloch mainnet security (k=8 ramp, WAN hashrate, checkpoint finality, third-party audit) exactly per POSTERNDEX-BRIDGE-DESIGN.md §0.

**Concrete choices.** **SP1 (Succinct, Plonky3 STARK/FRI over BabyBear), pinned SDK version** — over RISC0 or a bespoke circuit. Why: already in-repo (`crates/coherence-prover` scaffold + GPU service + deploy config); the only PQ, multi-audited (Veridise/Cantina/Zellic/KALOS), permissively-licensed general-purpose zkVM per COHERENCE-C1.md §3; and revm-inside-SP1 is proven prior art (Succinct's RSP proves real Ethereum mainnet blocks; OP Succinct productizes it). RISC0 is a credible fallback (also RISC-V, also STARK-based) but doubles toolchain surface for no gain.

**revm as the proven EVM** — over geth/evmone. Why: Rust, `no_std`-capable, the de-facto zkVM guest EVM (RSP, OP Succinct, zeth all use it), and it IS component 1's engine — the guest re-executes the exact same code the sequencer ran, one semantics, no dual-implementation drift. geth would push us toward a Cannon/MIPS fraud-proof design — the optimistic road rejected above.

**Proof mode — default `.core()` (raw FRI) per the existing COHERENCE rule; propose `.compressed()` (SP1's STARK-to-STARK recursion) as the practical target.** Core proofs grow with execution (one shard proof per ~2^21–2^22 cycles; an EVM batch is easily 100M–1B cycles → tens of shards → tens of MB). Compressed mode recursively folds shards into one constant-size (~MB-scale) STARK — still FRI, still hash-based, NO elliptic curves anywhere, so it appears compliant with the letter and spirit of 'no Shor-breakable wrapper'; but because COHERENCE-C1 §3 and the crate README literally say `.core()`, adopting `.compressed()` requires an explicit one-line amendment to that rule (open question below). **`.groth16()`/`.plonk()` remain absolutely forbidden.**

**SP1 patched precompiles for keccak256 and secp256k1** (`sp1-patches` crates: keccak for trie/EVM hashing, k256 for ECDSA tx recovery) — these are guest-side accelerations of hash/signature *checking inside the proof*, not proof-system curves; without them EVM proving cycle counts are prohibitive.

**State commitment: keccak-256 Merkle-Patricia Trie via `alloy-trie`/`alloy-primitives`** — bit-compatible with Ethereum so `eth_getProof`, wallets, indexers, and audited tooling work unchanged. (Keccak is hash-based — Grover-only degradation, PQ-acceptable; the PQ-critical path is the proof system, which stays FRI.)

**Witness format: RSP-style `ExecutionWitness`** (touched MPT nodes + bytecodes + ancestor hashes) rather than a full-state guest — keeps guest memory bounded and proving cost proportional to batch activity, not state size.

**Prover infra: extend the existing `coherence-prover/service` + `deploy/sp1-prover` Fly.io GPU pattern** (L40S, scale-to-zero, artifact-cache volume) with an async job API, since batch proofs take minutes, not the sub-request latency of the shielded-spend `/prove`.

**Reproducible guest builds**: guest ELF built in a pinned Docker toolchain (`cargo prove build --docker`), verifying key derived deterministically and published in-repo, so any verifier recomputes the vkey from source — no trusted vkey distribution.

**Interfaces / formats.** **1. Guest public values (ABI-stable, SHAKE-256-domain-separated, committed via `sp1_zkvm::io::commit`):**
```rust
struct BatchPublicValues {
  l2_chain_id: u64,            // fixed, e.g. a registered EIP-155 id for the testnet
  batch_index: u64,            // strictly increasing
  prev_batch_hash: [u8;32],    // SHAKE-256 of previous BatchPublicValues (chain link)
  prev_state_root: [u8;32],    // keccak-256 MPT root before the batch
  new_state_root: [u8;32],     // ... after the batch
  batch_tx_commitment: [u8;32],// SHAKE-256 of canonical RLP tx list == DA blob commitment
  deposit_root: [u8;32],       // SHAKE-256 merkle root of Bloch deposits applied
  l1_origin_hash: [u8;32],     // Bloch block hash the deposits were read from
  l1_origin_height: u64,       //   (verifiers check it is ≥K deep and on the selected chain)
  withdrawal_root: [u8;32],    // SMT root of L2→L1 withdrawal messages (consumed by component 4)
  timestamp: u64,
}
```
**2. Private guest input:** `BatchWitness { txs: Vec<Bytes> /* RLP EVM txs */, state_witness: ExecutionWitness /* MPT nodes, bytecodes, ancestor hashes */, deposits: Vec<DepositEvent> }`. Guest algorithm (normative): verify witness against `prev_state_root` → apply deposits → execute txs via revm (pinned hardfork config: Shanghai-equivalent; no EIP-4844 blob txs in v0) → fold withdrawals → compute `new_state_root` → commit publics. Unprovable ⇒ batch invalid by construction.

**3. On-Bloch anchor envelope `L2V0`** (component 2's wire format; this component defines the proving fields; zero-value output, TKV0 conventions, little-endian):
```
magic "L2V0"(4) | version u8=0 | op u8=0x01 COMMIT | l2_chain_id u64 |
batch_index u64 | new_state_root 32 | batch_tx_commitment 32 |
proof_hash 32 (SHAKE-256 of full FRI proof bytes) | vkey_hash 32 |
da_pointer_len u8 | da_pointer var (≤64B URI/CID into the DA layer)
```
≈ 190 bytes fixed + pointer — comfortably within TKV0-scale envelope norms. Full FRI proof bytes NEVER go on Bloch; they are published on the DA layer adjacent to the batch blob and on open mirrors, content-addressed by `proof_hash`.

**4. Prover service API** (extends `coherence-prover/service`; bearer-auth; sequencer-internal):
- `POST /prove-batch {batch_index, public: BatchPublicValues, witness_b64}` → `202 {job_id}`
- `GET /jobs/{job_id}` → `{status: queued|proving|done|failed, proof_b64?, cycles?, wall_ms?}`
- `POST /verify {proof_b64, public_values_b64}` → `{valid}` (tooling/tests; real verification is the open verifier)
- `GET /health`, `GET /vkey` → `{vkey_hash, sp1_version, guest_git_rev, elf_shake256}`

**5. `l2-verifier` (open-source binary, the trust anchor):** inputs = a Bloch node RPC URL + DA endpoint(s) + pinned `{vkey_hash → activation batch_index}` set from the repo. Loop: scan `L2V0` anchors on the selected chain → fetch proof+batch by `proof_hash`/`batch_tx_commitment` → SP1 FRI-verify against vkey → check public-values chain linkage and `l1_origin` depth → emit signed attestation log / alert on any gap, mismatch, or missing data. Exit codes and a machine-readable report so third parties can run it in CI. **Vkey upgrades:** new guest ⇒ new vkey_hash, announced via an `op=0x02 UPGRADE` envelope N batches in advance; verifiers pin the schedule from source, not from the operator.

**Tradeoffs.** **Validity vs optimistic:** validity costs continuous GPU proving (est. order-of-minutes and ~$0.01–$1 per batch on an L40S depending on gas used — MUST be benchmarked, not asserted) and adds proving latency before 'proven' status; optimistic is near-free to operate but is simply unenforceable on a no-contract base — its 7-day-window trust model would collapse to 'trust Postern'. We pay compute to keep the trust claim honest. **Core vs compressed FRI:** core is the letter of the existing PQ rule but proof size scales with cycles (tens of MB per EVM batch — heavy for DA and verifiers); compressed is constant-size, all-STARK, but needs a rule amendment and adds recursion (more prover time, more unaudited surface). **Proof-hash-on-chain vs proof-on-chain:** anchoring only `proof_hash` + DA pointer keeps Bloch txs ordinary-sized but makes verifiability contingent on proof AVAILABILITY — a withheld proof is detectable (verifiers alarm) but not preventable; mitigated by content-addressing, multiple mirrors, and treating a missing proof as an operator failure that halts 'proven' status. **keccak-MPT vs SHAKE-SMT state:** keccak-MPT buys full Ethereum tooling compatibility (the point of the L2) at the cost of hash heterogeneity with the SHAKE-256 base; a SHAKE-SMT would be prover-cheaper and aesthetically coherent but breaks `eth_getProof` and every wallet/indexer assumption. EVM-compat wins. **Single operated prover vs permissionless provers:** v0 is one Postern-run GPU service (liveness = trust the operator); because proving is deterministic from public data (batch + witness derivable from DA + state), anyone CAN prove — a permissionless prover market is a later decentralization step, not a v0 promise. **Batch cadence:** small frequent batches = lower proving latency, more Bloch anchor txs and fees; large batches = cheaper amortized proving, longer time-to-proven. Tunable; recursion (aggregate N batch proofs into one anchor) is the eventual answer.

**Honest risks & limits.** **(1) Verification is NOT base-consensus-enforced — say it everywhere.** Bloch nodes neither see nor verify these proofs; miners will happily mine an anchor for a batch whose proof is invalid or absent. The guarantee is exactly TKV0's: *reproducible public verifiability* — anyone running the open verifier will detect an invalid/missing proof and equal replays yield equal verdicts. Detection is not prevention: the base cannot slash, revert, or force the operator. The recourse is social/exit (stop using the L2, fork the operator out), plus value-gating. **(2) The L2 inherits Bloch's (absent) finality.** Bloch today is k=4, low-hashrate, trivially forgeable, 51%-attackable, unaudited. A base reorg orphans anchor transactions: batch validity is unharmed (proofs are self-contained), but anchor ORDERING and deposit provenance are — a reorg can invalidate `l1_origin` deposits already minted on the L2 (double-spend into the L2, the same attack POSTERNDEX-BRIDGE-DESIGN.md §0.1 names). Mitigations (deposits only credited at depth ≥K; re-anchoring policy after reorgs; withdrawals delayed past K) reduce, never eliminate, this on a 51%-attackable chain. **Hard gate: zero real value until Bloch mainnet-candidate security clears (k=8 ramp, WAN hashrate, checkpoint finality, audits).** **(3) Proofs cover validity ONLY — not availability, not ordering, not liveness.** The sequencer can censor, reorder within a batch (MEV), withhold batches/proofs, or halt; users' funds can be correct-and-stuck. Forced-inclusion/escape-hatch design belongs to components 3/4 and is intrinsically weaker here than on Ethereum because the base can't enforce it. **(4) Unaudited integration.** SP1 itself is multi-audited, but OUR guest, witness generator, trie code, envelope parsing, and verifier are not — a witness-generation or state-root bug is a SOUNDNESS hole (proving a wrong state as valid). zkVM toolchains have had real soundness bugs; pin versions, track upstream advisories, mandatory third-party audit before any value. **(5) Proving latency/cost budgets are UNMEASURED.** All figures above are estimates from RSP-class prior art; publish real L40S benchmarks (cycles/gas, wall-time, $/batch) before claiming anything. **(6) EVM-compat imports secp256k1 ECDSA accounts** — Shor-vulnerable, unlike the PQ base. Inherent to 'MetaMask/Uniswap unchanged'; disclosed, contained to the L2, with a PQ-signature account-abstraction path as future work. **(7) Owned product, single operator.** The sequencer+prover is Postern's; the base stays ownerless and gains nothing. No overclaim: this design makes state fraud *publicly provable and detectable*, not impossible.

## 4. Sequencer & Data Availability — the Disclosed Operator (L2-EVM on Bloch-SIS-PoW). Layer placement per POSTERNDEX-BRIDGE-DESIGN.md §1/§7: this is the ONE component with an operator, therefore it is an OWNED Postern product, never part of the ownerless commons. The Bloch base gains no operator, no privileged key, no consensus change — the sequencer writes ordinary zero-value envelope transactions exactly like TKV0 does. Every UI surface (RPC banner, explorer, PosternDex tab, wallet) carries the fixed label: "L2 operated by Postern Labs — single sequencer, trusted for liveness/ordering/DA; state validity publicly provable; testnet, zero value, unaudited."

**Architecture.** FIVE PROCESSES, ONE OPERATOR, ONE NEUTRAL ANCHOR TRAIL.

(1) SEQUENCER (owned): accepts EVM txs over standard eth_* JSON-RPC; executes them in revm against the L2 state (chain_id fixed at genesis); emits an L2 block every 2 s ("soft block", signed by the sequencer key — a pre-confirmation, explicitly NOT finality). Ordering: strict FIFO by sequencer-receipt time within two lanes — a priority lane (effective tip ≥ priority threshold, EIP-1559 semantics so wallets/Uniswap work unchanged) drained before the standard lane; within a lane, arrival order. No bundles, no private orderflow, no auctions in v1. The sequencer returns a signed inclusion receipt {tx_hash, seq_no, soft_block, timestamp, sig} for every accepted tx, making its FIFO promise after-the-fact auditable against published batches (detection, not prevention).

(2) BATCHER (owned): every 300 s OR when pending soft blocks reach 256 KiB compressed (zstd -19, dictionary trained on EVM calldata), whichever first, it seals a BATCH: canonical ssz/RLP list of the raw signed txs + forced-inclusion txs (see below), computes batch_data_hash = SHA3-256(compressed bytes), post-state root, and posts an L2V0 BATCH envelope to Bloch as an ordinary transaction (zero-value output, fee-paying BLCH input from the operator wallet). The anchor trail on Bloch is append-only and replayable by anyone via the same getblockcount/getblockhash/getblockbyheight RPC discipline as TKV0 §D.

(3) DA LAYER (the decision, dual-mode, per-batch flag): MODE A "DA-on-Bloch" — the compressed batch itself is posted in L2V0 DA_CHUNK envelope outputs. Reality check from the node source: script_pubkey is free-form and MAX_TX_SIZE is 400 KiB, so chunks are NOT tiny — but the hard ceiling is MAX_BLOCK_SIZE 1 MB per 30 s block ≈ 33 KiB/s for the ENTIRE chain, shared with all users' transactions, paid in BLCH fees, and amplified by every archival node forever. Mode A is true L1 DA (reconstructible from Bloch alone) but caps the L2 at roughly 100–200 tx/s absolute best case while monopolizing the base chain — antisocial and expensive at any real load. MODE B "Postern DA mirror" — compressed batches served from operator-run R2/S3 at GET /da/v0/batch/{batch_data_hash}, plus IPFS pin (CIDv1 of the identical bytes) plus a BitTorrent v2 infohash published in the BATCH envelope; only the 32-byte batch_data_hash is anchored on Bloch. **v1 DEFAULT IS MODE B, AND MODE-B DA IS A TRUSTED SERVICE: IF POSTERN WITHHOLDS OR LOSES BATCH DATA, NOBODY CAN RECOMPUTE L2 STATE OR EXIT, EVEN THOUGH THE HASH ON BLOCH PROVES WHAT THE DATA *WAS*. THE OPERATOR CANNOT SUBSTITUTE DIFFERENT DATA (hash-bound) BUT CAN MAKE DATA UNAVAILABLE. THIS SENTENCE APPEARS, BOLD, IN EVERY DOC AND UI.** Governance rule baked into the node software of the L2: full nodes refuse to follow a batch whose data they cannot fetch — withholding halts honest verifiers rather than blinding them. Mode A remains mandatory for two things regardless: FORCE_TX (user censorship escape) and the GENESIS/CONFIG envelope.

(4) PROVER (owned infrastructure, verifiable by anyone): SP1 zkVM proving of batch execution, directly extending the repo's existing coherence-prover pattern (guest = stateless EVM block execution via revm/reth — the rsp "Reth Succinct Processor" architecture; host + GPU HTTP service exactly like deploy/sp1-prover, Fly.io L40S, scale-to-zero). Public statement per proof: "starting from state_root_{n-1}, executing the tx list whose SHA3-256 is batch_data_hash yields state_root_n and withdrawal_root_n". PQ rule inherited from coherence-prover: core STARK/FRI proofs only, NEVER .groth16()/.plonk() (curve SNARKs are Shor-breakable and forbidden in this repo). FRI proofs are megabytes, so the proof itself lives on the DA mirror; the PROOF_COMMIT envelope anchors {proof_hash, vkey_hash}. The guest ELF + vkey are published and reproducibly built, so ANY third party runs `sp1 verify` against anchored roots. **CRITICAL HONESTY: Bloch consensus does not and will not verify these proofs (zero-consensus-change is a hard constraint). This is therefore a SOVEREIGN ANCHORED ROLLUP with publicly-verifiable validity proofs — fraud is cryptographically DETECTABLE and ATTRIBUTABLE by anyone, but not L1-IMPOSSIBLE. The L1 never rejects a lying state root; verifiers and the bridge signers do.**

(5) FORCED INCLUSION + ESCAPE HATCH (the two mitigations): FORCED INCLUSION — any user pays normal BLCH fees to post an L2V0 FORCE_TX envelope on Bloch containing their raw signed EVM tx. Rule: a FORCE_TX confirmed at Bloch height h with depth ≥ K=24 (the TKV0 confirmation discipline) MUST be executed in some batch whose BATCH envelope confirms by height h+W, W=240 Bloch blocks (~2 h). Compliance is a pure function of the anchor chain — anyone replaying Bloch verifies it; a violation is a publicly provable censorship event that the L2 client software surfaces as a red-banner "SEQUENCER CENSORING" state. v1 consequence is detection + reputation + exit-trigger, nothing more — no slashing exists and the design says so. Invalid forced txs (bad nonce/insufficient gas) are included-and-reverted so the deadline can always be met. ESCAPE HATCH — the BLCH deposit vault on Bloch L1 is a disclosed Postern M-of-N multisig (addresses published; Bloch has no covenants, so this CANNOT be trust-minimized in v1 — the signers are trusted to follow the published exit procedure). Procedure: if no new BATCH envelope confirms for 48 h ("sequencer vanished") or a proven censorship event stands unremedied for 72 h, the vault enters EXIT MODE anchored by a signer-posted envelope: users submit Merkle proofs of their account/ERC-20 balance against the LAST PROVEN state root, and signers pay out after a 7-day challenge window during which anyone can publish a verification contradiction. **The hatch depends on DA (you need the state to build your Merkle proof — Mode-B withholding can break it; the mirror is therefore also snapshot-published per proven root) and on the signers' honesty. Both dependencies stated in bold, everywhere.** ROADMAP, NEVER A PROMISE: v2 candidates are a rotating disclosed sequencer set with L1-anchored leader schedule, then shared sequencing (Espresso-style) — listed as research directions; no date, no commitment, and the roadmap section is titled "Things that do not exist".

**Concrete choices.** CONCRETE NAMED TECH AND WHY: (a) revm (via reth's execution stack) as the EVM — real production EVM in Rust, byte-for-byte mainnet semantics, so Uniswap v2/ERC-20 bytecode deploys unchanged; it is also the only EVM with a proven SP1-guest path (Succinct's rsp proves real reth blocks), which makes the prover choice and the execution choice the same codebase — one semantics, no re-implementation gap. (b) SP1 for validity proofs — not chosen abstractly: crates/coherence-prover in this repo is already an SP1 guest+host+GPU-service scaffold with a deploy config; the team's PQ rule (raw FRI, no Groth16 wrapper) carries over verbatim, and RISC0 is the fallback if SP1 licensing/perf disappoints (both run RISC-V guests; the guest is portable). (c) Envelope anchoring copied from TKV0 — the "L2V0" magic family reuses the exact zero-consensus-change trick proven by crates/bloch-tokens: zero-value outputs, strict first-wins decoding, malformed⇒no-op, deterministic replay over the documented node RPC. This is the strongest possible leverage of what exists: the anchor layer is TKV0's design with different ops. (d) zstd with a trained dictionary for batch compression — the same choice as OP Stack/Arbitrum's move from brotli/zlib; EVM calldata compresses ~3–5x. (e) DA mirror on Cloudflare R2 + IPFS pin + BitTorrent v2 — R2 because the operator already runs its site on Cloudflare (existing operational competence), IPFS/torrent because content-addressed redundancy lets ANYONE become a mirror the moment they fetch a batch, softening (not removing) the trusted-DA problem. Celestia-style external DA was considered and rejected for v1: it swaps "trust Postern" for "trust a second consensus system" while adding integration surface; it is listed as a v2 option. (f) EIP-1559 fee semantics on the L2 — not for fee-market purity but because wallets, ethers.js, and Uniswap's deployment tooling assume it; compatibility is the point. (g) K=24 / W=240 / 300 s cadence — derived from the node's real constants (30 s TARGET_BLOCK_TIME, TKV0's K=24 depth rule), not invented.

**Interfaces / formats.** ON-CHAIN WIRE FORMAT — "L2V0" envelope family (zero-value TxOutput script_pubkey, little-endian, strict decoding, malformed⇒no-op, first-wins per tx — all rules inherited from TKV0 SPEC.md): COMMON HEADER: magic "L2V0" (4B) | version 0x00 (1B) | op (1B). OPS: 0x01 GENESIS/CONFIG — chain_id u64, genesis_state_root 32B, sequencer_pubkey 32B, vault descriptor (M u8, N u8, N×20B addr hashes), W u32, K u8, da_mirror_url_len u8 + URL. rollup_id := txid of this tx (same identity trick as TKV0 token_id: globally unique, no registry). 0x02 BATCH — rollup_id 32B, batch_no u64, prev_batch_hash 32B, batch_data_hash 32B (SHA3-256 of zstd batch), da_mode u8 (0x01 on-Bloch / 0x02 mirror), post_state_root 32B, withdrawal_root 32B, l2_block_first u64, l2_block_last u64, ipfs_cid_len u8 + CID, infohash 32B. Fixed+var ≤ ~220B — one cheap output per batch. 0x03 DA_CHUNK (Mode A only) — batch_data_hash 32B, chunk_index u16, chunk_total u16, payload (bounded by MAX_TX_SIZE 400 KiB; reconstruction = concatenate by index, verify SHA3-256). 0x04 FORCE_TX — rollup_id 32B, raw RLP signed EVM tx (policy cap 64 KiB). Deadline rule: confirm-depth K=24 at height h ⇒ must execute in a batch anchored by h+W. 0x05 PROOF_COMMIT — rollup_id 32B, batch_no_first u64, batch_no_last u64, proof_hash 32B, vkey_hash 32B (proof bytes on mirror at /da/v0/proof/{proof_hash}). 0x06 EXIT_MODE — rollup_id 32B, trigger u8 (1=halt,2=censorship), evidence_batch_no u64, signed by vault signers. SEQUENCER RPC (owned endpoint): full standard eth_ namespace (eth_sendRawTransaction, eth_call, eth_getLogs, eth_feeHistory …) so MetaMask/ethers/foundry work unmodified; plus postern_getInclusionReceipt(txHash) → {seq_no, soft_block, timestamp, sig}, postern_getBatch(n), postern_operatorStatus() → {label:"single disclosed operator: Postern Labs", forced_inclusion_backlog, last_anchor_height, da_mode}. EXIT CLAIM (off-chain message to signers, format published): {rollup_id, state_root, account, MPT/verkle proof of balance + ERC-20 slots, L1 destination address, user sig}. DERIVATION PIPELINE (the neutral, anyone-can-run part, shipped as open source like bloch-tokens): replay Bloch via getblockcount/getblockhash/getblockbyheight → filter L2V0 by rollup_id → fetch batch bytes (chunks or mirror) → verify hashes → re-execute in revm OR verify SP1 proof against vkey → local state root MUST equal anchored root, else raise FRAUD alarm. Reorg rule inherited from TKV0 §D.2: track height→hash, rewind to fork point on mismatch, replay; L2 state anchored to reorged Bloch blocks is rewound with it, and the sequencer must re-post orphaned anchors.

**Tradeoffs.** (1) DA Mode B (mirror) vs Mode A (on-Bloch): B gives real throughput and keeps the 1 MB/30 s base chain unclogged, at the price of DA becoming a trusted service (withholding halts verification and can impair exits). A gives true L1 DA — the chain alone reconstructs everything — but the measured ceiling is ~33 KiB/s chain-wide (≈100–200 simple txs/s absolute max at 100% chain occupancy), it crowds out every other Bloch user, bloats archival storage forever, and costs BLCH fees per byte. Decision: B by default, A always available per-batch and mandatory for FORCE_TX/GENESIS, and the honest framing is that A is the fallback that keeps B honest-ish (the operator knows anyone can demand on-chain DA pressure). (2) Single sequencer vs consortium now: a single disclosed operator is honest and simple; a fake "decentralized" set of 3 Postern-run nodes would be decentralization theater, explicitly banned. Cost: total liveness dependence on one org — mitigated only by the escape hatch, and stated. (3) Sovereign anchored rollup vs waiting for covenants (E1): posting proofs the L1 can't verify is strictly weaker than an enforced validity rollup, but E1 requires a soft-fork nobody can schedule on an ownerless chain; shipping the sovereign version now, with the derivation pipeline open-source so verification is permissionless, beats vaporware. The E1 upgrade path (covenant-verified exits) is listed as roadmap, never promised. (4) FIFO vs fee auction ordering: FIFO-with-priority-lane sacrifices fee-market efficiency and is only detection-auditable (self-reported timestamps), but it is the honest baseline for a trusted sequencer — running a MEV auction while being the sole trusted orderer would be extracting from users under a trust relationship. (5) FRI proofs vs Groth16 wrapper: raw STARK/FRI keeps the repo's PQ discipline and avoids curve assumptions, at the cost of MB-scale proofs — acceptable only because verification is off-chain anyway; a wrapped proof would buy nothing here. (6) 300 s batch cadence: shorter cadence shrinks the soft-confirmation trust window but multiplies BLCH anchor fees and Bloch chain load; 300 s ≈ 10 Bloch blocks is the compromise, revisited with real fee data. (7) Proving lag: SP1 proving of EVM batches takes minutes on an L40S; state roots are anchored per batch but PROOF_COMMITs trail by 1–4 batches. Window semantics stated plainly: an anchored-but-unproven root is a sequencer claim, nothing more.

Bloch today runs the relaxed k=4 regime — trivially forgeable, low-hashrate, 51%-attackable, unaudited. An L2 cannot be more final than its L1: a Bloch reorg rewinds BATCH, FORCE_TX, PROOF_COMMIT, and EXIT anchors; forced-inclusion deadlines become ambiguous across forks; a reorged deposit can mint L2 funds against a deposit that no longer exists (the classic double-spend-by-reorg). NO REAL VALUE moves on this L2 until the Bloch mainnet gates clear (k=8 progressive ramp, live WAN hashrate, checkpoint-finality depth, third-party audit) — until then it is testnet, zero-value, mechanism-proving only, and every screen says so.** **THE TRUST SURFACE OF THE v1 OPERATOR, EXACTLY: with validity proofs the operator CANNOT forge state or steal via a false root without being cryptographically caught by any verifier — but Bloch does not verify proofs, so "caught" means publicly detected and attributed, NOT automatically reverted; the operator CAN censor any transaction (mitigation: forced inclusion — detection + deadline, no slashing); CAN halt entirely (mitigation: escape hatch — which itself depends on the DA mirror serving the state snapshot AND on the disclosed M-of-N vault signers actually honoring exits, because Bloch has no covenants and cannot force them); CAN reorder for MEV despite the published FIFO policy (receipts make it auditable after the fact, not preventable); and in DA Mode B CAN withhold batch data, which blinds verifiers and can break exits even though the anchored hash proves the data existed. THE BLCH VAULT IS OPERATOR CUSTODY IN v1. ## 5. L1<->L2 Bridge — canonical BLCH deposits/withdrawals + outside-asset (wBTC/wUSDT/wETH) plug-in socket, for the Postern-operated zk-validity EVM L2 anchored to the ownerless Bloch-SIS-PoW base. DESIGN ONLY — nothing built, audited, or safe; testnet/zero-value until POSTERNDEX-BRIDGE-DESIGN §0 gates clear.

**Architecture.** TWO INDEPENDENT BRIDGES SHARING ONE L2 SOCKET, with strictly asymmetric trust:

(A) CANONICAL BLCH BRIDGE (native rollup path — §2a of POSTERNDEX-BRIDGE-DESIGN, never touches foreign chains).
L1 side has NO smart contract, because Bloch has none: node validation (validate_tx_inputs) only enforces spent-UTXO script_pubkey == SHA3-256(pubkey)[..20], so the L1 leg is (v1, honestly custodial) an operator-held VAULT — a disclosed, published set of N single-key ML-DSA-65 addresses with funds sharded across them (see honestRisks: no production threshold ML-DSA exists, so 'multisig' is a quorum POLICY across independent keyholders, not a cryptographic M-of-N). E1 covenants would later let a vault UTXO enforce release rules natively; until that soft-fork, custody is disclosed as custody.

DEPOSIT FLOW: user builds one ordinary Bloch tx that (1) pays BLCH to any disclosed vault address and (2) carries a zero-value 'L2D0' deposit envelope output (same provably-zero-consensus-change trick as TKV0: nodes never constrain new-output script_pubkeys) naming the L2 recipient + L2 chain-id. The sequencer's L1 watcher (reusing crates/bloch-tokens indexer.rs replay algorithm verbatim: getblockcount/getblockhash/getblockbyheight, height->hash map, rewind-on-mismatch reorg handling) detects the deposit; after the component-2 confirmation depth K(amount) — an amount-tiered schedule, floor K=24 (6x the DAG k, matching TKV0 §D.3), scaling up with value — the deposit becomes a mandatory system 'BlochDepositTx' on L2 (OP-Stack deposit-tx pattern: custom EIP-2718 type, no signature, mints native gas-BLCH to the recipient). Deposit processing is part of the L2 DERIVATION RULE: the SP1 validity proof for each epoch commits, as a public input, the L1 view (Bloch block hash + height) it derived from, and proves 'every valid L2D0 envelope at depth >= K under that view was credited exactly once, and nothing else was minted'. So the sequencer cannot forge or double-credit deposits without breaking the proof — but the proof is only as good as the named L1 view: a Bloch reorg below that view reverses the deposit while the L2 credit stands. Deposits therefore inherit FULL Bloch reorg risk by construction; K only prices out casual reorgs (no finite K is finality on a 51%-attackable chain).

WITHDRAWAL FLOW (Bloch-finality-bound by construction): user calls L2BlochBridge.withdraw() on a fixed predeploy, which burns msg.value of native gas-BLCH and appends a withdrawal leaf to a keccak256 incremental Merkle tree whose root is folded into the epoch OUTPUT ROOT. The output root is (a) proven by the SP1 validity prover (coherence-prover lineage: core STARK/FRI proof ONLY, never the Groth16/Plonk wrapper — the project's post-quantum rule) and (b) anchored to Bloch by component 2 as an ordinary transaction. Release requires ALL of: [1] the anchor tx carrying that output root is at finality depth F on Bloch, checked by each keyholder against its OWN full node; [2] the raw FRI proof publicly verifies (proof bytes published; each keyholder re-verifies locally with the pinned SP1 verifier + guest vkey — no one trusts anyone's verification); [3] a valid Merkle inclusion proof of the leaf against the proven withdrawal root; [4] no active reorg freeze; [5] the post-release proof-of-reserves invariant still holds. Only then do quorum keyholders co-sign the L1 payout tx from their vault shards. Withdrawal latency is therefore F Bloch blocks + proving time — slow on purpose.

REORG SENTINEL (the §0.1 double-spend vector): every keyholder's release agent independently maintains the height->hash map; any mismatch deeper than R blocks trips a LOCAL freeze flag — all releases halt, in-flight withdrawals whose anchor was reorged revert to pending, and releases resume only W blocks after the fork resolves with the anchor re-confirmed on the new selected chain. Freeze is per-agent (no central kill switch can be subverted to fake liveness); a rate limiter caps outflow per key per epoch so a single compromised keyholder can skim at most its shard's daily limit.

PROOF-OF-RESERVES: permissionless — anyone sums UTXOs at the published vault address set on their own node and checks sum(vault) >= totalSupply(gas-BLCH on L2) + sum(pending unreleased withdrawals). The operator additionally publishes a signed daily snapshot, but the equation is verifiable without trusting it.

(B) OUTSIDE-ASSET SOCKET (wBTC/wUSDT/wETH — the POSTERNDEX-BRIDGE-DESIGN §3 spectrum, plugged into the L2, NOT TKV0 on L1). Wrapped assets mint as ORDINARY ERC-20s on the L2, so Uniswap v2/v3 pairs (wBTC/wUSDT etc.) deploy byte-for-byte unchanged. Three fixed predeploys: [1] BridgeTokenFactory — CREATE2-deploys BridgedERC20 instances at deterministic addresses keyed by (origin chain, origin asset, gateway); [2] FederatedGateway (the B1 path) — the only address with mint/burn rights on its tokens; mints require M-of-N EIP-712 attestations from the disclosed custodian set over (originChainId, originTxId, originVout, recipient, amount), with originTxId replay-protection; burn(amount, originChainAddress) emits RedeemRequested which custodians honor from the origin-chain vault (custodians here are ordinary EVM keys, so REAL cryptographic M-of-N is available on this side — e.g. a Safe-style threshold — unlike the L1 BLCH vault); [3] HTLCBridge (the B3 path) — a plain HashedTimelockERC20-style contract for custody-free point-in-time atomic swaps (the honest v1 for BTC per §8). [4] TrustRegistry predeploy — per-token on-chain metadata {trustModel: B1_FEDERATED|B3_HTLC, custodianSetHash, M, N, proofOfReservesURI, issuerFreezeRisk, gatesCleared} that wallets and the PosternDex frontend MUST surface as the in-product trust badge; wUSDT is registered with issuerFreezeRisk=true carrying Tether's freeze/blacklist double-custody disclosure into every L2 representation. TrustRegistry is informational, not enforcement — and says so. A WBLCH predeploy (WETH9 clone at a fixed address) wraps native gas-BLCH so BLCH pairs work on unmodified Uniswap.

The two bridges never share custody or code paths: a wBTC failure cannot touch the BLCH vault, and vice versa; only the TrustRegistry and factory are shared surface.

**Concrete choices.** - SP1 zkVM (existing crates/coherence-prover: guest/host/HTTP-service scaffold, Fly.io L40S GPU deploy) for the bridge-relevant statements — deposit-derivation correctness and the withdrawal-tree root — folded into the L2's epoch state-transition proof; CORE STARK/FRI mode only (client.prove(..).core()), never .groth16()/.plonk(), preserving the repo's post-quantum coherence rule end to end. RISC0 is the fallback zkVM if SP1 licensing/perf disappoints; the interface is zkVM-agnostic (proof bytes + vkey hash).
- revm as the EVM (per the L2 execution component) with two bridge-specific extensions: a BlochDepositTx EIP-2718 type (0x7E, copied from OP Stack's deposit-transaction design — the most battle-tested 'L1-triggered mint' pattern in production) and a reserved predeploy address band 0x42...00-0x42...ff (also OP Stack convention: L2BlochBridge=...0010, BridgeTokenFactory=...0012, FederatedGateway=...0013, HTLCBridge=...0014, TrustRegistry=...0015, WBLCH=...0006).
- L2D0 deposit envelope reuses the TKV0 mechanism (zero-value script_pubkey output, magic + LE fields, malformed=>no-op, first-wins) because it is already specified, reviewed prose, and PROVABLY zero consensus change on unmodified nodes.
- L1 watcher reuses crates/bloch-tokens indexer.rs replay/reorg algorithm (deterministic replay, height->hash mismatch detection) rather than inventing a second sync engine.
- Withdrawal tree: keccak256 incremental Merkle tree, depth 32 (Ethereum deposit-contract construction) — cheap in Solidity for the L2 side, trivial in the SP1 guest, standard tooling for inclusion proofs.
- L1 vault keys: ML-DSA-65 (the chain's only signature scheme). Threshold ML-DSA is research-grade (Raccoon et al., not standardized, not what Bloch verifies), so v1 is UTXO sharding across N independent keyholders + quorum release policy, each key in an isolated signer box (HSM support for ML-DSA is still emerging — name that, don't assume YubiHSM-class support).
- ERC-20 stack: OpenZeppelin ERC20 for BridgedERC20, WETH9 bytecode verbatim for WBLCH, EIP-712 typed attestations for federated mints, Safe-pattern threshold ownership for gateway admin — all boring on purpose; the whole point of the EVM L2 is to use unmodified, already-audited Ethereum contracts.
- Outside assets on the L2 (not TKV0 on L1) because: TKV0 is not consensus-enforced (indexer-only state — unacceptable for value-bearing wraps), Uniswap needs ERC-20s, and one trust disclosure surface (TrustRegistry) beats per-indexer conventions.

**Interfaces / formats.** L2D0 DEPOSIT ENVELOPE (one zero-value TxOutput.script_pubkey; all ints little-endian; malformed => token-layer no-op, BLCH still lands in the vault and is credited manually/refunded per published policy):
offset 0: 4B magic 'L2D0' | 4: u8 version=0x00 | 5: u8 op=0x01 DEPOSIT | 6: u64 l2_chain_id (EVM chain id) | 14: 20B l2_recipient (EVM address) | 34: end (exactly 34 bytes, no trailing). Deposit amount := sum of tx output values paying disclosed vault addresses; deposit_id := (txid, first vault-paying vout). One envelope per tx, lowest-index-wins (TKV0 rule C.1). Min deposit MIN_DEPOSIT_ATOMS (anti-dust, TBD).

CONFIRMATION DEPTH SCHEDULE K(amount) (testnet placeholder; re-derived at each §0 gate stage): <=10 BLCH -> 24 blocks; <=100 -> 96; <=1000 -> 288; above -> 288 + operator review. Published as a signed config; the derivation rule pins the schedule hash so the proof binds it.

BlochDepositTx (EIP-2718 type 0x7E): {sourceHash = keccak(deposit_id, l1_block_hash), from = alias(deposit_id), to = l2_recipient, mint = amount * ATOM_SCALE, gasLimit, data = 0x}. ATOM_SCALE = 10^(18 - BLOCH_DECIMALS) (constant TBD from L1 atom definition); withdraw() REVERTS unless msg.value % ATOM_SCALE == 0 (no dust loss, no rounding).

EPOCH OUTPUT ROOT (what component 2 anchors): output_root = keccak256(version_byte || l2_state_root || withdrawal_tree_root || l1_view_hash || l1_view_height || epoch_number). **Tradeoffs.** - CUSTODIAL VAULT NOW vs WAITING FOR E1 COVENANTS: covenant-encumbered vault UTXOs would be trust-minimized but require a consensus soft-fork nobody can force; shipping the L2 without base changes (hard constraint 1) means the L1 leg is custody. We take custody-with-disclosure now, design the release-agent checklist so the SAME rules become covenant script later, and label it.
- UTXO SHARDING + QUORUM POLICY vs CRYPTOGRAPHIC THRESHOLD: real M-of-N for ML-DSA doesn't exist in production; sharding across N keys means M colluding keyholders can steal only their shards plus rate-limit leakage per epoch — weaker than Bitcoin-style multisig, stronger than one key, and honest about it.
- DEPOSITS IN THE DERIVATION RULE vs SEQUENCER-DISCRETIONARY: forced derivation makes deposit crediting provable and censorship-evident (a proof that skips a due deposit is invalid), at the cost of binding every proof to an L1 view and forcing reorg handling into the protocol. Chosen anyway — it converts 'trust the sequencer to credit you' into 'trust math + the named L1 view'.
- WITHDRAWAL DELAY = ANCHOR FINALITY DEPTH vs FAST EXITS: hours-slow withdrawals are the honest price of inheriting Bloch's (absent) finality; a fast-exit LP market (someone fronts L1 BLCH against a pending withdrawal for a fee) is possible later but is a NEW trust/legal surface, deferred.
- AMOUNT-TIERED K vs FLAT DEPTH: tiered depth prices reorg cost against value at risk (the only lever on a chain with no finality gadget) at the cost of UX complexity; flat K would either overcharge small deposits or under-protect large ones.
- OUTSIDE ASSETS AS L2 ERC-20s vs TKV0 ON L1: TKV0 is indexer-convention state — fine for neutral issuance, indefensible for value-bearing wraps; ERC-20 on L2 gets consensus-enforced (validity-proven) balances, unmodified Uniswap, one TrustRegistry. Cost: outside assets live behind the sequencer's liveness and the L2's own trust stack — disclosed.
- PER-AGENT REORG FREEZE vs CENTRAL PAUSE: per-agent freezing means no single pause key to compromise and no operator able to quietly keep paying during an attack; cost is slower coordinated recovery and possible split-brain (some agents frozen, others not) — mitigated by requiring quorum anyway.
- TWO SEPARATE BRIDGES vs ONE UNIFIED: unified custody would pool risk across BLCH and wBTC/wUSDT; separation costs duplicate ops but caps blast radius per asset class.

**Honest risks & limits.** - THE VAULT IS CUSTODY, FULL STOP. v1 BLCH deposits are operator-held; quorum policy is organizational, not cryptographic (no production threshold ML-DSA). Colluding keyholders — or Postern itself — can steal reserves; proof-of-reserves DETECTS theft after the fact, it does not PREVENT it. This is disclosed in-product on every deposit screen.
- BLOCH REORGS BREAK BOTH DIRECTIONS. Bloch today is k=4, low-hashrate, 51%-attackable, unaudited, with NO finality gadget. Deposits: mint-against-deposit-then-reorg-the-deposit (POSTERNDEX-BRIDGE-DESIGN §0.1) leaves the L2 credit standing while the vault never received funds — K(amount) only prices out casual reorgs; NO finite depth is safe against a majority attacker. Withdrawals: F is a heuristic depth, not finality; the reorg sentinel freezes releases but cannot claw back an already-broadcast payout. The bridge's safety is BOUNDED BY L1 SECURITY BY CONSTRUCTION, which is why no real value moves until the §0 gates (k=8 ramp, live WAN hashrate, checkpoint finality, external audit, legal/money-transmission review) clear. Until then: testnet, zero-value, loudly labelled.
- THE VALIDITY PROOF DOES NOT PROVE L1 CANONICALITY. SP1 proves the state transition relative to a NAMED l1_view_hash; if that view is reorged, the proof remains 'valid' about a dead branch. Canonicality is checked out-of-proof by each release agent's own node — a trust assumption on node honesty/sync, stated.
- SEQUENCER TRUST REMAINS FOR LIVENESS/CENSORSHIP: validity proofs remove trust in state correctness, not in the operator's willingness to include your withdrawal or keep producing epochs. Forced-inclusion/escape-hatch design belongs to the sequencer component and is not solved here.
- DATA AVAILABILITY: if anchors carry only roots (component-2 dependent), reconstructing the withdrawal tree requires operator-published data; DA failure can strand provable-but-unprovable-by-you withdrawals. Labelled per component 2's DA choice.
- FEDERATED wBTC/wETH = B1 TRUST: M-of-N custodian compromise steals origin-chain reserves; the L2 ERC-20 becomes unbacked with no on-L2 recourse. wUSDT IS CUSTODIAL TWICE: custodian risk PLUS Tether freeze/blacklist/redemption risk — Tether can freeze the underlying and strand every L2 wUSDT holder even with a perfectly honest custodian; issuerFreezeRisk=true is carried into every wallet/DEX surface and cannot be waived.
- BRIDGES ARE THE MOST-EXPLOITED CONSTRUCT IN THE SPACE (billions lost). Nothing here is built or audited; the L2D0 parser, the SP1 guest, the gateway contracts, and the release agents are all unvalidated designs. External audit is a hard gate, not a nice-to-have.
- TrustRegistry is disclosure, not enforcement — a scam token can exist on the L2 regardless; the registry only makes honest labelling machine-readable.
- ML-DSA HSM support is immature; v1 keyholder boxes may be software signers — a real operational-security gap to close before any value.
