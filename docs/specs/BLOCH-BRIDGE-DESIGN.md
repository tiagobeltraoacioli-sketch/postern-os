# Bloch Bridge — design
**Status: DESIGN ONLY. Not built, not audited, not safe. Testnet / zero-value.** A SEPARATE, LATER, OPTIONAL module — the DEX ships WITHOUT it (native tokens; see [`POSTERNDEX-AMM-DESIGN.md`](POSTERNDEX-AMM-DESIGN.md) / [`POSTERNDEX-BRIDGE-DESIGN.md`](POSTERNDEX-BRIDGE-DESIGN.md) §2a). This wraps OUTSIDE assets (BTC/ETH/USDT) into 1:1 TKV0 tokens on Bloch and redeems them.
> **The four gates bound everything (see POSTERNDEX-BRIDGE-DESIGN §0).** Bloch is k=4 forgeable / 51%-attackable / unaudited — a reorg can unbback wrapped supply, so **no real asset is bridged until Bloch mainnet security + a third-party audit + legal review**. Bridges are the single most-exploited construct in crypto. USDT is inherently double-custodial (Tether + the federation). This is not legal advice.
_Consolidated from a 16-agent design fleet (1 PMO → 5 Fable-5 designers → 10 Sonnet reviewers). Each component carries its reviewers' verdicts._

## 1. B1 — Trust-Model Architecture & Federated Custody Vault (custodial/federated bridge path). An explicitly OWNED product/consortium per docs/specs/POSTERNDEX-BRIDGE-DESIGN.md §1/§3: a disclosed M-of-N custodian federation holding native BTC/ETH/USDT in threshold-signature vaults and minting/redeeming 1:1 wrapped TKV0 tokens (wBTC/wETH/wUSDT) on Bloch. DESIGN ONLY. Zero-value testnet federation first; no real assets until the §0 gates clear (Bloch k=8 mainnet-candidate security + finality depth, third-party audit of bridge logic, legal review for money transmission/securities, honest trust disclosure). This path is trusted-by-construction and says so: THE USER TRUSTS THE NAMED CUSTODIANS, FULL STOP — no 'decentralized' claim anywhere in code, docs, or UI.

**Architecture.** LAYERING (per §1: anything with an operator is a product, never the commons):
1. FEDERATION (owned, disclosed consortium): N signer organizations, each running a signer node with an HSM-backed key share. Initial mainnet parameters N=9, M=6 (testnet N=5, M=3). Stated attack surface, verbatim and published on every surface: collusion or compromise of M keys steals reserves. Dually, unavailability of N−M+1=4 signers freezes redemptions (safety/liveness split is disclosed, not hidden).
2. VAULTS (source chains):
   - BTC vault: a single FROST threshold-Schnorr group key (secp256k1, RFC 9591) expressed as P2TR (BIP-341) addresses. Per-deposit addresses are derived by taproot-tweaking the group key with a commitment to the depositor's Bloch mint address (see flows) — one logical vault, many auditable addresses, all sweepable via key-path with M-of-N FROST signing.
   - ETH + USDT(ERC-20) vault: one threshold-ECDSA (CGGMP21) group key controlling an EOA, fronted by a minimal audited Deposit/Vault contract that (a) binds deposits to Bloch mint addresses via events, (b) enforces a per-24h outbound rate limit and a timelock on limit changes — on-chain guardrails the pure-TSS EOA cannot give. USDT sits as an ERC-20 balance of the vault; it is INHERENTLY DOUBLE-CUSTODIAL (Tether + this federation) and is labelled so.
3. BLOCH SIDE (ownerless base, per TKV0): wBTC/wETH/wUSDT are ordinary TKV0 tokens. Because TKV0 v0 is mandatorily mint-closed, each wrapped token is issued ONCE with its maximum supply pre-minted to a federation-controlled TREASURY outpoint (wBTC: 2.1e15 base units = 21M BTC at 8 decimals; wETH/wUSDT: capped u64 supplies at 8/6 decimals). 'Mint' = TKV0 TRANSFER out of treasury; 'burn' = TKV0 TRANSFER back into treasury. Outstanding wrapped supply := issued_supply − treasury_balance, derivable by ANY independent TKV0 indexer with no privileged data. This makes proof-of-reserves arithmetic third-party-checkable by construction and means a Bloch reorg that unwinds a mint also unwinds the supply (indexer rewind-then-replay, TKV0 rule 7).
4. BRIDGE COORDINATOR (owned Postern service, stateless-recoverable): watches both chains, assembles signing requests, relays FROST/CGGMP21 rounds between signer nodes. It holds NO key material and CANNOT move funds; any M signers can reconstitute coordination if it dies (it is a liveness convenience, not a trust root — disclosed as such).
5. WATCHTOWERS (anyone): independent processes that recompute reserves and outstanding supply from public chain data and the published vault addresses, verify the continuous invariant reserves >= outstanding_wrapped_supply per asset, and alert/trigger mint-halt on violation. Postern runs some; the design requires at least 2 non-Postern operators before real value; anyone may run one (reads are public RPC on both chains).
KEY LIFECYCLE:
   - Generation ceremony: distributed key generation only (FROST DKG for BTC; CGGMP21 keygen for ETH) — no trusted dealer, no single machine ever holds the full key. Ceremony requirements: reproducibly-built, hash-pinned signer software; air-gapped or HSM-resident share storage (at least 3 distinct HSM vendors across the set, e.g. YubiHSM2 / Nitrokey HSM / cloud-HSM, no vendor >2 signers); authenticated pairwise channels; a signed public transcript (participant identities, software hashes, group public keys, resulting vault addresses) published before the first deposit.
   - Rotation (scheduled, e.g. semi-annual): proactive share refresh (re-randomize shares, same group key) so stolen old shares expire; vault addresses unchanged, announced via on-chain FED-UPDATE.
   - Eviction/replacement (membership change): remaining >= M signers run a fresh DKG for a NEW group key, then execute a supervised sweep of all vault UTXOs/balances to the new vault under the old quorum, publish new addresses via FED-UPDATE signed by the outgoing quorum, and PoR attestations must show continuity (old-vault balance → new-vault balance across the sweep, no gap in the invariant). Share-preserving resharing across membership change is deliberately NOT relied on for eviction — a sweep to a fresh key is the only way to provably invalidate an evicted party's material. Eviction triggers: missed heartbeats/attestations beyond SLA, evidence of key compromise, legal incapacity, or consortium vote per the (to-be-drafted) consortium agreement.
SIGNER-SET COMPOSITION & DIVERSITY (hard requirements before real value): N=9 distinct legal entities; max 2 per legal jurisdiction and max 2 under any one national jurisdiction's compulsion reach; max 2 per cloud/hosting provider (and >=3 signers on owned hardware, not cloud); no two signers sharing an executive, parent company, or security team; each signer's identity, jurisdiction, and contact published. Postern is at most 1 of N — the federation must survive Postern's compulsion or failure.

**Concrete choices.** - FROST (RFC 9591, secp256k1 ciphersuite) for BTC: produces a single BIP-340 Schnorr signature, so the vault is an ordinary P2TR key-path spend — cheapest on-chain footprint, no multisig script disclosure, arbitrary M-of-N, and taproot tweaking gives free per-deposit address binding. Reference: the ZF `frost-secp256k1` Rust crate (fits the project's Rust codebase).
- CGGMP21 threshold ECDSA for ETH/USDT: modern UC-secure TSS with identifiable aborts (a misbehaving signer is identified, feeding the eviction process) — chosen over GG18/GG20, which have known attack history. The group key is one EOA; ECDSA is required because Ethereum EOAs are ECDSA.
- Minimal Safe-style vault CONTRACT in front of the ETH EOA for rate limits + deposit-event binding: pure-TSS EOAs cannot enforce anything on-chain; a small audited contract caps blast radius of a signing-layer bug (a compromised quorum can still drain up to the rate limit per period — disclosed).
- TKV0 pre-minted treasury model for wrapped tokens: works with the shipped mint-closed v0 standard (no TKV1 fork needed for the bridge), makes outstanding supply a plain indexer query, and inherits TKV0's deterministic reorg-rewind semantics — directly serving the reorg constraint. Amount bounds fit u64 (BTC max supply in sats = 2.1e15 << 2^64).
- BRG0 memo envelopes (a new magic, distinct from TKV0's, on additional zero-value outputs — TKV0's 'first TKV0-magic envelope wins' rule ignores them, zero interference) to bind mints to source-chain deposits and burns to destination addresses ON-CHAIN, so the 1:1 mapping is publicly auditable, not a federation database.
- HSM-per-signer + DKG (never trusted-dealer): no single point ever holds the full key, matching the disclosed M-of-N trust claim exactly.
- N=9/M=6: M=6 makes theft require 6-party collusion/compromise across >=3 jurisdictions and >=3 HSM vendors; N−M+1=4 failures to halt keeps liveness reasonable. Testnet 3-of-5 to exercise the machinery cheaply. (Comparable prior art, cited honestly: Liquid's 11-of-15 functionary federation; WBTC's single custodian is the dishonest-simplicity baseline this design refuses.)
- Finality parameters (named, tunable constants): BTC deposits credited at 6 confirmations; ETH/USDT deposits credited only at Ethereum FINALIZED checkpoint (>=2 justified epochs, ~13 min) — not a conf count, because post-merge reorg risk is checkpoint-shaped; Bloch-side actions (recognizing a burn, trusting a mint) wait F_bloch = the §0 checkpoint-finality depth (pre-gate testnet default 60 blocks; NO real-value setting exists until the k=8 ramp + audit define it).

**Flows / on-chain formats.** ON-CHAIN FORMATS (spec level):
BRG0 memo envelope — script_pubkey of a zero-value output (same carrier discipline as TKV0), little-endian, strict decode: magic ASCII 'BRG0' (4B) | version 0x00 (1B) | op (1B) where op ∈ {0x01 MINT-MEMO, 0x02 REDEEM, 0x03 ATTEST, 0x04 FED-UPDATE}.
- MINT-MEMO body: asset_id (1B: 0x01 wBTC, 0x02 wETH, 0x03 wUSDT) | source_chain (1B) | source_txid (32B) | source_vout_or_logindex (4B) | source_block_hash (32B). Exactly one per mint tx; uniqueness of (source_chain, source_txid, index) is the replay guard — watchtowers flag any second mint referencing the same deposit.
- REDEEM body: asset_id (1B) | dest_len (1B) | dest (scriptPubKey for BTC, 20B address for ETH/USDT) | fee_bid (8B, u64 source-chain fee allowance deducted from payout).
- ATTEST body: asset_id (1B) | source_height (8B) | source_block_hash (32B) | reserves_base_units (8B u64) | outstanding_wrapped (8B u64) | vault_utxo_set_merkle_root (32B) | schnorr_sig by the federation group key over the preceding fields (64B). Group-key signature = M-of-N participated; anyone verifies against the published group pubkey.
- FED-UPDATE body: new_epoch (4B) | n (1B) | m (1B) | group_pubkey_btc (32B x-only) | group_addr_eth (20B) | signers_doc_hash (32B, hash of the published signer roster) | sig by OUTGOING group key (64B).

DEPOSIT → MINT (BTC): (1) User requests a deposit address from the coordinator (or derives it themselves — the derivation is public): addr = P2TR(P_fed, tweak = TapTweak(H('BLOCHBRIDGEv0' || bloch_mint_scriptpubkey || nonce32))). The tweak binds the deposit to the Bloch destination on-chain; the federation can key-path-sweep because the tweak is derivable. (2) User pays BTC to addr. (3) After 6 BTC confirmations, >=M signer nodes independently SPV-verify the deposit against their own bitcoind, then co-sign (this is an off-chain federation decision, honestly: the custodians attest, no light client on Bloch in B1). (4) Coordinator broadcasts the Bloch MINT tx: inputs spend the wBTC treasury outpoint; outputs: [0] user's colored output (TKV0 assignment = deposit sats), [1] TKV0 TRANSFER envelope {token_id=wBTC, [(0, amount),(2, treasury_remainder)]}, [2] treasury change (new treasury outpoint), [3] BRG0 MINT-MEMO. The treasury outpoint itself is guarded by the federation's Bloch-side threshold key (FROST over Bloch's signature scheme), so minting also requires M-of-N. ETH/USDT differ only at step 1–3: user calls Vault.deposit(blochAddr) / Vault.depositERC20(USDT, amt, blochAddr); signers credit only at Ethereum finality; wUSDT mints additionally check Tether's blacklist state of the vault (a frozen vault must halt wUSDT mints immediately).

BURN → REDEEM: (1) User builds a Bloch tx: TKV0 TRANSFER assigning their wrapped balance back to the current treasury outpoint's scriptPubKey + a BRG0 REDEEM memo with the destination. (2) Signers wait F_bloch Bloch blocks, then each independently verifies the burn tx is still in the canonical Bloch chain at the recorded block hash (reorg check — a reorged-away burn is simply never honored, and the TKV0 indexer rewind restores the user's balance). (3) M-of-N FROST (BTC) or CGGMP21 (ETH/USDT) signing releases the native asset to dest, net of fee_bid. (4) Release txid is published and linked to the burn txid in the public bridge log; one release per burn txid, ever.

PROOF-OF-RESERVES (mandatory, continuous): (a) Vault addresses (all BTC P2TR derivations' parent key, the ETH vault contract + EOA) are published at genesis and on every FED-UPDATE. (b) Every 24h (and after every sweep/rotation) the federation posts an ATTEST tx per asset on Bloch. (c) The invariant reserves >= outstanding_wrapped_supply is checked CONTINUOUSLY by watchtowers that recompute both sides from raw chain data — reserves from Bitcoin/Ethereum nodes at the attested height, outstanding supply from any TKV0 indexer — trusting no federation-published number. (d) Violation or a missed attestation window ⇒ automatic mint-halt (coordinator refuses new mints; signers' policy engines refuse mint signatures) while redemptions CONTINUE (redeem-only mode protects holders; never the reverse). (e) The UI shows the live invariant, the attestation age, and the raw addresses so anyone can re-verify.

TRUST-MODEL BADGE TAXONOMY (consumed by the PosternDex UI §5 and components 4–5) — one JSON document per bridge path, schema `bridge-trust-badge/v0`: { path_id, trust_model: 'custodial-federated' | 'spv' | 'atomic-swap', whom_you_trust: string (for B1, exactly: 'the named custodians listed below — full stop'), custodians: [{name, legal_entity, jurisdiction, contact, hsm_class}], quorum: {m, n}, attack_surface: 'collusion or compromise of M keys steals reserves', liveness_surface: 'N−M+1 signers offline freezes redemptions', double_custody: {flag, issuer: 'Tether', risks: ['freeze','blacklist','issuer redemption failure']} (wUSDT only, null otherwise), por: {vault_addresses[], attest_interval_h, latest_attest_txid, invariant: 'reserves >= outstanding_wrapped_supply'}, finality: {source_confs_or_checkpoint, f_bloch}, status: 'testnet-zero-value' | 'gated' | 'live', audits: [] }. SPV paths set whom_you_trust: 'the source chain's proof-of-work / consensus math, plus the redemption signer set (disclosed)'; atomic-swap paths set 'no one holds your asset; you trust the HTLC scripts and both chains' liveness'. The badge is signed by the federation group key and its schema is the interface contract for components 4–5.

**Tradeoffs.** - B1 vs B2/B3: federated custody is the LEAST trust-minimized path on the §3 spectrum but the only one giving persistent 1:1 wrapped balances for all three assets today (BTC SPV on Bloch is a big build; ETH light-client bigger; HTLCs give point-in-time swaps only). The design buys usability with disclosed trust, and the badge taxonomy exists precisely so the UI never blurs that.
- FROST P2TR key-path vs on-chain Bitcoin multisig (P2WSH CHECKMULTISIG): FROST hides the quorum and is cheap, but the signing is off-chain coordination — an observer cannot verify M-of-N participation per spend from the chain alone (they trust the ceremony transcript + attestations). Script multisig is publicly countable but caps N, costs more, and leaks the signer set structure. Chose FROST + published transcripts.
- CGGMP21 EOA vs Gnosis-Safe-style contract with per-signer keys: the Safe is on-chain-verifiable and supports modules/timelocks natively but exposes per-signer keys and costs gas per approval; pure TSS is opaque. Chose the hybrid (TSS EOA behind a thin rate-limit contract) — partial on-chain guardrails without per-signer key exposure. The rate limit itself trades incident blast-radius against redemption throughput.
- N=9/M=6 vs smaller/larger: higher M hardens theft but softens liveness (4 outages freeze redemptions); larger N eases liveness but multiplies ceremony/rotation cost and jurisdictional attack surface. 6-of-9 is a defensible middle; it is a parameter, not a truth.
- Eviction via sweep-to-new-key vs share resharing: resharing is cheaper and keeps addresses stable, but cannot PROVE an evicted signer's material is dead; the sweep costs on-chain fees, an operational window, and an address change (mitigated by FED-UPDATE + PoR continuity), and was chosen because provable invalidation beats convenience for a custody product.
- Pre-minted TKV0 treasury vs a new mintable TKV1: treasury works today with zero standard changes and free reorg semantics, but the treasury outpoint is a hot Bloch-side threshold key and 'outstanding = issued − treasury' is a convention indexers/UIs must implement uniformly (spec'd in the badge/PoR docs). A future TKV1 with federation-gated mint would be cleaner but is a standard fork this bridge deliberately does not require.
- Redeem-only halt mode vs full halt on PoR violation: continuing redemptions during an incident can race a partial theft (first-come drain of what remains), but a full freeze traps every holder against custodian discretion; redeem-only was chosen as the holder-protective default, disclosed.
- Per-deposit tweaked BTC addresses vs one static vault address: tweaks bind deposits to mint destinations trustlessly and improve auditability, at the cost of a more complex PoR (reserves = sum over the derivation set, hence the UTXO-set merkle root in ATTEST) versus one trivially watchable address.

**Honest risks & limits.** - TRUST MODEL, stated plainly: on this path the user trusts THE NAMED CUSTODIANS, FULL STOP. Collusion or compromise of M keys steals reserves. Nothing about FROST, MPC, HSMs, attestations, or the word 'federation' makes this decentralized, and no Postern surface may imply otherwise. The federation can also censor (refuse to mint/redeem for anyone) and can be legally compelled; jurisdiction diversity raises the cost of compulsion, it does not eliminate it.
- REORG / FINALITY DOUBLE-SPEND (the central problem): Bloch today is k=4, trivially forgeable, 51%-attackable, unaudited. Attack A (Bloch reorg): attacker burns wBTC, receives native BTC after F_bloch, then a deep Bloch reorg erases the burn — the indexer rewind restores their wrapped balance while they keep the BTC ⇒ unbacked supply. F_bloch mitigates only up to reorg depth F_bloch; against a 51% attacker on today's chain NO finite F_bloch is safe — which is exactly why real value is hard-gated on the §0 mainnet-candidate security (k=8 ramp, WAN hashrate, checkpoint finality, audit). Attack B (source-chain reorg): a BTC deposit reorged away after mint leaves wBTC unbacked; 6 confs is a probabilistic judgment, not a proof, and ETH pre-finality reorgs are why only FINALIZED deposits count. Attack C (in-flight ops during either reorg): mitigated by signers re-verifying canonical inclusion immediately before signing, but a race window is irreducible. Bridges are the single most-exploited construct in crypto (billions lost: Ronin — 5-of-9 validator keys, precisely this design's failure class; Wormhole; Multichain, whose MPC opacity hid effective key centralization). Assume adversaries; assume this design has an undiscovered flaw until audited.
- CUSTODY/OPERATIONAL: ceremony compromise (poisoned build, exfiltrated shares) defeats everything downstream — hence reproducible builds and published transcripts, which REDUCE, not remove, this risk; HSMs mitigate remote theft, not insider misuse; the coordinator, while trustless for funds, is a censorship/liveness single point until federated; the eviction sweep is itself a high-value signing event and an attack window.
- PROOF-OF-RESERVES LIMITS: PoR proves the vault held funds at attested heights — it does NOT prove absence of encumbrances (the federation could have pledged the keys' output elsewhere), does not prove intent or solvency of the custodian entities, and snapshot attestations can in principle be gamed with borrowed funds between windows; the continuous watchtower invariant narrows but does not close this. PoR is necessary, never sufficient.
- USDT DOUBLE CUSTODY: wUSDT depends on Tether AND the federation. Tether can freeze/blacklist the vault address at will, instantly stranding reserves so that wUSDT holders cannot be made whole even by a perfectly honest federation; Tether's own reserve/redemption risk passes through 1:1. wUSDT CANNOT be trust-minimized on any path — it is custodial twice over, and the badge, the UI, and this document all say so.
- LEGAL: operating this federation is likely money transmission (and possibly more) in most target jurisdictions; the consortium agreement, licensing, and Postern's incorporation are HARD GATES before any real value. Not legal advice.
- SCOPE HONESTY: everything above is a design. Nothing is built, audited, or safe; the testnet federation holds zero value by design and every screen says so.

**Open questions.** - WHO are the N custodians? Recruiting >=8 non-Postern, jurisdiction-diverse, HSM-capable legal entities is the hardest unbuilt dependency; the consortium agreement (eviction votes, liability, insurance, cost sharing) needs counsel per jurisdiction. Related §8 question: does Postern operate the only bridge or bootstrap the consortium from day one?
- Exact F_bloch and BTC-conf values for real value cannot be set until the §0 security work lands — who owns deriving them from measured Bloch hashrate/finality data, and are they per-asset and per-amount (larger mints, deeper finality)?
- Bloch-side treasury key: FROST assumes Schnorr/secp256k1 — confirm Bloch's transaction signature scheme supports it (the PQ-wallet direction in the ecosystem suggests it may not); if Bloch signatures are PQ/non-Schnorr, the treasury needs a different threshold scheme (e.g. threshold variants for the actual scheme, or a script-level M-of-N) — this is a blocking spec dependency on the node's signature layer.
- ETH vault contract scope: is the thin rate-limit contract enough, or should redemptions also be timelocked on-chain (better incident response, worse UX)? Formal spec + audit scoping needed.
- TKV1 (federation-gated mintable tokens) as a cleaner long-term standard vs the treasury convention — and if treasury stays, the 'outstanding = issued − treasury' convention must be added to indexer guidance so all indexers/UIs agree.
- Watchtower economics: what makes >=2 independent non-Postern watchtowers actually run (grants? none — money-hygiene rules constrain incentives)? An unwatched invariant is theater.
- Fee model for mint/redeem (flat vs bps, who sets it, where disclosed) — must stay utility-service revenue, never token-linked, per project rules.
- Interaction contract with components 4–5: freeze the bridge-trust-badge/v0 JSON schema and the BRG0 envelope formats with golden byte vectors (TKV0-style) before any implementation; who owns that vector suite?
- Incident playbook details: exact mint-halt/redeem-only trigger thresholds, communication SLAs, and whether a compromised-but-not-yet-drained vault should emergency-sweep to a pre-committed fallback key (pre-signed sweep templates?) — powerful but itself a new attack surface.
- Insurance/recourse: is any custodial-loss coverage feasible pre-incorporation, and how is 'no recourse' worded in the UI until it exists?

## 2. B3 — Atomic Swaps / HTLC: trustless, custody-free, point-in-time BTC<->Bloch swaps. No bridge, no wrapped supply, no custodian; nobody ever holds the counterparty's asset. This is the honest v1 for BTC per POSTERNDEX-BRIDGE-DESIGN.md §8 while Bloch runs the forgeable k=4 regime, and per §6 Phase 2 it may precede the full custody gates because it holds nothing — audit still applies. Deliverables: (1) a Bitcoin-side HTLC template (standard script, zero Bitcoin changes), (2) a Bloch-side HTLC output class "HTL0" (a minimal, height-gated consensus upgrade — see honest disclosure in choices/risks), (3) the swap protocol with reorg-sized timeout asymmetry, (4) swap-client daemons for both parties, (5) an optional Postern-hosted matchmaking/orderbook layer, disclosed as an OWNED Postern product that never touches funds.

**Architecture.** FOUR LAYERS, two neutral + two peripheral.

L1a — Bitcoin leg (neutral, unchanged Bitcoin): a BIP-199-style HTLC in P2WSH (P2TR script-path as an option). Watched via the party's own Bitcoin Core node (descriptor wallet) or a bundled Neutrino/BIP-157 light client; no third-party API dependency.

L1b — Bloch leg (neutral, ownerless base): a new consensus-recognized script_pubkey class `HTL0` on the Bloch UTXO layer. Ground truth from the node source (~/dev/BlochSISPoW-project/src/main.rs, fn validate_tx_inputs, line 1809): today the ONLY spend rule is script_pubkey == SHA3-256(pubkey)[..20] + hybrid Falcon-1024‖ML-DSA-65 signature; tx.locktime exists in the wire format (crates/bloch-crypto/src/core/mod.rs:732) and is committed by the sighash but is NEVER validated. Therefore Bloch has no hashlock and no enforced timelock primitive, and an HTLC output class is a consensus change: old nodes reject any spend whose script_pubkey is not a 20-byte pk-hash, so recognizing HTL0 spends is a coordinated flag-height network upgrade ("HTLC-V0"), not a soft-fork in the Bitcoin sense. It is deliberately ~100x narrower than the E1 covenant layer: two fixed predicates (SHA-256 preimage check; absolute-height refund check), no interpreter, no opcodes, no Turing anything. On today's tiny node population a height-gated upgrade is feasible; it is disclosed as such.

L2 — swap clients: `bloch-swapd`, a Rust daemon each party runs (or the Postern wallet embeds). Holds both chain watchers, drives the state machine (fund/verify-confs/claim/refund), persists secrets and pre-built refund transactions to disk before broadcasting anything, and enforces the timeout invariants — refusing to participate if the counterparty proposes unsafe timelocks. It is the watchtower for its own swap; an optional Postern-hosted watch/alert service exists but is an owned convenience, never required for safety if the machine stays online.

L3 — matchmaking/orderbook (OWNED Postern product, disclosed): a coordination-only service — order posting, quote matching, encrypted param handshake (amounts, H, pubkeys, timelock heights, fee rates), liveness pings, reputation scores. It NEVER holds keys, funds, or the secret. Concretely: a Cloudflare Durable Object per trading pair speaking JSON over WSS (fits Postern's existing CF footprint), with the message schema published so anyone can run a rival matcher, use Nostr relays, or match OTC — the HTLC rails are neutral; only the hosted matcher is a product, labelled per §7.

**Concrete choices.** HASH FUNCTION: SHA-256 for the hashlock on BOTH chains — forced by Bitcoin Script (OP_SHA256; no SHA-3 opcode exists), so the HTLC-V0 upgrade adds a SHA-256 check to the Bloch node (sha2 crate, alongside its native SHA3). Preimage s is exactly 32 random bytes; both chains enforce len==32 (Bitcoin: OP_SIZE 32 OP_EQUALVERIFY; Bloch: fixed-width field) to kill oversize-preimage incompatibility attacks.

BITCOIN SCRIPT (P2WSH witness script, miniscript `andor(pk(claim),and_v(v:sha256(H),1),and_v(v:pk(refund),after(T_btc)))` equivalent):
OP_IF OP_SIZE 32 OP_EQUALVERIFY OP_SHA256 <H> OP_EQUALVERIFY OP_DUP OP_HASH160 <claim_pkh> OP_ELSE <T_btc> OP_CHECKLOCKTIMEVERIFY OP_DROP OP_DUP OP_HASH160 <refund_pkh> OP_ENDIF OP_EQUALVERIFY OP_CHECKSIG. Built via rust-miniscript; funded/spent with Bitcoin Core 27+ descriptor wallets or BDK. Absolute CLTV (block height), not relative CSV, so the refund time is fixed at handshake regardless of confirmation delays.

WHY NOT SCRIPTLESS/ADAPTOR SIGNATURES: taproot adaptor-signature swaps (as in production Monero-BTC swaps) need Schnorr-style adaptor tweaks; Bloch signs with hybrid Falcon-1024‖ML-DSA-65 (README: both must verify) and lattice adaptor signatures are research-grade, not production crypto. Explicit hashlock scripts on both chains is the honest, buildable choice; it costs privacy (the swap is linkable via H) — disclosed.

BLOCH HTL0 OUTPUT (on-chain format, normative): script_pubkey, 85 bytes, all ints LE —
offset 0, 4B: magic ASCII "HTL0"; 4, 1B: version 0x00; 5, 32B: H = SHA-256(s); 37, 20B: claim_pkh = SHA3-256(claim_pk)[..20]; 57, 20B: refund_pkh = SHA3-256(refund_pk)[..20]; 77, 8B: refund_height (u64, absolute accepted-height in the GhostDAG-Q ordering). Output value = the BLCH being swapped (non-zero; contrast TKV0's zero-value envelopes — no collision: different magic, and TKV0 rides zero-value outputs only).
SPEND RULES (consensus, active ≥ flag height): claim path script_sig = 0x01 ‖ s(32B) ‖ sig ‖ pk, valid iff SHA-256(s)==H ∧ SHA3-256(pk)[..20]==claim_pkh ∧ hybrid sig verifies over the existing sighash — valid at ANY height, including after refund_height (first confirmed spend wins). Refund path script_sig = 0x02 ‖ sig ‖ pk, valid iff containing block's accepted height ≥ refund_height ∧ pk hashes to refund_pkh ∧ sig verifies. No general tx.locktime enforcement is introduced — the timelock lives inside the output, minimizing consensus surface.

CLIENT: bloch-swapd in Rust; Bitcoin via BDK/Core RPC, Bloch via the node's documented JSON-RPC (getblockcount/getblockhash/getblockbyheight — same surface bloch-tokens uses). ORDERBOOK: Cloudflare Durable Object per pair, WSS+JSON, published schema, Postern-branded and disclosed as owned. TESTBED: Bitcoin signet <-> Bloch testnet, zero value, before anything else.

**Flows / on-chain formats.** ROLES: Alice holds BTC, wants BLCH; Bob holds BLCH, wants BTC. Alice is the secret-holder and funds FIRST (the secret-holder must be the first funder, else she gets a free option before committing anything).

HAPPY PATH — (1) Match: via orderbook (or OTC) the parties exchange {amount_btc, amount_blch, alice_btc_refund_pk, alice_bloch_claim_pk, bob_btc_claim_pk, bob_bloch_refund_pk, H, T_btc, T_blc, conf policy}; each swapd validates the timelock invariants below and refuses otherwise. (2) Alice generates s (32 random bytes), H=SHA-256(s), persists s encrypted, funds the Bitcoin P2WSH HTLC (claim=Bob-with-s, refund=Alice-after-T_btc). (3) Bob's swapd watches Bitcoin; after N_btc confirmations (6 for real value; 3 signet) he funds the Bloch HTL0 output (claim_pkh=Alice, refund=Bob-after-T_blc). (4) Alice's swapd watches Bloch; ONLY after Bob's funding is buried ≥ N_blc_reveal (below, sized to Bloch's reorg horizon) does she broadcast the claim spend — which necessarily reveals s on-chain. (5) Bob's swapd extracts s from Alice's claim script_sig and claims the Bitcoin HTLC; after 6 BTC confs Bob is final. Swap complete; at no instant did either party hold both assets.

REFUND PATHS — Bob never funds: Alice waits and refunds Bitcoin at T_btc (griefing cost = capital lockup, see risks). Alice never claims: Bob refunds Bloch at T_blc; Alice later refunds Bitcoin at T_btc; nobody lost principal. Alice claims late (after T_blc): claim remains VALID but races Bob's refund — first confirmed spend wins; swapd never claims within a safety margin of T_blc (auto-aborts to the refund plan instead).

TIMEOUT ASYMMETRY (the core safety math, per the k=4 constraint) — invariant chain, with t() = wall-clock estimate (Bloch ~30 s/block, Bitcoin ~600 s):
(i) N_btc = 6 confs before Bob funds (protects Bob from a Bitcoin reorg of Alice's funding).
(ii) N_blc_reveal = max(coverage by a stored checkpoint, 720 Bloch blocks ≈ 6 h) before Alice reveals s. While k=4 is trivially forgeable NO depth is truly safe against a determined attacker — which is exactly why real value is gated; the parameter exists so the mechanism is correct when the k=8 ramp + checkpoint-finality land, where N_blc_reveal := checkpoint depth D_cp.
(iii) t(T_blc) ≥ t(fund_blc) + N_blc_reveal + claim window; concrete v1: T_blc = Bloch funding height + 2,880 blocks (~24 h).
(iv) t(T_btc) − t(T_blc) ≥ D_cp·30 s + 6·600 s + margin, with margin ≥ 12 h; concrete v1: T_btc = BTC funding height + 288 Bitcoin blocks (~48 h). Rationale: after Alice claims on Bloch and reveals s, Bob must be able to (a) see the reveal even through a Bloch reorg-and-replay, and (b) get his Bitcoin claim 6-conf-final, all strictly before his own Bitcoin refund matures — and, symmetrically, Alice's Bloch claim must be checkpoint-buried strictly before T_blc so a Bloch reorg cannot resurrect Bob's refund path after he has taken the BTC. The ~24 h Bloch-side refund delay is deliberately conservative precisely because Bloch's reorg horizon is unproven; swapd hard-rejects any proposal violating (i)–(iv).

ORDERBOOK MESSAGES (spec level, JSON over WSS): {type:"order", pair:"BTC/BLCH", side, amount, min_premium, maker_pks, ttl} → {type:"take", order_id, taker_pks} → {type:"params", H, T_btc, T_blc, conf_policy, fee_rates} → {type:"funded", chain, txid, height} progress events → {type:"reveal", s? no — never; the secret NEVER transits the matcher} → {type:"done"|"abort"}. The matcher relays and timestamps; it can lie about liveness but can never spend, censor a chain, or learn s.

**Tradeoffs.** HTL0 upgrade vs no consensus change: I looked hard for a zero-consensus path and it does not exist — the node's single spend predicate (pk-hash + hybrid sig, main.rs:1809) cannot express a hashlock, and lattice signatures preclude adaptor-signature scriptless swaps; even a P2SH-style trick fails because old nodes verify the signature against the raw pk. So B3 costs one small network upgrade. That is still massively cheaper and more auditable than E1 covenants (two fixed predicates vs an interpreter) and it doubles as the first live rehearsal of Bloch's upgrade governance. Alternative rejected: swapping only via an L2 (E2) — that reintroduces a sequencer/operator into the one path whose whole point is trusting no one.

Explicit hashlocks vs adaptor signatures: hashlocks are linkable (same H on both chains — a public correlation beacon) and cost more bytes; adaptor sigs would be private but are not production-real for ML-DSA/Falcon. Honesty wins: hashlocks, with the privacy loss disclosed.

Secret-holder-funds-first vs taker-funds-first: funding order pins the free option on the party who committed capital first (Alice); reversing it gives the secret-holder a cost-free option. Chosen order plus premiums/size-caps is the standard, least-bad arrangement.

Absolute timelocks vs relative: absolute heights fix the deadline at handshake and avoid needing per-input sequence semantics (which Bloch's tx format lacks); cost is that slow confirmation eats into the usable window — swapd compensates by aborting early.

CLTV-in-output vs enforcing tx.locktime globally: enforcing the existing locktime field network-wide would be a broader consensus change affecting every tx; embedding refund_height in the HTL0 output touches only HTL0 spends. Narrower blast radius, chosen.

Postern-hosted DO orderbook vs pure P2P (Nostr): the hosted matcher has better liveness/UX and spam control but is an owned product with censorship power over MATCHING (never over funds); publishing the schema and supporting rival matchers caps that power. Pure P2P ships later if demanded.

24 h/48 h windows vs tighter: long windows shrink reorg risk but enlarge the free option and capital lockup. v1 picks safety over capital efficiency — correct while the chain is unproven; parameters tighten as D_cp gets a real, measured value.

**Honest risks & limits.** TRUST MODEL, exactly: you trust (a) Bitcoin PoW at 6 confs, (b) Bloch PoW/checkpoint finality at the chosen depth, (c) your own machine staying online (or a disclosed watch service) through the timeout windows, (d) the audited correctness of two scripts and one small consensus predicate. You trust NO custodian, NO federation, NO oracle, NO sequencer. The matcher is trusted only for matching liveness and can rug nothing.

REORG / FINALITY DOUBLE-SPEND (the central problem): today Bloch is k=4 forgeable and 51%-attackable, so NO Bloch confirmation depth is meaningful against a resourced adversary. Concrete attack: Bob funds Bloch, Alice claims (reveals s), Bob claims BTC, then Bob 51%-reorgs Bloch past Alice's claim and confirms his refund after T_blc — Bob exits with BTC AND BLCH. The timelock asymmetry ((ii)–(iv)) makes this attack require sustaining a reorg deeper than a checkpoint for ~24 h+, which is the best a protocol can do; it cannot conjure security the base chain lacks. Therefore: REAL-VALUE SWAPS REMAIN GATED on the §0 chain-security gates (k=8 ramp, WAN hashrate, checkpoint finality, audit) even though B3 holds no custody — B3 merely shifts the reorg loss from "unbacked wrapped supply harming everyone" to "one counterparty in one swap", which is why it may precede the custody gates but not the security gates for real value. Until then: signet/testnet, zero value, labelled on every screen.

FREE OPTION: after both legs fund, Alice holds an American option until ~T_blc (~24 h): she claims only if BLCH/BTC moved in her favor, else lets it expire and refunds. Unfixable in any HTLC design; mitigations disclosed as mitigations, not fixes: maker-priced upfront premium (a small unconditional output to Bob on Alice's Bitcoin funding tx), short-as-safe windows, per-swap size caps in v1 (e.g. 0.01 BTC), orderbook reputation. GRIEFING: either party can stall, locking the other's capital for 24–48 h at near-zero attacker cost (Bitcoin fees only); premiums plus reputation raise the cost, never to zero.

CUSTODY/COLLUSION: none possible — there is nothing to collude over; no proof-of-reserves needed because there are no reserves. The corresponding honest LIMIT: point-in-time swaps ONLY — no persistent on-Bloch BTC balance, no wBTC token to trade on PosternDex, no standing liquidity, both parties online with capital locked for hours, poor UX at size. That standing-balance gap is exactly what B1 (federated custody) and B2 (BTC SPV) wrapping exist for later, post-audit+legal.

USDT: B3 deliberately excludes it. A USDT HTLC on Ethereum is technically writable, but USDT can never be trust-minimized — it is double-custodial by nature (Tether issuer risk: freeze/blacklist/redemption, PLUS any bridge custodian in B1/B2 paths), and Tether can freeze the very contract mid-swap. Any future wUSDT ships only under B1 with the double-custody disclosure of §3; pretending an HTLC fixes USDT would be an overclaim.

RESIDUAL: HTLC linkability (same H on both chains deanonymizes the pair); Bitcoin-side fee spikes can strand a claim near T_btc (swapd reserves aggressive fee headroom and aborts early); the HTLC-V0 upgrade itself is unaudited until the contracted audit covers it — audit applies to B3 despite Phase-2 precedence.

## 3. B2 — SPV / Light-Client Deposit Verification for the Bloch Bridge (BTC first; ETH scoped-and-deferred). A trust-minimized DEPOSIT path: an on-Bloch Bitcoin light client (PoW-verified header chain + Merkle inclusion proofs) proves that a BTC deposit really happened, so minting wBTC (a wrapped 1:1 token per docs/specs/POSTERNDEX-BRIDGE-DESIGN.md §3-B2) needs no custodian attestation. Explicit scope limit, stated up front: SPV trust-minimizes the MINT direction only. REDEMPTION (releasing native BTC on burn) still requires a threshold signer set to sign a Bitcoin transaction — B2 is "trustless in, bonded-federation out," and must never be marketed as fully trustless. This module is DESIGN ONLY, a separate optional later module: the DEX ships without it, and no real value flows until the §0 gates (Bloch k=8 mainnet-candidate security, third-party audit, legal review, honest trust labeling) clear.

**Architecture.** FIVE SUBSYSTEMS.

(1) BTC HEADER RELAY ("bloch-btcrelay") — a Bitcoin light client whose state lives on the bridge substrate. On E2 (recommended first substrate, per bridge doc §2): the light client is a deterministic state machine INSIDE the L2's state-transition function, so its correctness is covered by the L2's validity proof posted to Bloch — the sequencer cannot fake a header chain without breaking the proof. On E1 (covenant path, long-term): a singleton "relay UTXO" whose covenant script enforces the state transition append_headers(old_state, headers[]) -> new_state, carrying a commitment (MMR root, see Choices) to all accepted headers; heavier, deferred. State kept: (a) an append-only Merkle Mountain Range over accepted BTC block hashes, (b) per-header metadata for the last 4·2016 headers (hash, height, nBits, timestamp, cumulative chainwork), older ones pruned to the MMR, (c) a fork tree of the last 500 headers so heavier competing branches can displace the tip, (d) a hard-coded trusted CHECKPOINT (recent BTC block hash + height + chainwork + retarget state) baked in at deploy — the relay refuses any chain not descending from it. Header submission is PERMISSIONLESS: anyone may submit batches of raw 80-byte headers; a small relayer rebate (paid from bridge operating fees, an owned-product cost, never BLCH emission) keeps at least one honest relayer live, and the bridge operator runs one as backstop.

(2) DEPOSIT VAULT ADDRESSING — the BTC vault is a Taproot P2TR output controlled by a FROST t-of-n group key Q (see Choices). Each deposit gets a UNIQUE address: Q tweaked per BIP-341 with t = H_taptweak(Q || H(bloch_recipient_pk || deposit_nonce)), so the deposit itself binds the Bloch recipient — no OP_RETURN needed, no address reuse, and the tweak is verifiable on-Bloch from public data. The signer group can still spend every tweaked output (standard taproot key-path with tweak).

(3) DEPOSIT PROOF VERIFIER — verifies {raw BTC tx, block hash, tx index, Merkle branch} against an accepted header: parse the tx (SegWit-aware; txid over the stripped serialization), double-SHA256 Merkle path to the header's merkle_root, check the claimed output pays the expected tweaked P2TR script for a registered (recipient, nonce), extract amount in sats, enforce the confirmation-depth AND cumulative-work policy (below), enforce one-mint-per-BTC-outpoint replay protection keyed on (txid, vout), then queue the mint behind a CONTEST WINDOW.

(4) MINT MODULE — after the contest window, credits wBTC 1:1 (minus a disclosed flat fee) to the Bloch recipient. On E2 wBTC is an L2 ledger token; its L1 TKV0 representation is an open design point because TKV0 v0 mandates the mint-closed flag (crates/bloch-tokens SPEC.md §1.2 — supply is fixed at ISSUE), which is incompatible with an elastic wrapped supply — see Open Questions. Mints are additionally gated on BLOCH-side finality: the crediting L2 batch must be anchored in a Bloch block buried past the checkpoint-finality depth (and the whole module is disabled until the §0 chain-security gate — on today's k=4 chain a Bloch reorg could replay/erase mints).

(5) REDEMPTION MODULE (the honest non-SPV part) — burn wBTC with a BTC destination scriptPubKey attached; after the burn is Bloch-final, the FROST t-of-n signer set (disclosed, bonded/collateralized, tBTC-v2-style) co-signs a BTC payout from vault UTXOs; a relayer then SPV-proves the payout tx back into bloch-btcrelay to close the redemption and meter signer liability. Signers are an OWNED consortium (an operator ⇒ a product, per the layering rule), with mandatory continuous PROOF-OF-RESERVES: the vault UTXO set is public on Bitcoin, and the invariant sum(vault UTXOs) >= wBTC supply is checked automatically via the same light client and displayed in-product.

CONFIRMATION-DEPTH / MINIMUM-WORK POLICY (source chain, central to the reorg problem): a deposit is provable only when BOTH hold — (a) depth tiers scaled by value: <0.01 BTC: 6 confs; 0.01–0.1: 12; 0.1–1: 24; >=1 BTC: 36; plus a per-2016-block epoch cap on total minted value (throttles the blast radius of any single deep-reorg attack); (b) work-not-height: the chainwork accumulated on top of the deposit's block must be >= depth_tier × expected_work_per_block, where expected_work is derived from the checkpointed difficulty — so an attacker cannot substitute many cheap low-difficulty headers for few real ones. All accepted-branch headers must also satisfy Bitcoin's own rules (see Flows), whose retarget clamp (difficulty can drop at most 4× per 2016 blocks) makes a fake low-difficulty fork from the checkpoint astronomically expensive.

ECLIPSE / FAKE-HEADER-CHAIN MITIGATIONS: (i) hard-coded recent checkpoint (fake chains must fork after it, paying real PoW); (ii) cumulative-work acceptance — the relay follows most-work, so eclipsing the relay requires out-mining Bitcoin for the contest duration, not merely feeding it isolated headers; (iii) permissionless multi-relayer submission — eclipse requires suppressing every honest submitter on Bloch, not just a P2P peer set; (iv) CONTEST WINDOW: a proven deposit waits N Bloch-hours before mint, during which anyone submitting a heavier BTC branch that excludes the deposit voids it; (v) watchtower monitoring (an owned service): compares relay tip vs multiple independent Bitcoin nodes/APIs and can trip an on-substrate CIRCUIT BREAKER that pauses mints (pause-only power, publicly logged — it can never mint or seize); (vi) sanity bounds: header timestamps must satisfy median-time-past and not exceed local time + 2h, and nBits must equal the retarget-computed value exactly.

ETHEREUM — FEASIBLE BUT DEFERRED (documented, not promised): verifying Ethereum on Bloch means an Altair sync-committee light client — track the 512-member committee, verify aggregate BLS12-381 signatures on LightClientUpdate messages, follow finalized headers, then verify deposit receipts/events via MPT (Merkle-Patricia) proofs against the receipts root. That is a heavy build (BLS12-381 pairing verification inside the L2 STF or a SNARK wrapping it, Helios/Telepathy-style), and its trust model is WEAKER than BTC SPV: you trust an honest supermajority of the current sync committee, not full Ethereum consensus. Until built and audited, wETH/wUSDT can exist only via the B1 federated path with that disclosure; wUSDT additionally carries the inherent Tether double-custody disclosure and can NEVER be trust-minimized regardless of path.

**Concrete choices.** NAMED TECH, WITH WHY. (1) Bitcoin header verification exactly per Bitcoin Core rules: 80-byte headers; PoW check double-SHA256(header) <= target decoded from the nBits compact encoding; difficulty retarget every 2016 blocks using the first/last-block timespan (preserving Core's off-by-one) clamped to [timespan/4, timespan·4]; chainwork per header = floor(2^256 / (target+1)); median-time-past over the last 11 headers. Why: byte-for-byte compatibility with Bitcoin consensus is non-negotiable — any divergence is a fork-acceptance bug. (2) Prior art adopted deliberately: BTC-Relay (Ethereum, 2016) for the permissionless header-relay + relayer-fee model; Interlay/XCLAIM for the SPV-mint + collateralized-vault-redeem split and its formal treatment; tBTC v2 (Threshold Network) for bonded, rotating threshold-signer wallets and sortition. Why: bridges are the most-exploited construct in crypto — copy designs with published analyses and years of adversarial exposure rather than inventing. (3) Signing: FROST (IETF RFC 9591) threshold Schnorr over secp256k1, producing BIP-340 signatures for taproot key-path spends — the vault looks like an ordinary P2TR output on Bitcoin (cheap, private, no on-chain multisig fingerprint); CGGMP21 threshold ECDSA is the documented fallback only if a legacy (pre-taproot) output type were ever required. (4) BIP-341 tweaked per-deposit addresses (Q + H(...)·G) instead of OP_RETURN recipient tagging. Why: binds the Bloch recipient cryptographically into the deposit output itself, avoids users needing nonstandard-tx wallets, and yields address-per-deposit accounting for proof-of-reserves. (5) Merkle Mountain Range over accepted header hashes for the relay's long-term state. Why: O(log n) inclusion proofs against unboundedly many historical headers with O(1) on-substrate storage growth, letting the relay prune raw headers safely. (6) Substrate: E2 L2 with validity proofs as the first home (bridge doc §2 recommendation) — the light client + verifier run inside the proven state-transition function, so header/SPV verification is trust-math even though the sequencer is an operator (trusted for liveness only); the E1 covenant "relay UTXO" is specced as the ownerless-native long-term option, not the v1. (7) Wrapped tokens as TKV0-family tokens per the bridge doc, with the mint-closed conflict flagged (Open Questions). (8) ETH path, when/if built: Altair sync-committee light client + BLS12-381 aggregate verification + MPT receipt proofs, optionally SNARK-wrapped (Helios/Telepathy pattern) — named now so the deferral is concrete, promised never.

**Flows / on-chain formats.** MESSAGE FLOWS AND ON-CHAIN FORMATS (spec level; all integers little-endian to match TKV0 conventions; all messages are bridge-module transactions inside the E2 L2, whose batch commitments anchor to Bloch as ordinary transactions).

M1 SUBMIT_HEADERS { count: u16, headers: count × 80 bytes (raw Bitcoin serialization) }. Verifier, per header: prev_blockhash links to a known header in the fork tree; double-SHA256(header) <= target(nBits); at height % 2016 == 0, nBits equals the retarget computation exactly, else nBits equals parent's; timestamp > MTP(last 11) and <= substrate_time + 7200s. Effects: extend fork tree; recompute best tip by cumulative chainwork; on tip change, roll accepted-branch headers older than the fork buffer into the MMR; if a previously-accepted branch is displaced, any pending deposits proven only on it revert to unproven and any un-minted queued credits are voided.

M2 REGISTER_DEPOSIT_INTENT { bloch_recipient_pk: 32B, deposit_nonce: 8B, min_amount_sats: u64 }. Effects: derive tweak t = H_taptweak(Q || H(recipient_pk || nonce)); record expected scriptPubKey = P2TR(Q + t·G); return the bech32m address to the user. Intents expire (e.g. 30 days) to bound state.

M3 PROVE_DEPOSIT { intent_id: 32B, btc_block_hash: 32B, tx_index_in_block: u32, merkle_branch_len: u8, merkle_branch: len × 32B, raw_tx: var, vout: u32 }. Verifier: block_hash is on the accepted best branch with depth >= tier(amount) AND accumulated chainwork above it >= tier × checkpoint-derived expected work; txid = double-SHA256(stripped raw_tx); fold txid up merkle_branch by tx_index to the header's merkle_root; raw_tx.outputs[vout].script_pubkey == expected P2TR script for intent_id; amount = outputs[vout].value >= min_amount_sats; (txid, vout) absent from the spent-deposit set; epoch mint cap not exceeded. Effects: mark (txid,vout) consumed; enqueue PENDING_MINT { recipient, amount, matures_at = now + CONTEST_WINDOW }.

M4 CONTEST (implicit) — any M1 during the window that makes the deposit's block non-best (or below required depth) voids the PENDING_MINT and re-opens the intent. No special message: contest IS header submission, which keeps it permissionless.

M5 MINT (module-internal, at maturity) — credit wBTC: amount − fee to recipient on the L2 ledger; emit MintReceipt { btc_txid, vout, amount, recipient, relay_tip_hash } into the batch data anchored on Bloch, so any outside indexer can audit supply-vs-deposits. Effective only once the anchoring Bloch block is past checkpoint-finality depth.

M6 BURN_FOR_REDEEM { amount_sats: u64, btc_dest_spk_len: u8, btc_dest_spk: var (standard-script-only allowlist: P2TR/P2WPKH/P2WSH), max_fee_sats: u64 }. Effects: debit wBTC; enqueue redemption; queue becomes signer-actionable only after the burn's Bloch anchor is final.

M7 REDEEM_PAYOUT_PROOF — same structure as M3 but proving the signers' payout tx (paying btc_dest_spk from vault UTXOs) is confirmed; closes the redemption, updates the tracked vault UTXO set, and feeds the proof-of-reserves invariant sum(vault UTXOs) >= wBTC_supply, whose violation trips the circuit breaker and is displayed in-product.

CONSTANTS TABLE (deploy-time, published): checkpoint {hash, height, chainwork, retarget state}; conf tiers {6/12/24/36 by value band}; CONTEST_WINDOW (initial: 24 Bloch-hours — deliberately long while the chain is young); epoch mint cap; fees; FROST t-of-n and signer roster; Bloch finality depth. Every constant appears in the UI next to the trust-model badge required by bridge doc §5.

**Tradeoffs.** (1) SPV vs full validation: the light client proves INCLUSION under PoW, not transaction validity — a miner could theoretically bury an invalid tx; mitigation is depth (economically infeasible on Bitcoin at 6+ confs) — accepted, this is the standard SPV assumption, and it is why depth tiers scale with value. (2) E2-embedded light client vs E1 covenant relay: E2 ships without a consensus change and gets verification covered by validity proofs, but inherits a sequencer (liveness/censorship trust, an operator ⇒ a product); E1 is ownerless-native but requires covenant opcodes powerful enough for double-SHA256 + retarget arithmetic in-script plus a singleton state-carrying UTXO — a soft-fork nobody can force; E2 first, E1 documented. (3) Tweaked per-deposit addresses vs OP_RETURN tagging: tweaks are wallet-friendly and cryptographically binding but require the user to obtain the address from the bridge (an intent step, M2) before depositing — a mis-sent deposit to a stale/expired intent needs a manual signer-set refund path (disclosed as federated, not SPV). (4) Value-tiered confirmations + epoch caps vs UX: large deposits wait hours and throughput is capped; deliberate — a source-chain reorg after mint leaves wrapped supply UNBACKED, the worst failure class, so latency is the price of backing. (5) Long contest window vs deposit latency: 24h is hostile UX but is the only defense that converts "eclipse the relay" into "out-mine Bitcoin for a day"; shrink only with audited monitoring maturity. (6) FROST bonded signers for redemption vs pure trustlessness: the only alternatives are BitVM-style covenant tricks (immature, enormous) or no-redemption (one-way peg) — bonded threshold signing is the honest, buildable compromise, and it caps but does not eliminate trust. (7) Header pruning via MMR vs keeping all headers: O(1) state growth vs slightly larger deposit proofs for old blocks — MMR wins since deposits are always recent. (8) ETH sync-committee client deferred vs shipping wETH sooner via B1: shipping B1-wETH earlier is honest ONLY with the loud federated-custody label; conflating it with B2's trust badge would be the overclaim this design forbids.

**Honest risks & limits.** TRUST MODEL, STATED EXACTLY. Mint direction: you trust (a) Bitcoin PoW majority (deep-reorg safety), (b) the correctness of the light-client/verifier code (UNAUDITED until §0 gate 2), (c) on E2, the validity-proof system's soundness, and the sequencer for liveness/censorship (it can delay, not forge). Redeem direction: you trust t-of-n disclosed signers not to collude or lose keys — t colluding signers STEAL THE ENTIRE VAULT. Bond slashing deters only up to bond value; if vault value exceeds total bonds, theft is rational — hence the epoch mint caps, and this must be printed next to the deposit button. B2 IS NOT FULLY TRUSTLESS AND MUST NEVER BE MARKETED AS SUCH: it removes custodian say-so from minting only. REORG DOUBLE-SPEND (the central problem, both directions): (i) BTC reorg after mint → deposit vanishes, wBTC supply unbacked; mitigations are depth tiers, work-not-height acceptance, contest window, epoch caps — mitigations, not eliminations. (ii) Bloch reorg — today's chain is k=4, trivially forgeable, 51%-attackable, unaudited: a reorg can erase a mint the user already trades against, or replay a burn to double-redeem native BTC; therefore this entire module is HARD-GATED on the §0 mainnet-candidate gates (k=8 ramp, real WAN hashrate, checkpoint finality, third-party audit) and runs testnet/zero-value only until then — no exceptions. ECLIPSE/FAKE-CHAIN RESIDUAL: mitigations force an attacker to produce real PoW exceeding Bitcoin's honest chain for the contest window AND suppress all honest relayers on Bloch; the watchtower/circuit-breaker backstop is an OWNED service — a centralization point, disclosed, powers limited to pause. CUSTODY/COLLUSION: the signer consortium is an owned product with an operator; proof-of-reserves (vault UTXOs vs wBTC supply, auto-checked by the same light client) is MANDATORY and continuous, but proof-of-reserves proves backing, not intent — it cannot prevent a future collusive theft, only make it immediately visible. USDT DOUBLE-CUSTODY: wUSDT depends on (a) Tether the issuer — freeze, blacklist, redemption and solvency risk on the underlying — AND (b) the bridge signer set; no light client changes that; wUSDT is inherently custodial twice over, cannot be trust-minimized by B2 or anything else, and (like wETH) is deferred behind the unbuilt ETH light client anyway — near-term wUSDT would be pure B1 with the double-custody label. FURTHER: nothing here is built or audited; bridges are the single most-exploited construct in crypto (billions lost) and this design assumes adversaries but cannot prove their absence; the redemption consortium likely constitutes money transmission — legal review is a hard gate before any real value; the flat fees are utility revenue for an operated service, never a BLCH mechanism.

**Open questions.** (1) WRAPPED-TOKEN STANDARD CONFLICT: TKV0 v0 mandates mint-closed fixed supply (crates/bloch-tokens SPEC.md §1.2 flags bit 0), which cannot represent an elastic wBTC supply on L1. Options: keep wBTC purely as an L2 ledger token (L1 sees only anchored commitments — simplest, weakest L1 composability); or specify a TKV1 with an issuer-gated MINT/BURN op (reintroduces an issuer key into a deliberately neutral standard); or pre-issue a max-supply TKV0 token to a bridge-controlled reserve and treat "mint" as release (ugly supply-reading semantics). Needs a decision before Phase 1. (2) SIGNER COLLATERAL DENOMINATION: BLCH is worthless-by-design and unsuitable as slashable bond; tBTC bonds in a valuable L1 asset. Bond in BTC held in separate FROST wallets (cross-vault slashing needs its own signing ceremony — recursive trust)? External legal contracts instead of crypto-economic bonds? This determines how real the "collateralized" claim is and must be resolved honestly or the collateral claim dropped. (3) CHECKPOINT ROTATION GOVERNANCE: the hard-coded BTC checkpoint needs periodic advancement; on E2 the operator updates it (a disclosed product power — publish and time-lock the procedure?); on E1 it would need a redeploy/soft-fork story. (4) CONTEST-WINDOW AND TIER CALIBRATION: 24h/6-36 confs are placeholders; final values need adversary-cost modeling (Bitcoin rent-a-hashrate cost vs epoch cap) as audit input. (5) RELAYER INCENTIVES: rebate size and funding source; is one operator-run relayer plus altruists enough, or does the relay need a fee market? (6) MIS-SENT/EXPIRED-INTENT DEPOSITS: exact refund procedure via the signer set (that path is federated — how is it labeled distinctly in-product?). (7) ETH DECISION LATER: sync-committee client in-STF vs SNARK-wrapped; whether the weaker committee-honesty assumption deserves a distinct trust badge from BTC-SPV, or whether wETH simply stays B1 indefinitely. (8) E1 COVENANT OPCODE SET: minimum opcodes for in-script header verification (double-SHA256, u256 compare, retarget arithmetic, state-carrying UTXO) — worth specifying now so the community can evaluate the soft-fork independently of Postern. (9) CONSORTIUM COMPOSITION: does Postern operate the initial signer set alone (maximal honesty label) or bootstrap independent members before launch — bridge doc §8 leaves this open, and the answer changes the money-transmission analysis in each jurisdiction.

## 4. Wrapped TKV0 Mechanics: Mint/Burn, 1:1 Peg, Redemption Queue & Reorg-Safe Finality — the token-layer mechanics of the Bloch bridge (B1 federated path per POSTERNDEX-BRIDGE-DESIGN.md §3), issuing wBTC/wETH/wUSDT as TKV0 tokens on the unmodified `crates/bloch-tokens` standard, with the peg invariant, the dual-chain finality state machine, reorg handling, redemption queue, rate limits, and circuit breaker. DESIGN ONLY: a separate, later, optional module; the DEX ships without it; real value is gated on §0 (k=8 ramp, WAN hashrate, checkpoint finality, audit, legal).

**Architecture.** **A. The mint-authority problem and the Treasury model (works on TKV0 v0 unmodified).** TKV0 v0 hard-rejects any ISSUE without FLAG_MINT_CLOSED set (SPEC §1.2; `envelope.rs:237` returns an error for `flags != FLAG_MINT_CLOSED`), so there is no open-mint op to gate behind an operator key. Instead, per asset, the bridge operator performs a ONE-TIME ISSUE of the full hard supply cap to output 0 (R3), where output 0 is locked to the bridge operator's threshold key. That operator-held balance is the **treasury** — economically "unminted" supply. `token_id := txid` of that ISSUE tx, published permanently (the three token_ids ARE the asset identifiers; anything else with symbol "WBTC" is a fake, and the frontend pins by token_id, never symbol). "Mint" = TKV0 TRANSFER from treasury outpoints to the depositor. "Burn for redemption" = TKV0 TRANSFER from the user back to the treasury address (NOT a literal R2/R4 color burn — literal burns destroy color forever and would permanently shrink mintable capacity; they are tolerated as accidental over-collateralization, see risks). This realizes "FLAG_MINT_CLOSED semantics controlled by the bridge operator key" without touching the standard: the flag guarantees no one — operator included — can ever inflate the token_id's total supply; the operator key only controls circulation out of a fixed pot. A TKV1 open-mint extension is explicitly rejected for v1 (it would fragment the standard and hand the operator true inflation power; see openQuestions).

**B. Per-asset parameters (u64 base-unit arithmetic forces these).** wBTC: decimals=8 (sats), ISSUE supply = ramp cap, e.g. 1,000 BTC = 1e11 base units (NOT 21M — supply is unchangeable in v0, so the cap is the permanent ceiling; pick per ramp phase, new token_id per phase if raised — disclose migration). wETH: **decimals=9 (gwei), not 18** — 18 decimals in u64 caps total supply at ~18.4 ETH, which is unusable; gwei precision caps at ~1.8e10 ETH (fine) and sub-gwei deposit dust is truncated in the user's favor (bridge keeps the dust in the vault as buffer). wUSDT: decimals=6 (native USDT precision), cap e.g. 1e13 = 10M USDT. Symbols WBTC/WETH/WUSDT (all within `A–Z0–9`, ≤8).

**C. The peg invariant, stated exactly.** For each asset: `circulating(t) = ISSUE.supply − treasury_balance(t) − color_burned(t)` (all three computable by ANY independent TKV0 indexer from public chain data — no operator API needed). Required invariant at every observation: **`vault_reserves(t) ≥ circulating(t)` — reserves lead, supply lags.** Achieved by strict ordering: (1) reserves are credited (deposit source-final) BEFORE any mint signature is produced; (2) circulating is debited (burn Bloch-final) BEFORE any native release is signed. During in-flight windows reserves temporarily exceed circulating; the reverse must never occur, and any indexer observing `circulating > vault_reserves` is proof of operator fraud or a successful reorg attack — trigger (b) of the circuit breaker.

**D. Components (the bridge daemon, `bloch-bridged`, run by each of the N custodians).** (1) **Source watchers**: bitcoind (own full node, ZMQ rawblock + RPC) for BTC; own geth/reth + a consensus-layer beacon node for ETH/USDT, consuming ONLY finalized checkpoints (Casper FFG) — never the unfinalized head. No third-party RPC (Infura etc.) in the trust path. (2) **Bloch watcher**: embeds the `bloch-tokens` indexer crate as a library — same R1–R6 rules, same per-height block-hash journal, same rewind-then-replay reorg recovery (SPEC §3.7) — extended with a bridge-event scanner for BRG0 memo outputs (see flows). (3) **State-machine store**: embedded sqlite, append-only event log; every deposit keyed by `deposit_id = H(chain_id ‖ txid ‖ vout_or_log_index)`, single-use, idempotent. (4) **Signer coordinator**: FROST (Schnorr, M-of-N, taproot) for the BTC vault; for ETH/USDT a **Gnosis Safe M-of-N contract** as the vault (simpler and independently audited vs threshold-ECDSA CGGMP21 — Safe chosen for v1, threshold-ECDSA noted as the non-contract alternative); for Bloch treasury spends, M-of-N over Bloch's native signature scheme (aggregate or naive multi-input multisig, whichever the Bloch script supports — open question). (5) **Policy engine**: confirmation tables, caps, breaker logic — a deterministic pure function over the event log, so all N custodians independently compute identical decisions and only co-sign when they agree (the M-of-N quorum IS the policy enforcement: a single compromised daemon cannot mint or release alone). (6) **PoR attester**: hourly report — vault addresses + balances with source-chain block refs, circulating per independent TKV0 derivation, pending queues — M-of-N signed, published on posternlabs.com, and its hash anchored on Bloch in a zero-value tx (same anchoring pattern as FFG/RWA/BaaS).

**E. Layer placement (doc §1/§7).** The token_ids and TKV0 rails are neutral/ownerless — anyone can index, verify, or fork. The federation, vaults, daemon, PoR service are an OWNED product/consortium with named operators. The frontend badge says "custodial-federated (M-of-N)" per doc §5.

**Concrete choices.** **TKV0 v0 unmodified + treasury model** — zero standard changes, reuses the audited-to-be indexer, FLAG_MINT_CLOSED gives a cryptographic hard cap no operator can inflate; chosen over a TKV1 open-mint op (standard fragmentation, true inflation power) and over per-mint ISSUE txs (each mint would create a new token_id — unusable as a fungible asset). **FROST** (RFC 9591-style Schnorr threshold) for the BTC taproot vault — key never exists whole, on-chain footprint is a single keypath spend, refresh/resharing supported for custodian rotation. **Gnosis Safe M-of-N** on Ethereum for ETH+USDT vaults — battle-tested contract, on-chain-auditable signer set and policy, avoids shipping CGGMP21 threshold-ECDSA in v1. **Ethereum finalized-checkpoint-only ingestion** (beacon API `finalized` head) — replaces probabilistic confirmations with economic finality (reversal requires ≥1/3 stake slashing). **BTC value-scaled confirmations**: floor 6; required depth ≥ depth such that estimated cost-to-reorg (from live hashrate × depth) > 10× deposit value; concrete v1 table: <0.01 BTC→6, 0.01–0.1→12, 0.1–1→24, ≥1 BTC→72, plus per-mint max 5 BTC. **Bloch finality parameter F**: F := checkpoint-finality horizon once that ships (mainnet-candidate gate); until then testnet placeholder F = max(64, 16·k) blocks with value pinned to zero — today's k=4 regime is declared NON-FINAL for any real value, full stop. **BRG0 memo envelope** (new, bridge-scoped, off-consensus): a second zero-value output carrying magic "BRG0" — TKV0's decoder ignores non-"TKV0"-magic outputs entirely (R2 "first TKV0-magic envelope wins"), so BRG0 piggybacks on the same tx without touching token semantics. **Deterministic mint construction** (one canonical tx per deposit_id, deterministic treasury coin selection) — the anti-double-mint mechanism under reorgs. **Own full nodes on all three chains per custodian** — removes RPC-provider trust. **sqlite append-only event log** — replayable, auditable, deterministic policy evaluation across custodians.

**Flows / on-chain formats.** **BRG0 memo wire format (spec-level, LE integers, strict decode like TKV0):** header: magic "BRG0" (4B) ‖ version 0x00 ‖ op (1B). Op 0x01 MINT-ATTEST body: source_chain (1B: 0x01=BTC, 0x02=ETH, 0x03=USDT-ERC20) ‖ source_txid (32B) ‖ source_index (4B, vout or log index) ‖ amount_base_units (8B) ‖ deposit_id (32B). Op 0x02 REDEEM-REQUEST body: source_chain (1B) ‖ dest_len (1B, 1..=64) ‖ dest_address_bytes (raw scriptPubKey for BTC / 20-byte address for ETH-USDT) ‖ min_fee_ack (8B, max native-chain fee user accepts deducted). Op 0x03 CONTROL body: 0x00=PAUSE / 0x01=UNPAUSE ‖ asset_mask (1B) ‖ reason_code (2B) — signed by the operator quorum key; on-chain so every wallet/indexer sees halt state deterministically. Malformed BRG0 ⇒ bridge-layer no-op (token layer unaffected).

**MINT state machine (per deposit_id):** `DEPOSIT_SEEN` (watcher sees tx paying a vault address; BTC deposits pay a per-user taproot address tweaked from the FROST vault key with H(user's Bloch claim address) — the deposit address itself binds WHICH Bloch address may receive the mint, killing misattribution/front-running; ETH/USDT deposits call a thin deposit-router contract that emits `Deposit(blochAddr, amount)` into the Safe) → `SOURCE_FINAL` (BTC: value-scaled conf table met; ETH/USDT: containing block ≤ finalized checkpoint) → policy engine checks epoch caps, breaker state, deposit_id unused → `MINT_SIGNED` (M-of-N co-sign ONE canonical Bloch tx: inputs = deterministically-selected treasury colored outpoints; outputs: [0] TKV0 TRANSFER envelope assigning (user_vout, amount) and (treasury_change_vout, remainder) — remainder MUST be explicitly assigned, R4 burns unassigned color; [1] user's zero-value colored output; [2] treasury change colored output; [3] BRG0 MINT-ATTEST) → `MINTED` (tx in a Bloch block; TKV0 indexer confirms user credited) → `BLOCH_FINAL` (depth ≥ F). Only at BLOCH_FINAL does the frontend show the balance as spendable-against; before that it is displayed "minting — not final". 

**Bloch reorg interaction (rewind-then-replay × in-flight ops):** the bridge journal is keyed to the same per-height block hashes as the TKV0 indexer; a hash mismatch triggers the shared rewind: truncate bridge events above the fork point, restore snapshot, replay the new branch. Mints that fall out of the chain revert `MINTED → MINT_SIGNED`; recovery is **rebroadcast of the byte-identical canonical tx** — never construct a second distinct mint for the same deposit_id unless the first is provably conflicted (a DIFFERENT final tx spent its treasury input), which itself requires quorum review because it indicates operator-key misuse. This is what prevents mint-replay double-credit: two different mint txs for one deposit can't both survive because they'd spend from the same deterministic treasury outpoint chain, and policy forbids re-selection. Burns that fall out revert to `BURN_SEEN` and their redemption-queue timers reset automatically (timers are defined in terms of final depth, not wall clock). Any reorg of depth ≥ r_halt (v1: r_halt = k, i.e. 4 today) additionally fires the circuit breaker.

**BURN → REDEMPTION queue:** user builds one tx: spends their wBTC outpoints; output [0] TKV0 TRANSFER assigning the redeemed amount to a treasury-address output (and explicit change to self); output [n] BRG0 REDEEM-REQUEST with destination address. The bridge derives the credited amount from TKV0 indexer STATE (never from raw envelope parsing — R2/R4 edge cases like over-assignment make the raw envelope a no-op, and honoring it would release against nothing). States: `BURN_SEEN` → `BURN_FINAL` (depth ≥ F on Bloch) → `QUEUED` (FIFO per asset; delay window T_redeem = F blocks already elapsed + a wall-clock hold: 1h for small, 24h for amounts > 10% of epoch cap — the hold exists for fraud/anomaly monitoring and PoR reconciliation before irreversible native release) → `RELEASE_SIGNED` (M-of-N FROST sig for BTC / Safe execution for ETH-USDT; native-chain fee deducted per min_fee_ack) → `RELEASED` (source-chain confirmed) → `CLOSED`. Per-epoch release caps mirror mint caps. If a queued redemption's burn is reorged away before release, it silently reverts — by construction nothing native has moved yet.

**Rate limits (policy engine, published constants):** per-epoch (144 Bloch blocks) mint cap and release cap per asset; per-tx max; global TVL cap = ISSUE supply, ramped by issuing successor token_ids only as §0 gates clear (testnet: all caps nominal, value zero). **Circuit breaker triggers:** (a) Bloch reorg depth ≥ r_halt; (b) any indexer-derived `circulating > vault_reserves`; (c) source anomaly (BTC reorg ≥ 2 blocks touching a vault address; ETH finality stall > 4 epochs); (d) manual M-of-N halt; (e) cap breach or deposit_id reuse attempt. Halt = no new mint signatures, redemption releases frozen (queue keeps accepting burns), BRG0 CONTROL PAUSE beacon broadcast; resume requires M-of-N UNPAUSE plus a full event-log replay reconciling against fresh TKV0 indexer state.

**Tradeoffs.** **Treasury model vs TKV1 open-mint:** treasury needs zero standard changes and caps supply cryptographically, but the cap is permanent (raising it = new token_id + disclosed migration) and treasury-held balance is "mintable by operator" — indistinguishable on-chain from circulating except by knowing the treasury address, so the address set must be published and pinned. **Literal color-burn vs transfer-to-treasury for redemption:** literal burn is more visibly irreversible but permanently destroys mint capacity and cannot carry the redeem-to address cleanly; transfer-to-treasury preserves capacity but means a "burn" is only as final as the operator's promise not to re-mint it without a matching deposit — mitigated by PoR (detection, not prevention). **Safe multisig vs threshold-ECDSA for ETH:** Safe is audited, transparent, and simple, but puts the signer set and policy on public display and costs gas per action; CGGMP21 hides the signer set and looks like an EOA but is a large, riskier cryptographic build — v1 takes Safe. **Finalized-only ETH ingestion:** ~13 min minimum deposit latency vs eliminating probabilistic-reorg risk entirely — taken. **Value-scaled BTC confs:** large deposits wait hours; the alternative (flat 6 confs) leaves big mints economically attackable. **Deterministic canonical mint tx:** removes double-mint-under-reorg but means a stuck tx (e.g., treasury outpoint chain disturbed) requires quorum intervention rather than automatic re-construction — safety over liveness, deliberately. **F sized to worst-case reorg:** long mint/redemption latency on Bloch; the alternative is exactly the §0.1 double-spend — no real-value shortcut exists, hence the mainnet-security gate rather than a smaller F. **wETH at 9 decimals:** sub-gwei truncation (dust to vault buffer) vs u64 arithmetic staying inside TKV0's checked-math guarantees — taken. **FIFO queue + holds:** predictable and fraud-monitorable but no priority fees / instant exit; instant-exit market-makers could be layered later without protocol changes.

**Honest risks & limits.** **Trust model, stated plainly (B1 federated):** the user trusts (1) the M-of-N custodian federation — collusion or compromise of M keys steals the entire vault; proof-of-reserves makes unbacked minting DETECTABLE within one attestation period, never PREVENTABLE; (2) Bloch consensus finality; (3) the source chain's finality; (4) for wUSDT, ADDITIONALLY Tether Ltd. **wUSDT is double-custodial and cannot be trust-minimized**: Tether can blacklist the vault address itself, freezing the backing for ALL wUSDT holders simultaneously — a concentrated freeze risk strictly worse than holding USDT directly; response to a freeze (pro-rata haircut vs legal recovery) must be disclosed in advance. **The reorg double-spend is the central risk and today it is UNSOLVED on Bloch:** the chain runs the relaxed k=4 regime — trivially forgeable, low-hashrate, 51%-attackable, unaudited. A Bloch reorg deeper than F after a native release re-credits the attacker's wBTC while they keep the BTC (§0.1 attack, redemption side) — F, the delay windows, and the breaker only shrink the window; the actual fix is checkpoint finality + k=8 + WAN hashrate, which is why **no real asset may be bridged before the §0 gates**; until then everything is testnet zero-value tokens proving the mechanics. **Source-side residual risk:** the BTC conf table is probabilistic — a deposit reorged away AFTER a mint leaves supply unbacked; residual probability is quantified in the published policy and absorbed by an over-reserve buffer (target ≥ 105% reserves), which is a disclosed operator cost, not magic. ETH finality reversal (mass slashing) is accepted as out-of-model. **Off-consensus enforcement gap:** TKV0 indexers observe, they don't enforce — the invariant lives in the operator quorum's policy engine, not in consensus; a covenant (E1) or validity-proven L2 (E2) vault is the eventual trust-minimization path and this design is explicitly NOT that. **Operational:** custodian key ceremonies, FROST resharing on membership change, and the Bloch treasury multisig scheme are unbuilt and unaudited; bridges are the single most-exploited construct in crypto (multi-billion-dollar losses: Ronin, Wormhole, Nomad) — assume adversaries, and assume this design has bugs until third-party audit. **Legal:** custodial bridging is likely money transmission; hard gate, unresolved, not legal advice. **Liveness:** M-of-N going offline freezes both mints and redemptions — users' native assets are locked until quorum recovers; disclosed on-screen.

**Open questions.** (1) Bloch treasury M-of-N mechanics: what multisig/aggregate-signature construction does Bloch script actually support for the operator key, and is a PQ scheme (per the Postern PQ wallet) required for the treasury from day one? (2) Exact F: how the checkpoint-finality design parameterizes the horizon (fixed depth vs checkpoint-interval multiple) — F cannot be finalized before that spec exists. (3) TKV1 open-mint extension (issuer-key-gated MINT op with per-token authority) vs permanent treasury model — revisit only if the community wants it on the neutral rail; default is no. (4) Consortium composition: does Postern operate solo initially (single-org M-of-N = weaker than it looks — disclose) or bootstrap independent custodians before any real value? Key-ceremony and resharing procedure spec. (5) Supply-cap ramp mechanics: successor token_id migration UX (swap window? both trade on the DEX?) when raising a cap. (6) BTC B2 (SPV light-client on Bloch) as a later deposit-proof upgrade removing custodian say-so on mints (release still needs the federation) — feasibility and where SPV verification runs (covenant vs L2 vs off-chain quorum). (7) Tether-freeze contingency policy: pro-rata haircut vs socialized buffer vs suspension — must be written and published before any wUSDT mint. (8) Fee model for bridge operations (mint/redeem fees as fiat-equivalent utility revenue, never touching BLCH) and whether fees sit inside min_fee_ack or separately. (9) Insurance/over-reserve buffer sizing methodology and who capitalizes it. (10) Whether the redemption queue needs anti-censorship guarantees (operator can stall specific users today — disclose or mitigate via forced-redemption covenant later). (11) Per-jurisdiction legal analysis (money transmission, sanctions screening on redemption destinations) — hard gate. (12) Atomic-swap HTLC (B3) BTC path shipping BEFORE this custody bridge, per the design doc's own recommendation — does its existence change wBTC's launch priority at all?

## 5. Bloch Bridge — Security, Monitoring, Compliance & the Hard Gates (operational-defense and governance layer). This is the layer that decides WHETHER and WHEN the bridge may hold value, watches it once it does, and forces honesty into every screen. It is an OWNED Postern product/consortium function by the project's own rule (it has operators, pause keys, and legal exposure); it is designed now, built later, and the bridge it guards is a separate optional module the DEX ships without. Design-only: nothing here is built, audited, or safe, and every artifact below says so.

**Architecture.** FIVE PLANES, fail-closed by construction.

(P1) GATE REGISTRY — the §0 hard gates as machine-readable launch blockers. A signed artifact `bridge-gates.json` (Ed25519/minisign-signed, published at posternlabs.com and mirrored in-repo under docs/specs/) with one record per gate: {id, title, owner, status: BLOCKED|IN_PROGRESS|CLEARED, evidence: [sha256-pinned URLs], cleared_by: [signatures], cleared_at}. The bridge deployment pipeline and the bridge daemons themselves read this file at startup and at a 10-minute poll: any gate != CLEARED (or signature/staleness failure) hard-disables all mainnet value paths — mints and deposits refuse; redemptions/burns remain enabled (users can always exit; only entry is gated). Gates:
- G1 Bloch chain security. Owner: Bloch consensus maintainer. Evidence: k=8 progressive-ramp activation height reached and held ≥30 days without stall (the earlier k=8 attempt at block 213,000 was reverted for stalling the chain — the ramp with matched difficulty reduction is the fix); live WAN hashrate above a published floor with ≥N independent miners (floor set from the attack-cost model, published); checkpoint reorg-depth protection active with a stored depth D_cp, and the bridge's own mint-recognition depth set ≥ D_cp. Until G1: k=4, trivially forgeable, 51%-attackable — zero value, period.
- G2 Third-party audit. Owner: Postern eng lead. Evidence: contracted external audit report covering the bridge daemons, the covenant/L2 enforcement logic (whichever substrate, E1 or E2), the FROST/threshold-ECDSA ceremony code, and this watchtower — findings triaged, criticals fixed, re-tested; report hash pinned in the registry. Bridges are the single most-exploited construct in crypto (billions lost); no exceptions.
- G3 Legal review. Owner: Postern counsel (incorporation itself still pending — that is a sub-blocker). Evidence: written money-transmission analysis for the custodial (B1) path per launch jurisdiction (in the US: FinCEN MSB registration question + state MTL survey; in the EU: MiCA CASP scoping; plus securities/commodities posture for wrapped assets and LP fees per jurisdiction), stored privately with a public summary. Explicitly NOT legal advice, and the registry says so.
- G4 Trust-model honesty. Owner: product/frontend lead. Evidence: automated CI assertion (see P5) that every bridge-touching screen renders the correct trust badge and the verbatim USDT double-custody disclosure; a signed screenshot corpus per release is the evidence artifact.
Testnet/zero-value operation is the ONLY mode until all four clear.

(P2) WATCHTOWER — a 24/7 monitoring service: three independent Rust daemons (source-chain watcher, Bloch watcher, invariant engine) exporting Prometheus metrics, Alertmanager routing to PagerDuty/Signal for on-call, plus a public read-only status page. The watchtower source is published (MIT/Apache-2.0) so third parties can run their own against the same public data — Postern's instance is a product; the ability to verify is not.

(P3) CIRCUIT-BREAKER / PAUSE PLANE — asymmetric authority, fail-closed: PAUSE of mints is 1-of-G (any single guardian key, or the watchtower's own automated trigger) so speed beats consensus during an attack; UNPAUSE requires the custodian emergency quorum (the same M-of-N that controls the vault) PLUS a 24-hour public notice window. Redemptions are never paused by a single key — pausing redemptions requires the full M-of-N quorum (freezing user exits is the more dangerous power and is priced accordingly).

(P4) CUSTODY/KEY PLANE (interfaces this layer defends): BTC vault = P2TR output under a FROST threshold-Schnorr key (RFC 9591), M-of-N over N disclosed custodians; ETH/USDT vault = a minimal audited Ethereum contract (Gnosis-Safe-class M-of-N, or an EOA under CGGMP21 threshold-ECDSA — pick one at build time, see choices). Key ceremonies, proactive resharing, and the compromise/defection playbooks live here.

(P5) DISCLOSURE ENGINE — a signed `trust-manifest.json` mapping every asset/path to its trust model (B1 federated-custody / B2 SPV / B3 HTLC), the exact who-do-you-trust sentence, and required verbatim disclosures. The frontend renders badges ONLY from this manifest; a CI job (headless-browser snapshot per screen) fails the release if any bridge screen lacks its badge or the USDT text. This is how G4 is "verified on every screen" mechanically rather than by promise.

**Concrete choices.** Named tech, and why:
- FROST (RFC 9591, Zcash-Foundation `frost-secp256k1` Rust implementation) for the BTC vault: native Schnorr → single P2TR key on-chain (cheap, private, no bare-multisig footprint), t-of-n with distributed key generation and proactive share refresh (key-compromise playbook depends on refresh being cheap).
- CGGMP21 threshold-ECDSA (e.g. the audited `dfns/cggmp21` or Silence-Labs implementations) as the fallback for ETH if an on-chain Safe is not used; RECOMMENDED default for ETH/USDT is a minimal Gnosis-Safe-class M-of-N contract instead, because an on-chain multisig is auditable by anyone from etherscan-class explorers, which strengthens proof-of-reserves (reserve address policy is publicly enforced, not just attested).
- BTC SPV (B2 path, later): bitcoin header chain verification + Merkle inclusion proofs, headers sourced from ≥2 independent bitcoind nodes + electrs; ETH deposits proven against FINALIZED beacon checkpoints only (a consensus light client — Helios-class — is the eventual B2-ETH answer but is explicitly a large build; v1 ETH is B1 with the watchtower reading Lighthouse/reth).
- HTLC atomic swaps (B3) for BTC precede all custody: SHA-256 hashlock + CLTV timelock on the BTC side, matching hashlock/timelock covenant or L2 contract on the Bloch side — no custody, nothing for this layer to guard except honest UX (timeout-refund education), which is why it can ship before G2/G3 clear in full.
- TKV0 (crates/bloch-tokens) for the wrapped token itself — with one hard spec consequence: TKV0 v0 is MINT-CLOSED (ISSUE flags bit 0 MUST be 1, supply fixed at issuance, R3 assigns full supply to output 0). So wrapped tokens CANNOT be minted on demand under raw TKV0 v0. Two spec-level options, both recorded: (a) pre-issue max supply (e.g. 21M×10^8 base units for wBTC) to a covenant/L2-controlled treasury outpoint; "minting" is a TRANSFER out of treasury, "burning" is a TRANSFER back (plus R2's burn-by-malformed as an irreversible-destroy option); circulating = supply − treasury balance, which every indexer can derive; or (b) a TKV1/covenant-native mintable extension. Recommend (a): zero standard change, and the treasury outpoint under covenant/L2 control is exactly the enforcement point E1/E2 already provides.
- Monitoring stack: Rust daemons (same zero-dep discipline as bloch-tokens where possible), Prometheus + Alertmanager + Grafana, PagerDuty for paging, a public status page (static, signed JSON feed — no third-party SaaS in the trust path). Reorg detection on Bloch reuses the TKV0 indexer's per-height block-hash journal technique (SPEC.md R7: hash mismatch at an indexed height ⇒ rewind-then-replay), promoted from recovery mechanism to ALERT source.
- Attestation signing: minisign/Ed25519 operator keys, published in-repo and on the site; third-party attestations from a named accounting/audit firm (selection is an open question) on a fixed calendar.

**Flows / on-chain formats.** DEPOSIT→MINT (B1 custodial, the flow this layer polices):
1. User obtains a deposit address derived from the vault key (BTC: P2TR under the FROST group key with a per-deposit tweak committing to the user's Bloch destination address — the tweak binds destination to deposit so custodians cannot redirect; ETH/USDT: deposit to the Safe with the Bloch destination in calldata / a registry event).
2. Source-chain watcher observes the deposit and starts the FINALITY CLOCK — dual finality, both sides, non-negotiable: BTC ≥ 6 confirmations (config `btc_conf_min`, raised under fork alerts); ETH/USDT: the deposit block must be FINALIZED by the beacon chain (2 epochs, ~13 min; never mere confirmations — USDT is an ERC-20, same rule). Only then do custodians sign.
3. Each custodian node independently verifies the deposit (own full node — bitcoind / reth+Lighthouse; no shared RPC) and co-signs a MintAuthorization: {v:1, asset, source_chain, source_txid, vout|log_index, amount_base_units, dest_bloch_addr, source_height, source_finality_evidence_hash, expiry_height} — canonical serialization, FROST/M-of-N signature over its hash.
4. The bridge operator submits the Bloch transaction: TKV0 TRANSFER (op 0x02, token_id = the wrapped token's issuance txid) moving `amount` from the treasury outpoint to the user's output, with change explicitly re-assigned to treasury (TKV0 R4 burns unlisted remainder — the treasury change assignment is mandatory and the watchtower alarms if a mint tx omits it). The covenant (E1) or L2 validity proof (E2) enforces that treasury spends only occur under a valid MintAuthorization.
5. The mint is RECOGNIZED (shown as final, counted in supply) only at Bloch depth ≥ `bloch_mint_depth` = max(2·k, checkpoint depth D_cp) — under today's k=4 that is meaningless (hence G1); the parameter exists so the design is honest about needing it.

BURN→REDEEM: user sends a TKV0 TRANSFER of wrapped tokens back to the treasury outpoint accompanied by a RedeemIntent envelope/L2 message {asset, amount, dest_source_chain_addr}. The redemption executes only after (a) the burn is `bloch_burn_depth` deep (same depth rule — a Bloch reorg must not be able to erase a burn AFTER the BTC has left the vault; this is the reverse double-spend) and (b) a `redeem_delay` window (24 h at launch) during which the watchtower can flag anomalies and a guardian can pause. Then M-of-N sign the source-chain release (FROST-signed BTC tx / Safe execution).

REORG HANDLING (the central problem, both directions): Source-chain reorg after mint — if the deposit tx vanishes below its recorded height, the invariant engine sees reserves < supply and auto-pauses ALL mints for that asset within one polling interval; the minted wUSDT/wBTC is now unbacked and the incident process (SEV1) governs socialization/clawback per the published policy — this is exactly why conf thresholds are set from reorg cost, not UX. Bloch reorg after mint — the mint TRANSFER can be replayed on the new branch (same signed authorization, replay-protected by source_txid uniqueness: one deposit, one authorization, ever); the danger case (user swaps the wrapped tokens before the reorg, then the mint is re-orged and replayed to a different history) is bounded by `bloch_mint_depth` ≥ D_cp — checkpoint-finality depth is the actual security floor, which is why G1 lists it. Bloch reorg after redeem — bounded by `bloch_burn_depth` before any native asset leaves the vault.

INVARIANT WATCHER (continuous): per asset, every Bloch block AND every source-chain block, compute assert: `circulating_wrapped ≤ reserves_confirmed − pending_redemptions`, where circulating_wrapped = issued_supply − treasury_balance (derivable by ANY TKV0 indexer — proof-of-liabilities is public by construction, a genuine advantage of doing this on a transparent UTXO token) and reserves_confirmed = vault UTXO set / Safe balance at finalized heights. Violation ⇒ automatic mint pause + SEV1 page. MINT-RATE ANOMALY: EWMA baseline per asset plus hard velocity caps — per-transaction cap, rolling 1-hour cap, rolling 24-hour cap; a breach queues the mint for manual custodian review instead of auto-signing (defense against the classic bridge exploit shape: one bug, infinite mint, drained in minutes).

PROOF-OF-RESERVES cadence: (tier 1, continuous) the watchtower publishes, every 10 minutes, a signed JSON snapshot {timestamp, asset, vault_utxos/safe_addr, reserves, circulating, source_height, bloch_height, sig} to the status page — anyone can recompute both sides from public chains; (tier 2, daily) an operator attestation signed by the vault keys themselves (a FROST signature over the snapshot proves current control of the reserve key, not just past ownership); (tier 3, quarterly) a third-party attestation by a named firm confirming key control, no double-pledging, and procedure compliance, report hash pinned in the gate registry. wUSDT PoR additionally links Tether's own reserve attestations and says plainly that Postern cannot attest Tether's reserves.

INCIDENT RESPONSE runbook (spec level): SEV1 = invariant violation, suspected key compromise, unbacked supply — immediate auto/guardian pause of mints, custodian conference within 1 h, user notice on status page within 4 h, no unpause without quorum + 24 h notice, public post-mortem within 7 days; SEV2 = source-chain finality stall (beacon >3 epochs unfinalized ⇒ pause ETH/USDT mints automatically), deep fork alerts (bitcoind getchaintips fork ≥2 blocks ⇒ raise btc_conf_min; Bloch reorg ≥2 ⇒ alert, ≥k/2 ⇒ pause mints), signer unavailability; SEV3 = monitoring degradation, attestation lateness. KEY-COMPROMISE playbook: single-share compromise ⇒ proactive resharing (FROST refresh / CGGMP21 key-refresh) within 24 h and a precautionary sweep of the vault to the refreshed key; suspected ≥M compromise ⇒ treat reserves as contested: immediate pause, emergency sweep race to a pre-established cold escrow key, full public disclosure — no pretending. SIGNER-DEFECTION playbook: liveness SLO per custodian (signing round participation ≥99% monthly); if available signers < M for >72 h, redemptions are stalled — escalation is a pre-signed, time-locked recovery path (BTC: CSV-encumbered fallback spend to a 2-of-3 cold escrow after 90 days, published in advance so users know the terminal backstop) and public identification of the defecting custodians; persistent defector ⇒ quorum-approved resharing that excludes them.

USDT DOUBLE-CUSTODY DISCLOSURE — mandatory verbatim text, rendered from the trust-manifest on the deposit screen, redeem screen, token detail page, and docs, asserted by G4 CI: "wUSDT users trust BOTH the bridge custodians AND Tether. Tether can freeze or blacklist the underlying USDT or fail to honor redemption, making wUSDT unbacked even if the bridge custodians are honest. This path cannot be trust-minimized." No screen ships without it.

**Tradeoffs.** 1. Fail-closed 1-of-G pause vs censorship: a single guardian can freeze mints (and the automated watcher can too) — that is a griefing and legal-seizure vector, accepted deliberately because in every historical bridge exploit the minutes mattered; the compensating controls are that redemptions need full quorum to pause (exits stay open) and unpause needs quorum + public notice. 2. Long finality windows (ETH finalized-only ≈13 min, BTC 6+ conf, Bloch checkpoint-depth recognition) vs UX: users will compare unfavorably to fast bridges; fast bridges are the ones that got drained — the design refuses to trade the invariant for latency. 3. Velocity caps bound the worst-case bug loss but also cap legitimate throughput and add a manual-review centralization point. 4. Pre-issued-max-supply TKV0 treasury (option a) keeps the token standard untouched and makes circulating supply publicly derivable, but concentrates the entire wrapped supply behind one covenant/L2-controlled outpoint — the enforcement substrate (E1/E2) becomes the single most security-critical code in the system, which is why G2's audit scope names it explicitly. 5. Gnosis-Safe-class on-chain multisig for ETH is publicly auditable (better PoR) but doxxes operational patterns and costs gas; threshold-ECDSA EOA is cheaper/quieter but PoR degrades to attestation-only — recommend the Safe and eat the cost. 6. Publishing the watchtower source and all thresholds/playbooks tells attackers the tripwires; secrecy was never real protection for a system whose state is public, and the honesty rule wins. 7. The CSV time-locked recovery path prevents permanent fund loss on signer defection but is itself a theft path if the cold escrow is compromised — it trades one terminal risk for a smaller, disclosed one. 8. Third-party attestations cost real money quarterly for a system that may hold little value early; the alternative (self-attestation only) fails the no-overclaim rule for a custodial product.

**Honest risks & limits.** TRUST MODEL, stated flat: the B1 bridge is a trusted, operated, custodial product. Users trust: (i) M-of-N custodians not to collude — M colluding signers steal the entire reserve, full stop; proof-of-reserves detects theft after the fact, it does not prevent it; (ii) the pause guardians not to abuse freeze power and not to be legally compelled into it; (iii) the covenant/L2 substrate's correctness (unaudited until G2) — a bug there is an infinite-mint bug; (iv) Postern's operational competence (watchtower uptime, ceremony hygiene); and for wUSDT additionally (v) Tether — freeze/blacklist/redemption risk that no amount of bridge engineering removes; wUSDT is inherently double-custodial and is disclosed as such verbatim. B2 (SPV) reduces deposit trust to source-chain PoW/consensus math but redemption still needs a signer set; B3 (HTLC) alone is custody-free and is the only path honest to offer real BTC before the gates clear. REORG/FINALITY DOUBLE-SPEND is the central risk and today it is fatal: Bloch runs k=4, trivially forgeable, low-hashrate, 51%-attackable, unaudited — an attacker can mint against a deposit and reorg the deposit away (source side) or reorg/replay Bloch history around a mint or burn (Bloch side); the k=8 ramp already failed once (block 213,000 revert) so G1 is genuinely uncleared, and the mitigation parameters (bloch_mint_depth, D_cp) are only as good as the chain's real hashrate. Checkpoint depth caps reorgs only for nodes that share the checkpoint. RESIDUAL even after all gates: a >M key compromise or collusion event loses funds with no recourse; a source-chain deep reorg beyond the conf threshold (theoretically possible on BTC, practically possible on smaller chains) leaves unbacked supply; the watchtower itself can be DoS'd or fed eclipse-attacked chain views (mitigated, not eliminated, by multiple independent nodes per chain); PoR proves existence and control at time t, not the absence of undisclosed liens; legal risk is live — the custodial bridge is likely money transmission in major jurisdictions, Postern is not yet incorporated, none of this document is legal advice, and G3 can lawfully conclude "do not launch B1 at all." Until every gate clears, this entire layer supervises testnet, zero-value assets only, and every screen says so.

**Open questions.** 1. Guardian set composition and size G: Postern-only at first (honest but centralized) vs day-one consortium — and whether guardians overlap with custodians (separation is cleaner; overlap is operationally simpler). 2. Concrete M-of-N (5-of-7? 4-of-6?) and custodian identity/jurisdiction diversity — also G3-entangled (custodian = money transmitter?). 3. Whether the CSV time-locked recovery backstop is acceptable at all, and its parameters (90 days? who holds cold escrow?). 4. Exact bloch_mint_depth once k=8 ramp and checkpoint depth D_cp are final — needs the attack-cost model from live WAN hashrate, not a guess. 5. Unbacked-supply socialization policy after a source-chain reorg (pro-rata haircut vs operator makes whole vs insurance) — must be published BEFORE launch, not improvised during a SEV1. 6. Third-party attestation firm selection and whether quarterly is sufficient cadence at meaningful TVL. 7. Choice pinned at build: Safe-contract vs CGGMP21-EOA for the ETH/USDT vault. 8. Whether the watchtower should be run redundantly by non-Postern parties from day one (source is public; who actually runs instances?). 9. TKV0 option (a) pre-issued treasury vs a TKV1 mintable extension — coordinate with the tokens crate owner before Phase 1. 10. Whether the HTLC (B3) BTC path fully ships first as the flagship trust-minimized story, making B1 custody a later, clearly-worse-trust alternative rather than the default. 11. Incident-comms legal review: what a money-transmitter may say publicly mid-incident varies by jurisdiction. 12. Bug-bounty scope and size once G2's audit lands (a bounty is not in the gates but probably should be evidence under G2).

## Reviewer verdicts (soundness + security/honesty)

- **Soundness [needs-work]** — B2 — SPV / Light-Client Deposit Verification for the Bloch B: Core mechanics are correct and buildable with the named tech (BTC Core-compatible header verification incl. the retarget off-by-one and chainwork=floor(2^256/(target+1)) formula, MTP timestamp rules, MMR for pruned long-term state, FROST/BIP-340 for taproot key-path signing, BIP-341 per-deposit tweaking, value-tiered depth + work-not-height acceptance). Trust-model disclosure (SPV-mint/federated-redeem split, Bloch-reorg hard gate at k=4, TKV0 mint-closed conflict, signer-collateral denomination) is honest and non-hand-wavy, and the design correctly cites real prior art (BTC-Relay, Interlay/XCLAIM, tBTC v2) rather than inventing novel crypto. That said, four concrete pieces are missing or under-specified: (1) SEGWIT/MERKLE-DUPLICATION BUG — M3's Merkle-fold verification (txid up merkle_branch to merkle_root) doesn't guard against the CVE-2012-2459 duplicate-transaction/Merkle-malleability class that historically bit BTC-Relay itself; nothing in the spec rejects proofs built over a tree with an odd-tx-count duplication or checks that sibling hash pairs aren't identical. (2) REDEMPTION LIVENESS/GRIEFING — the design bonds signers against theft/collusion but never addresses signer UNAVAILABILITY: after a user burns wBTC (M6), if fewer than t of the disclosed FROST signers are online/responsive, there is no stated timeout, escalation, wallet-rotation, or backfill mechanism (unlike tBTC v2's wallet-rotation and ROAST-style robust signing, which this design cites tBTC as prior art for but doesn't actually adopt for the liveness dimension) — a burned-but-unredeemed user has no recourse path described. (3) VALIDITY-PROOF COST OF SHA256-HEAVY VERIFICATION — embedding Bitcoin header verification (double-SHA256 per 80-byte header, retarget arithmetic, MMR updates, potentially large batch catch-up submissions) inside the E2 L2's proven state-transition function is asserted as "covered by the L2 validity proof" but no proving-cost/throughput analysis is given; SHA256 is not cheap inside typical SNARK/STARK circuits, and this is flagged as a cost concern for the E1 covenant path but conspicuously not costed for the recommended E2 path either. (4) FROST-over-tweaked-taproot-key signing ceremony robustness (nonce-reuse hazards, multi-round coordination among possibly-offline signers) is asserted but not named as a specific sub-protocol (e.g., ROAST) despite being directly relevant to gap (2). None of these are fatal to the architecture — all are patchable within the stated design (duplicate-tx check is a one-line fix; liveness needs a documented timeout/backup-signer procedure; proving cost needs benchmarking before Phase 1) — but they are exactly the kind of concrete, well-precedented bridge-exploit vectors (Merkle malleability, threshold-signer liveness) that should be closed before this leaves "design only."

- **Soundness [needs-work]** — Bloch Bridge — Security, Monitoring, Compliance & the Hard G: Overall the threat model, named crypto (FROST RFC 9591, CGGMP21, Gnosis-Safe-class multisig, minisign/Ed25519), and monitoring stack (Rust daemons, Prometheus/Alertmanager/PagerDuty) are real, correctly-matched-to-purpose, and the doc is unusually honest about deferring hard problems (Ethereum light client explicitly called "a large build," B2/SPV explicitly "later," E1/E2 covenant substrate explicitly out of scope as a separate module). That said, several concrete gaps remain:

1. HTLC timelock symmetry (B3) is under-specified/likely wrong: the doc says BTC-side CLTV and the Bloch-side hashlock/timelock should "match." Real atomic-swap safety requires an *offset*, not equal, timelock — the responder's (Bloch-side) timelock must expire strictly before the initiator's (BTC-side) so the last mover cannot be griefed or double-claim. As written this is either imprecise language or a genuine protocol flaw; needs an explicit relative-delta parameter (e.g., Δ blocks) before this is buildable.

2. B3/HTLC reorg risk is dismissed ("nothing for this layer to guard except honest UX") despite the rest of the document treating Bloch's k=4/reorg-ability as "the central problem." If Bloch can reorg deeper than the HTLC's own timelock margin, a claim revealing the preimage on Bloch could be undone and later double-spent/refunded — the same class of risk formalized elsewhere via bloch_mint_depth/D_cp is not applied here. This is an inconsistency, not just a residual risk already priced in.

3. The covenant/L2 enforcement (E1/E2) is named as "the single most security-critical code in the system" in the tradeoffs, yet its actual mechanism — how a covenant or L2 verifies an M-of-N/FROST signature over a MintAuthorization on-chain, and at what verification cost/script complexity — is entirely undefined here. Deferring it to a separate module is a legitimate scoping choice, but the tradeoff analysis treats the allocation of risk to that layer as settled without any feasibility check that Bloch's actual script/covenant capability can do this at all.

4. Threshold-sig liveness is addressed for steady-state signing (99% SLO, 72h stall → CSV fallback) but not for DKG/proactive-resharing ceremonies themselves, which also need t-of-n liveness; a partial outage during a scheduled reshare (e.g. post-compromise) isn't covered by the signer-defection playbook as written.

5. The 10-minute gate-registry poll interval leaves a window where a newly-failed gate (e.g., an in-flight G1 stall or a just-discovered audit-critical bug) doesn't hard-disable mints for up to 10 minutes; the invariant engine's continuous checks are a partial compensating control but this isn't stated as intentional defense-in-depth.

None of these invalidate the design's core soundness — the fail-closed gate registry, dual-finality clock, invariant/velocity-cap engine, asymmetric pause/unpause authority, and TKV0 pre-issued-treasury mechanism for a mint-closed token standard are all coherent and buildable with the named tools. The gaps are concrete, fixable spec omissions (mainly around HTLC timelock ordering and B3's reorg-depth treatment) rather than fundamental flaws.

- **Soundness [needs-work]** — B1 — Trust-Model Architecture & Federated Custody Vault: Overall direction is sound and the crypto primitives are real, matched to their job, and buildable (FROST/RFC 9591 for BTC P2TR key-path spends via frost-secp256k1, CGGMP21 for the ETH/USDT TSS EOA with identifiable aborts, HSM+DKG key lifecycle, TKV0 pre-minted-treasury mint/burn accounting). The honesty discipline is unusually strong — reorg/finality double-spend is correctly identified as the central unsolved problem with no finite F_bloch safe against a 51% attacker on today's k=4 chain, USDT double-custody is stated plainly, PoR limits (no proof of non-encumbrance/solvency) are acknowledged, and real value is correctly hard-gated behind the §0 security ramp. No SPV/HTLC claims are made that don't apply — B1 explicitly declines to build a Bloch-side light client and substitutes custodian attestation instead, which is a disclosed trust choice, not hand-waving.

That said, two concrete technical gaps should block implementation sign-off, not just be filed as open questions:

1. Internal inconsistency on the load-bearing mechanism for minting: the "flows" section asserts as working machinery that "the treasury outpoint itself is guarded by the federation's Bloch-side threshold key (FROST over Bloch's signature scheme), so minting also requires M-of-N" — for all three assets (wBTC/wETH/wUSDT), since all share the single TKV0 treasury-outpoint model. But "openQuestions" simultaneously flags this as unconfirmed and potentially infeasible: "FROST assumes Schnorr/secp256k1 — confirm Bloch's transaction signature scheme supports it... if Bloch signatures are PQ/non-Schnorr, the treasury needs a different threshold scheme... this is a blocking spec dependency." A design document should not describe a mechanism as functioning in its core flow spec while flagging in the same breath that it may not be technically possible given the target chain's actual signature scheme. This is the single highest-impact unresolved feasibility question in the whole component — if Bloch is PQ/non-Schnorr (which the doc itself notes the ecosystem's PQ-wallet direction suggests), the entire mint/burn mechanism as specified needs a redesign (script-level M-of-N or a different threshold scheme), which doesn't exist yet.

2. Mint throughput/liveness bottleneck from the single-treasury-outpoint model is unanalyzed: each MINT tx consumes the current treasury outpoint and produces a new one as change, meaning every mint across all users for a given asset must be strictly serialized, each requiring a fresh 6-of-9 Bloch-side threshold-signing ceremony (assuming gap #1 is resolved) before the next mint can even be constructed. Under concurrent deposit volume this is a real latency/throughput ceiling, and chaining unconfirmed treasury outputs to keep up introduces its own reorg exposure on Bloch (the exact class of risk §0/Attack-A already worries about). Neither queuing strategy, parallelization, nor confirmation-wait tradeoffs for the treasury chain are discussed anywhere in the design.

Minor/lower-severity: (a) "reproducibly-built, hash-pinned signer software" is asserted across signers using three distinct HSM vendor classes (YubiHSM2/Nitrokey/cloud-HSM), which in practice likely need vendor-specific integration code — tension with a single hash-pinned build that the doc doesn't resolve (probably needs per-HSM-class pinned hashes rather than one global hash). (b) ATTEST's vault_utxo_set_merkle_root has no specified leaf format/hash function yet — acceptable since it's explicitly deferred to a golden-byte-vector spec pass in openQuestions, but worth tracking as a pre-implementation blocker alongside gap #1.

The HTLC timeout/griefing and cross-chain light-client-proof-cost concerns named in the review brief don't apply to B1 as scoped (no HTLCs here; no on-chain proof verification is attempted — the design substitutes disclosed custodian attestation instead, which is the honest and correct choice given the trust model it declares). Liveness under threshold-sig quorum loss (N−M+1 offline freezes redemptions) is named as a tradeoff but only at the "some signers go offline" level, not at the "M-of-N ceremony required per mint, at what latency and with what recruitable signer responsiveness SLA" level — connects to gap #2.

- **Soundness [needs-work]** — Wrapped TKV0 Mechanics: Mint/Burn, 1:1 Peg, Redemption Queue: Core mechanics are technically sound and well-grounded: the treasury-as-fixed-pot trick correctly works around TKV0 v0's FLAG_MINT_CLOSED-only ISSUE rule without touching the standard; the peg invariant (vault_reserves ≥ circulating, achieved by credit-before-mint / debit-before-release ordering) is the right primitive; wBTC/wETH/wUSDT decimal choices are checked against u64 overflow with correct arithmetic (gwei-for-ETH math checks out: 1.8e19/1e9 ≈ 1.8e10 ETH cap); FROST-taproot for BTC and Gnosis Safe for ETH/USDT are appropriate, currently-buildable primitives; finalized-checkpoint-only ETH ingestion is the correct conservative choice; value-scaled BTC confirmation tiers are a legitimate defense against large-deposit reorg economics. The design also correctly avoids two of the trap categories named in the brief by construction rather than hand-waving: no HTLCs are used (this is the custodial B1 path, not the B3 atomic-swap path, and it says so), and no SPV light-client trust is attempted under Bloch's reorg-able k=4 chain (explicitly deferred to a future B2 gate) — that's honest scoping, not omission. The single biggest cross-chain risk (a Bloch reorg past F re-crediting an attacker after native release) is explicitly named as UNSOLVED and used as the real gate on shipping real value — this is the correct way to handle an unsolved problem, not glossed over.

Real gaps that need more design work before implementation:
1. Deterministic treasury coin-selection is asserted to prevent double-mint under reorg but is only worked through for a SINGLE deposit_id being reorged and rebroadcast byte-identical. It is not worked through for the CONCURRENT case: if a reorg reorders two in-flight mints (deposit A and deposit B) relative to each other, deposit A's canonical tx may reference a treasury outpoint that deposit B's mint already consumed in the new fork. The doc doesn't specify whether treasury spending is single-threaded/serialized (which would bound mint throughput by Bloch finality depth F — a real liveness/throughput cost never discussed, notable given F could be large under the testnet placeholder) or uses a collision-aware selection+reservation protocol across custodians. This is asserted as solved ("policy forbids re-selection") without the actual algorithm.
2. The ETH/USDT "thin deposit-router contract" that emits Deposit(blochAddr, amount) and forwards to the Safe is new, unaudited custom code sitting directly on the custody path (user funds may transit it before reaching the Safe) — it gets zero technical scrutiny (reentrancy, upgradeability, whether funds transit or the Safe receives directly) despite being a first-class attack surface equivalent in importance to the vault itself.
3. Per-user taproot addresses tweaked from the FROST group key are workable but require tweak-aware FROST signing on every sweep/release (standard with taproot-FROST implementations, but not called out as a build dependency alongside the FROST choice).
4. Two load-bearing items are correctly flagged as open (Bloch treasury multisig construction; exact F) rather than answered — appropriate for a design doc, but they mean the reorg-safety mechanism (F) and the treasury custody scheme are not yet fully specified, so "reorg-safe finality" in the component name is aspirational pending those answers.

None of these are fatal to the architecture, but #1 in particular (concurrent-mint coin selection under reorg) is the one place where the "no second distinct mint can survive" safety claim is under-specified rather than demonstrated.

- **Soundness [needs-work]** — B3 — Atomic Swaps / HTLC (Trustless, Custody-Free v1): Verified against the actual repos (BlochSISPoW-project + bloch-protocol). The Bitcoin-side leg, protocol flow, and honesty framing are solid; the Bloch-side consensus primitive has one concrete, checkable soundness gap the design missed by not grepping far enough.
