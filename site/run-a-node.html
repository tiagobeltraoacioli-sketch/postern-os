Run a mainnet-beta node

Join the Bloch-SIS-PoW mainnet beta.

This page walks you through building and running a node of the ownerless Bloch-SIS-PoW protocol on its mainnet beta — as a relay, or as a solo miner. The network is nascent and unaudited, and its coins carry no value claim. You are helping run and harden experimental post-quantum PoW research, nothing more.

Read before running anything

  • Mainnet beta — a designation, not a security claim. As of node v0.1.0-alpha2 the Module-SIS gate is a difficulty-driven k-ramp: k=4 today, rising 5→6→7→8 as the network's own ASERT difficulty sustains above spaced thresholds, and easing back if hashrate falls — the Bitcoin model. This replaces the fixed k=8 gate, which was choking block production at low hashrate for no security gain (β=q/16 is the trivial regime at any k — raising k adds no cryptographic hardness). The ramp is a structural filter, not a security claim; real security is cumulative SHAKE-256 hashcash work — hashrate × time. Onboarding: a new node can sync from genesis (the historical chain validates under the ramp) or fast-sync from the optional signed snapshot.
  • Very few nodes, low hashrate → 51%-attackable. The software is unaudited: a third-party audit is contracted but not done yet, and the concrete-security analysis and IACR ePrint are still outstanding.
  • Recently patched. An internal security review's fixes are merged into main and deployed to the public demo nodes — a fresh build from this page already includes them (this is separate from, and does not substitute for, the outstanding third-party audit).   • The coin is not a security and not an asset. No token sale, no listing effort, no market-making, no price — no value claim. Disclosed in full: a 17% founder premine (10-year cliff, 40-year vest), structurally passive. Full disclaimer.
  • Run it to evaluate, strengthen, break, and report — not as an investment. Use at your own risk.

Step 1 · Get the source

Clone the protocol repository.

The protocol is not a Postern Labs product and has no official website. It lives in its own ownerless repository — rendered as text on purpose, because the protocol has no official site to link to and this site will not invent one:

gitlab.com/blochsispow-group/BlochSISPoW-project
# Prefix the path above with your git host scheme of choice, then:
git clone <the repository above> bloch
cd bloch

Prerequisites: a Rust toolchain (rustup, stable), plus a C toolchain — clang, cmake, pkg-config — needed by RocksDB, blst, and the PQClean-based crypto crates.

Step 2 · Build

One command, one binary (plus friends).

cargo build --release

Binaries land in target/release/: bloch (the full node), bloch-cli (an RPC client, like bitcoin-cli), and bloch-wallet. Verify the build with cargo test if you like — the suite should pass.

Prefer an appliance? The Postern OS node ISO (x86_64) is now hosted, release-signed, and QEMU-boots on x86_64 (a first hardware boot is still further out) — grab it, with its checksum and signature, from downloads. Building from source, as on this page, remains the strongest verification.

Step 2b · Fast-sync from a snapshot — optional

Optional: bootstrap at the tip instead of syncing from genesis.

Under the difficulty-driven k-ramp (node v0.1.0-alpha2), a fresh node can sync from genesis again — the historical chain validates under the ramp's k=4. If you'd rather skip the initial block download, a signed snapshot of a current node's chain state (the pruned RocksDB at the tip) gets you to the tip in one pass. A convenience, not a requirement.

The older snapshot is a dead end — use the one below

The previously published bloch-db-snapshot.tar.gz ends at height 394,361. Peers have since pruned block bodies below ~394,913, so a node restored from it asks for the ~550 blocks in between, no peer has them, and it stalls forever with a healthy-looking log. This snapshot (height 408,482) starts above that gap and syncs normally.

Why this happens: pruning deletes block bodies below tip − 10,000. A published snapshot must be refreshed before the network prunes past the height it ends at, or the chain from snapshot to tip breaks silently. That is a real failure this network hit, not a hypothetical.

# 1) download the signed snapshot + checksums, verify, restore, then start
curl -O https://pub-dca67fd26bfb4a6b98115e596095ecd3.r2.dev/bloch-db-snapshot-408482.tar.gz
curl -O https://pub-dca67fd26bfb4a6b98115e596095ecd3.r2.dev/SHA256SUMS-408482
sha256sum -c SHA256SUMS-408482     # must print: bloch-db-snapshot-408482.tar.gz: OK

mkdir -p ./bloch-data
tar xzf bloch-db-snapshot-408482.tar.gz -C ./bloch-data   # restores ./bloch-data/db

# 2) start — it boots at the snapshot's tip and syncs the small gap forward
./target/release/bloch --data-dir ./bloch-data \
  --listen /ip4/0.0.0.0/tcp/16110 \
  --peer /ip4/45.32.154.137/tcp/16110

The snapshot excludes node identity, so your node generates its own. This is a trust-the-operator bootstrap — you trust the snapshot's chain instead of verifying it from genesis, an honest disclosed tradeoff you can now avoid entirely by syncing from genesis. Always verify the SHA-256 and signature before trusting it. Add --mine once it has caught up to mine on the tip. Published to downloads.

Step 3 · Run a relay node

A non-mining node that validates and relays.

./target/release/bloch \
  --data-dir ./bloch-data \
  --listen /ip4/0.0.0.0/tcp/16110 \
  --rpc-bind 127.0.0.1 --rpc-port 16210

Network selection: the current build connects to the live network — the chain designated mainnet beta — directly with the command above. (Older builds needed a historical --testnet flag to select the live chain; if your build's --help shows a network flag, match whatever network your bootstrap peer uses.) Network selection does not change the PoW regime: the difficulty-driven k-ramp (k=4 today, rising with hashrate) applies either way.

The flags shown are also the defaults, spelled out so you can change them deliberately:

--data-dir
Where the chain lives: RocksDB block/UTXO storage, the persisted known-peers list, and node identity keys. Default ./bloch-data, relative to where you launched the node. Delete it to start fresh.
--listen
The libp2p P2P multiaddr your node accepts peers on. Default /ip4/0.0.0.0/tcp/16110. This is the address other testers will use to bootstrap from you.
--max-peers
Maximum inbound peer connections. Default 50. Raise it on a bootstrap/hub node (e.g. --max-peers 500) so newcomers aren't dropped once it fills up — a leaf node can leave it at the default. Non-consensus operator knob (see the peering release notes).
--rpc-bind / --rpc-port
JSON-RPC over HTTP. Defaults to 127.0.0.1:16210 — local only, on purpose. Exposing RPC publicly (--rpc-public) is dangerous when unauthenticated; if you must, set --rpc-api-key.
Ports
16110/tcp P2P · 16111/tcp P2P WebSocket · 16210/tcp RPC (keep local) · 16310/tcp Prometheus metrics (only with --metrics).

Step 4 · Or run a miner

Solo-mine on the mainnet beta.

# make a miner address first (only the public address is used to mine):
./target/release/bloch-cli newwallet ~/miner-wallet.json   # prints: Address: bloch1q…

./target/release/bloch --mine \
  --miner-address bloch1q…YOUR_ADDRESS \
  --data-dir ./bloch-data \
  --listen /ip4/0.0.0.0/tcp/16110 \
  --peer /ip4/45.32.154.137/tcp/16110

Adding --mine makes the node brute-force Module-SIS solutions (under the current ramp gate — k=4 today, rising toward k=8 as hashrate grows) and attach the solution vector as each block's PoW witness, with the coinbase paid to --miner-address. Mining via the node is solo only: Stratum V1/V2 pool mining is disabled because the hash-PoW share protocol has no field for a lattice solution vector — a SIS-native pool dialect exists separately (see Pool).

To be blunt about the economics: the coins you mine carry no value claim — no price, no market, no listing — on a nascent, low-hashrate network that is 51%-attackable. The ramp's k is a structural filter, not a security claim — raising k adds no cryptographic hardness at β=q/16; what mining actually contributes is cumulative hashcash work, the only real security source. Mine to exercise the machinery and add hashrate to a young network, not as an investment.

Step 5 · Check it's alive

Query the node over RPC.

# with the bundled CLI (defaults to 127.0.0.1:16210):
./target/release/bloch-cli getnetworkinfo
./target/release/bloch-cli getblockcount

# or raw JSON-RPC over HTTP:
curl -s -X POST http://127.0.0.1:16210/ \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"getnetworkinfo","params":[]}'

getnetworkinfo reports version, network (current builds still report the legacy string testnet for the live mainnet-beta chain — a rename ships in a later release), peer count, and sync state. Other read methods include getblockcount, getdaginfo, getmempoolinfo, getpeerinfo, getblockbyheight, and getbalance. Optional Prometheus metrics: add --metrics and scrape 127.0.0.1:16310.

Step 6 · Peering

Every node is a seed. No node is privileged.

The shipped seed list is empty — literally DEFAULT_SEEDS = [] in the source. That is the ethos, honestly applied: no foundation-run bootstrap servers, no DNS seeds yet (a TODO in the code), no node with a special role. The flip side, stated just as honestly: your node will sit alone until you give it a peer. This step shows exactly how to give it one, so anyone — with zero prior context — can join.

First, what a peer address (multiaddr) looks like

You bootstrap by handing your node the multiaddr of any node already on the network. A multiaddr is just a slash-separated recipe for "how to reach this machine". You will only ever need these two shapes:

/dns4/<hostname>/tcp/16110     # reach a peer by DNS name
/ip4/<a.b.c.d>/tcp/16110       # reach a peer by raw IPv4 address
#     └── who ──────┘ └─port┘   16110 is the default P2P port

That address is simply the other node's --listen address as seen from your side of the network — nothing more. Now use it.

The one-line way to join, right now

To break the cold-start, here is one node Postern keeps online for the mainnet beta. Point your node at it and you are on the network:

./target/release/bloch \
  --data-dir ./bloch-data \
  --listen /ip4/0.0.0.0/tcp/16110 \
  --peer /ip4/45.32.154.137/tcp/16110

Honest note: that node is a convenience, not an authority

The address above is one Postern-operated node offered purely to break the cold-start — it is not a privileged seed. DEFAULT_SEEDS is still empty in the source, it is not hard-coded into any build, it does not gate consensus, and if it vanished the network would continue unchanged. Do not treat it as official infrastructure — the ownerless protocol has none. It is a starting line, not a gatekeeper: peer with others too, and the moment you are connected, your node is a seed for the next person.

Confirm you actually connected

Give it a few seconds, then ask your node who it is talking to. The peer count should climb above zero and your height should start catching up to the network:

./target/release/bloch-cli getpeerinfo      # peer_count > 0 means you're in
./target/release/bloch-cli getnetworkinfo   # watch "peers" and "blocks" rise

After the first contact, it runs itself

--peer can be repeated to dial several nodes at once, and DNS names are resolved automatically. Once you have any connection, peer exchange (PEX) takes over: your node learns more peers from the ones it already knows, persists them in the data dir, and redials them on every restart — so you only ever need one good address once. Prefer more than one bootstrap peer? Add a friend's node, or one shared in the community channel, on its own --peer line.

For LAN or single-machine experiments, add --allow-private-peers so RFC1918/loopback addresses (like a second node at /ip4/127.0.0.1/tcp/16110) are accepted. And if you have no peer to dial at all, start an island: run one miner and one relay pointing at each other. On a network this young — very few nodes, stated plainly — every new peer measurably matters.

Recent peering upgrade — past the ~50-node wall

A bootstrap node used to cap at a hardcoded 50 peers and drop newcomers, and fresh miners could fork from genesis. Fixed with non-consensus knobs (--max-peers, --dns-seed) and a mining-readiness/IBD-latch guard. What changed and how to set up correctly: Release notes → · root-cause PDF ↓.

Why the network wasn't growing past ~50 nodes — and how to set up correctly

A bootstrap node used to cap out at a hardcoded 50 peers and drop every newcomer, and fresh miners forked from genesis instead of syncing. Both are now addressed with non-consensus operator knobs (--max-peers, --dns-seed, and a sync-before-mine guard). The full root-cause write-up and the correct setup procedure:

Alternative · Docker & Fly.io

Containerized, if you prefer.

The repository ships a Dockerfile (digest-pinned base images, non-root user, core dumps disabled) exposing 16110, 16111, 16210, and 16310. Build and run from the repo root:

docker build -t bloch-sis .

docker run -d --name bloch \
  -p 16110:16110 -p 127.0.0.1:16210:16210 \
  -v bloch-data:/bloch-data \
  bloch-sis \
  --rpc-bind 0.0.0.0 --rpc-port 16210 \
  --listen /ip4/0.0.0.0/tcp/16110 \
  --data-dir /bloch-data

Inside the container RPC must bind 0.0.0.0 to be reachable; the -p 127.0.0.1:16210:16210 mapping keeps it local to your host. Add --mine to the arguments to mine, and --peer <multiaddr> to bootstrap.

The repo also carries a fly.toml for Fly.io (it runs the node with --mine on a persistent volume). From the repo root:

flyctl launch --copy-config --no-deploy   # first time: creates the app
flyctl volumes create bloch_data --size 30 --region <your-region>
flyctl deploy

See deploy/fly/README.md in the protocol repo for the full walkthrough — and remember what the machine will be doing: mining coins that carry no value claim, on unaudited mainnet-beta research software.
