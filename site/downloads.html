Get the beta

Everything ships as source. On purpose.

Postern's integrity story is reproducibility: you build what you run, and the same inputs produce the same artifact. The x86_64 Postern OS ISOs are now hosted, release-signed, and click-downloadable below — with their SHA-256 digests and a minisign signature beside them, so you verify before you boot. the node ISO now QEMU/TCG-boots to a login prompt (boot log recorded); the desktop ISO's QEMU boot is still pending, and a physical-hardware boot is further out; the aarch64 mobile image is now built, hosted, and release-signed too — but not yet boot-tested on any platform (no QEMU-aarch64 or hardware boot), so treat it as the least-proven download. Building from source remains the strongest verification, and it's still here. Here is exactly what you can run today, and how.

Honest status — read before anything else

  • Everything here is pre-production. The Rust product cores are built and test-verified. The OS images have started to exist: the x86_64 node and desktop ISOs are built, hosted, and release-signed — the node ISO now QEMU/TCG-boots to a login prompt (boot log recorded, grader rc=0); the desktop ISO's QEMU boot is still pending, and a physical-hardware boot is further out; the mobile image (aarch64, PinePhone / Mobile NixOS) is now built, hosted, and release-signed, but not yet boot-tested on any platform — it has not been booted on QEMU aarch64 or on hardware, so it is the least-proven of the three. The UIs and cloud/enterprise editions remain designs and reference prototypes. Hosting a signed image is not attestation, and built is not booted — we don't claim otherwise. Each item is labelled with its exact status wherever it appears.
  • The underlying protocol now runs a mainnet beta — a designation, not a security claim. As of node v0.1.0-alpha2 the fixed k=8 Module-SIS gate is retired: the gate is a difficulty-driven k-ramp — k=4 today, rising 5→6→7→8 as the network's own ASERT difficulty (the on-chain hashrate proxy) sustains above spaced thresholds, and easing back if hashrate falls (the Bitcoin model). Raising k adds no cryptographic hardness at β=q/16 — the ramp is a structural/throughput filter, not a security claim, and no security is claimed. Real security is cumulative SHAKE-256 hashcash work — hashrate × time. A brand-new node can sync from genesis again under the ramp, or use the signed snapshot as an optional one-command fast-sync. The network is nascent: very few nodes, low hashrate → 51%-attackable. It is unaudited — a third-party audit is contracted but not done yet, and the concrete-security analysis and IACR ePrint are still outstanding.
  • The coin is not a security and not an asset. No token sale, no listing effort, no market-making, no price. Disclosed in full: a 17% founder premine (10-year cliff, 40-year vest), structurally passive.
  • Do not use any of this to protect real secrets yet. It is a public beta for evaluation, feedback, and reproduction of our claims.

Want to see what's not done yet? Two roadmaps — because the two layers must never blur. The old single "Future Roadmap" PDF mixed the ownerless protocol and the owned products in one plan; it is replaced by two documents. Bloch — open protocol items (Markdown) ↓ is not a company plan and has no owner: the base follows the Bitcoin model — no authority, no schedule, no dates — so it is an honest list of candidate items any node operator or community member may pursue, BIP-style: further gate/difficulty tuning beyond the difficulty-driven k-ramp, the third-party audit, the no-shortcut proof and IACR ePrint, a live multi-node WAN network, Coherence (shielded txs — no privacy claim today), and the neutral permissionless tokens / fork / L2 capability. Nobody schedules these; the community may create a foundation someday if it chooses — its prerogative, not Postern's; Postern does not drive the protocol. And the base stays pure PoW: BFT and oracles were removed from base consensus and stay out — the base's only built-in finality is checkpoint reorg-depth protection, a normal PoW feature, not a gadget and not governance. Distinct from the base, a post-quantum FFG-BFT finality overlay (hashrate-weighted, anchored as ordinary zero-value transactions — not a base-consensus change; coins still do not vote) is a candidate item with a declared activation target of block 1,000,000, not built (see the roadmap note). The rule: the base is ownerless; anything with an operator, a service, or a "who runs it?" answer is a Postern product. Everything on both lists is unaudited, the chain's gate is the difficulty-driven k-ramp (k=4 today — a structural filter, not a security claim by itself), there are no promises and no dates on the ownerless side, and BLCH is not a security — Postern's revenue never touches the token.

3 · The reproducible OS

Postern OS — download, verify, then boot.

The os/ directory holds declarative NixOS profiles: a minimal image that boots into a running node as a hardened systemd service (dedicated user, ProtectSystem=strict, syscall filtering), plus desktop, mobile, browser, cloud, and attestation profiles. Because it's Nix, the same inputs produce the same image — that reproducibility is the product.

Honest status: the x86_64 node and desktop ISOs are now hosted, release-signed, and downloadable below, each with its SHA-256 digest and a minisign signature. A QEMU boot is still pending for both — no boot log or .evidence sidecar is published next to either ISO yet, so we make no boot claim — and a boot on physical hardware is further out. Hosting and signing a release is not attestation; built is not booted; we won't imply otherwise. The mobile image (aarch64, PinePhone / Mobile NixOS) is now built, hosted, and release-signed and is downloadable below with its SHA-256 and the same signed checksum list — but it has not been boot-tested on any platform (neither QEMU-aarch64 nor hardware), so it is the least-proven artifact here and "built + signed" is emphatically not "it boots." Prefer to build it yourself? That path is still below, and it remains the strongest verification.

Verify before you boot — both steps, every time

A download you haven't verified is a download you're trusting to the network. Fetch the SHA256SUMS list and its minisign signature into the same folder as the ISOs, then run both checks — neither is optional:

# 1. Checksum — every ISO you downloaded must verify against the signed list
sha256sum -c SHA256SUMS

# 2. Signature — proves the checksum list itself was published by Postern.
#    The key is inline below; or fetch it:
#    https://pub-dca67fd26bfb4a6b98115e596095ecd3.r2.dev/os/keys/postern-os-minisign.pub
minisign -Vm SHA256SUMS -P RWTSe98wfKKHuVRDnywuQmH/cMyP/HNuD/hFFLQeKdQeAHENliqJpmKs

The checksum proves the file is intact; the signature proves the checksum list came from us. You need both. The minisign public key RWTSe98wfKKHuVRDnywuQmH/cMyP/HNuD/hFFLQeKdQeAHENliqJpmKs is published here, as a file, and in the release notes, so you can cross-check it from more than one independent place.

Before you install — read these

  • Back up first. The installer repartitions the target disk and everything on it is gone. There is no undo.
  • Full-disk encryption (LUKS) means your passphrase is the data. Lose it and nobody — including us, by design — can recover the disk. Store it somewhere that isn't the same machine.
  • Secure Boot: these images are not signed for Microsoft-endorsed Secure Boot yet. Disable Secure Boot in firmware, or enroll your own keys — both change your machine's security posture. Signed-shim support is planned, not shipped.
  • No boot has been observed yet. Neither ISO has a published QEMU boot log, and neither has booted on physical hardware. Treat both a QEMU boot and a real-hardware install as unproven until the boot evidence is published.
  • The mobile .img is the least-proven artifact — it has not booted anywhere. It is built, hosted, and release-signed, but it has never been booted on QEMU-aarch64 or on a PinePhone. Flashing it to a device is genuinely experimental; the first hardware boot has not happened. Verify the signature, but don't expect it to come up yet.
  • Mainnet beta, unaudited — not a security claim. Hosting a signed image is not attestation. Evaluate it and reproduce our builds; don't protect real secrets with it yet.

Prefer to build it yourself? That is still the strongest verification — the same inputs produce the same image, which is the whole point:

# On a Linux host with Nix + flakes, from the source tree:

# Bootable node ISO  ->  ./result/iso/*.iso
nix build .#iso

# Desktop ISO  ->  ./result/iso/*.iso
nix build .#desktop-iso

# Just the node package
nix build .#bloch && ./result/bin/bloch --help

# Try it in a VM without flashing anything
nixos-rebuild build-vm --flake .#bloch-os && ./result/bin/run-*-vm

The mobile edition is built, hosted, and release-signed, but not yet boot-tested on any platform. See the honest labels on the products page.

3b · The non-attestable tier

Postern for postmarketOS — community edition. The apk repo is now published.

A separate, deliberately humbler product: the Postern suite packaged as ordinary postmarketOS/Alpine apk packages for phones postmarketOS already supports. It is not “Postern OS” and never will be called that: Alpine packages are not reproducible and not attestable — our apk signature proves who published it, not what it was built from — and wallet keys on this platform are software-backed, not hardware-backed. The attestable images are the Nix-built “Postern OS” family above, only.

Honest status: three packages are now built, signed, and published for aarch64, in one signed Alpine apk repository on our public R2 bucket (one signing key for all three): postern-wallet (the real light-wallet CLI), postern-apps (the web-app bundle), and postern (a meta that pulls the two and declares the pmOS runtime deps — phosh + tor — which only resolve on a booted pmOS). Built natively on an aarch64 host (no qemu, no cross) in an Alpine container with abuild, from source tarballs pinned to the v0.1.0-alpha1 tags.

What that is not, spelled out: it is three apks and an index — not an operating system; the flavor / bootable image is not built. It is signed with an alpha build key (builder-6a52d247), not a stable, long-lived Postern release key — treat the signature as “this build, this key,” not a trust anchor. It has never been booted or run on a physical device — “built + signed + installs via apk” is not “runs correctly on your phone.” Non-attestable (Alpine/musl, not Nix), unaudited, and the coin the wallet holds is worthless by design.

Which phones can it reach?

Because these are plain aarch64 apk packages, they add onto any 64-bit postmarketOS install — and postmarketOS itself now reaches on the order of ~700 device models. But reachable is postmarketOS's word, not ours: we have booted Postern on none of them. "the apks install" is not "it runs on your phone."

postmarketOS sorts devices by how complete their support is. Since the v24.12 release the top main tier is essentially QEMU-only; the real, actively-maintained phones live in community, and the long tail (254 devices in the v26.06 release the apks target) sits in testing, where core hardware — modem, camera, GPU — may simply not work yet. postmarketOS's own device pages at wiki.postmarketos.org are the source of truth for what each one can and can't do; check yours before you expect anything.

4 · The desktop app

Postern Desktop — Tauri, build from source.

A desktop app for the OS you already run (Linux first; cross-platform): start/stop and monitor a node, hold a wallet (mnemonic shown once, byte-identical addresses to the mobile core), watch the miner, stream the logs. Rust backend, dependency-free web UI.

Postern Desktop includes an Encrypted Backup pane and a Swap pane — both reference prototypes, unaudited:

  • Encrypted Backup → Filecoin. The pane seals a file locally with the Postern AEAD seal (XChaCha20-Poly1305), writes a post-quantum SHAKE-256 “DATA0” integrity anchor, then performs a real upload of the sealed ciphertext to Filecoin through a Lighthouse S3 token — a real content ID (CID) comes back. Only sealed ciphertext ever leaves the device; keys and plaintext do not. It spools through a durable, crash-safe on-disk backup queue (the DirBackend spool). A reference prototype, unaudited — don't entrust a real backup to it yet.

It builds from source in desktop/ with the standard Rust + Tauri toolchain (cargo tauri build after the Tauri prerequisites for your platform). The desktop command surface is hardened — a sidecar sha256 integrity-pin (fail-closed), default-deny capabilities, a strict CSP — but that is a pin, not an audit, and everything here is a beta.
