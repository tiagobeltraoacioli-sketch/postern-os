Syncing from genesis is not possible — and the older snapshot is now a dead end

Block bodies below roughly height 376,422 were pruned on every node and are unrecoverable, so a node started empty asks for block 0 and no peer can answer. Worse, the previously published bloch-db-snapshot.tar.gz ends at 394,361 while peers have since pruned below ~394,913 — a node restored from it stalls forever in the ~550-block gap, with connected peers and a healthy-looking log.

Use the snapshot below (height 408,482). It starts above the gap and syncs normally. Verified end-to-end on a real machine, not assumed.

The mechanism worth understanding: pruning deletes bodies below tip − 10,000, so a published snapshot must be refreshed before the network prunes past the height it ends at. Miss that window and the path from snapshot to tip breaks silently. This network hit exactly that.

Why you might want this

Genesis sync works — the snapshot just skips the wait.

The Module-SIS gate is now a difficulty-driven k-ramp (node v0.1.0-alpha2): k=4 today, rising toward k=8 as the network's own difficulty grows. Under the ramp's k=4 rule, the historical chain validates again — the earlier fixed k=8 gate, which made the k=4-mined history unvalidatable from genesis, is retired. So a brand-new node has two valid paths:

  1. Sync from genesis — full validation from block zero, the strongest-trust path. Just point the node at a peer and let the initial block download run.
  2. Restore the signed snapshot — a pruned capture of a current node's chain state at the tip. Your node skips the initial block download, boots at the tip, and mines forward under the current ramp (k=4 today). A convenience, not a requirement.

Honest tradeoff

The snapshot path is a trust-the-operator bootstrap: you trust the snapshot's chain rather than verifying it yourself from genesis. That is a real, disclosed weakening versus full validation — you can avoid it entirely by syncing from genesis — so you should verify the SHA-256 and the signature before trusting any snapshot, and prefer one you can cross-check. Unaudited, zero-value research chain; the coin carries no value claim.

How to do it

One command to be on the network.

You need the built bloch binary first (see Run a node, steps 1–2). Then:

# 1) download the signed snapshot + checksums, and verify
curl -O https://pub-dca67fd26bfb4a6b98115e596095ecd3.r2.dev/bloch-db-snapshot-408482.tar.gz
curl -O https://pub-dca67fd26bfb4a6b98115e596095ecd3.r2.dev/SHA256SUMS
curl -O https://pub-dca67fd26bfb4a6b98115e596095ecd3.r2.dev/SHA256SUMS-408482
sha256sum -c SHA256SUMS-408482     # must print: bloch-db-snapshot-408482.tar.gz: OK

# 2) restore it into your data dir (it holds the pruned chain at the tip)
mkdir -p ./bloch-data
tar xzf bloch-db-snapshot-408482.tar.gz -C ./bloch-data   # → ./bloch-data/db

# 3) start — boots at the snapshot's tip, syncs the small remaining gap, mines
#    (make a miner address first: bloch-cli newwallet ~/miner-wallet.json)
./target/release/bloch --data-dir ./bloch-data \
  --listen /ip4/0.0.0.0/tcp/16110 \
  --peer /ip4/45.32.154.137/tcp/16110 \
  --mine --miner-address bloch1q…YOUR_ADDRESS

Confirm with bloch-cli getblockcount (it should already be near the network tip) and bloch-cli getpeerinfo. The snapshot excludes node identity, so your node generates its own — run as many as you like. Drop --mine --miner-address to run a pure relay/seed.

Snapshot published to the downloads host. It is a periodic capture of a Postern-operated node's pruned state — one operator, not official infrastructure; verify it, or produce your own from any node you trust with tar czf snap.tgz -C <data-dir> db.

Worked example · deploy on a VPS

Standing a node up on Edgevana (what actually worked).

No affiliation — read this

Postern Labs has no association, partnership, sponsorship, or endorsement relationship with Edgevana. It is simply one host we happened to use successfully while testing; any routable VPS or bare-metal box works identically. Nothing here is a recommendation to buy from Edgevana or any provider.

The model we ran — nothing special, a small routable Linux box:

  • Ubuntu 24.04 LTS · ~2 vCPU · ~8 GB RAM · ~33 GB disk
  • A public, routable IPv4 (so it can reach the bootstrap and be reached back) + SSH-key access

On GPUs, honestly: the PoW is SHAKE-256 hashcash + a Module-SIS gate, and the reference miner is CPU-bound — there is no GPU miner today, so a GPU instance buys you nothing for mining right now. A modest CPU box is the working recipe. (A SHAKE/lattice GPU or ASIC miner is buildable — see the ASIC page — but none exists yet.)

# on the VPS (Ubuntu): deps + Rust, then build
sudo apt update && sudo apt install -y git clang cmake pkg-config build-essential curl
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y && . "$HOME/.cargo/env"
git clone <gitlab.com/blochsispow-group/BlochSISPoW-project> bloch && cd bloch
cargo build --release --bin bloch --bin bloch-cli

# restore the snapshot (above) into ./bloch-data — or skip it and sync
# from genesis — then run as a seed + miner
./target/release/bloch --data-dir ./bloch-data \
  --listen /ip4/0.0.0.0/tcp/16110 --max-peers 500 \
  --peer /ip4/45.32.154.137/tcp/16110 \
  --mine --miner-address bloch1q…YOUR_ADDRESS

Keep --max-peers 500 so it can act as a hub/seed for others. Confirm with bloch-cli getpeerinfo and getblockcount. The chain is unaudited and the coin is worthless by design — run it to strengthen the research network, not as an investment.

Standing disclosures

The underlying protocol runs a mainnet beta — unaudited (audit contracted, not done), nascent, low-hashrate and 51%-attackable. The Module-SIS gate is now a difficulty-driven k-ramp (v0.1.0-alpha2): k=4 today, rising 5→6→7→8 as the network's own difficulty grows, easing back if hashrate falls — the Bitcoin model. The ramp is a structural filter, not a security claim: real security is cumulative SHAKE-256 hashcash work — hashrate × time. Nothing here is a certified security product yet.
